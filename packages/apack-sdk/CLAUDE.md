# @apackdev/sdk

The pack-facing API, types and build tooling for apack packs, used by built-in and external packs alike. It also holds the pack build pipeline that `@apackdev/cli` drives (`src/build/`), the content engine the host runs (`src/content/`), and the registries of what registered packs contributed, which read the registry the app binds (it holds no registry of its own). The host-only side lives in `@apackdev/host`.

The root `CLAUDE.md` covers the subpath split (`/repositories`, `/fe`, `/utils` vs `/utils/pure`), the `@apackdev/source` condition, `.ts` relative specifiers, and API reports. This file goes one level deeper. The typed EARS contract is in `TYPED-EARS.md`; read it before touching `src/types/entities.ts`, `src/types/sdk-entities.ts`, `@apackdev/ears`'s `src/entities.ts`, `src/runtime.ts` and `src/typed.ts`, or `generateEars` in `src/build/generate-entries.ts`. Pack-facing guides: `docs/public-facing/manifest.md`, `content.md`, `services-and-data.md`, `testing.md`, `cli.md`.

## Layers

Imports point down only (`check:specifiers`, `findUpwardImports`; `package.json` declares only `@apackdev/ears`):

- `@apackdev/ears` below: the engine, the core `EARS` types and the persistence port. The SDK adds its entities, their shapes and repositories on top, and holds no engine state.
- The SDK: the pack contract and the pack runtime (the registries of what packs registered, the services' contracts, event sends, logging and error reports, the SDK entities' repositories) and the `HostRuntime` port.
- `@apackdev/host` above (never imported here): the five app services, app state, and what the app runs (pack runtime, bus, migrations). The API and the renderer compose and bind it.

The rule for what crosses the port: bind resources, derive behaviour. A resource has identity per running app and is a `HostRuntime` member: the event bus (`transport`), the engine (`ears`), the registered packs (`packs`), the app version and its services (`services`: `appData`, `onboarding`, `settings`, `runHistory`, `inference`, `secrets`, `filesystem`; their contracts are types in `src/services/<name>.ts`, implemented in `@apackdev/host/services/<name>.ts`). Behaviour over a resource is SDK code, written once: the sends, `createLogger`/`onLog` and `reportError` run over the bound bus, and `services.logger`, `services.emitter` and `services.repository` are built here. The registered packs are an instance the composition root creates (the API, the renderer, the harness per test file, the CLI per build) and binds as `packs`; the SDK only reads it (`PackRegistryView`, `FePackRegistryView`), and contexts without an app use `testPacks`.

## `src/` map

Each directory is one `package.json` export (`./<dir>` → `src/<dir>/index.ts`) unless noted.

- `actions/`: pure helpers content actions may inline (`formatProviderError`, `buildTranscript`). It's the only bare import `compileSourceDir` allows in action and prompt sources.
- `artifacts/`, `blocks/`, `steps/`: definition types and their registries (see Registered packs). `steps/` also has `utils.ts` and `result-truncator.ts` (`truncateResult`, `isTruncated`: what a step records on its run node is capped, and made storable — a BigInt as digits, a loop cut where it closes).
  Three of the repo's five value-serialising passes are in this package — that one, the logger's meta pass and `redactSecrets` — and what each decided about a BigInt, a loop, a repeat, a Date and depth is one table: [`docs/references/value-serialisation.md`](../../docs/references/value-serialisation.md). They differ on purpose; read it before making a sixth agree with any of them.
- `build/`: manifest readers, codegen, content compilers and the flow DSL compiler (see Build pipeline).
- `database-console/`: the Database console's code runners, `runQueryCode` (the read helpers) and `runTransactionCode` (read and write helpers) over the bound engine, with the `EARS` the caller passes (`consoleEars(names, { hint? })` builds it from declared entity types and relation kinds, `installedEars()` from the bound app's registered packs, so the console names every installed pack's types, not only the pack whose console it is), `READ_HELPER_NAMES`/`WRITE_HELPER_NAMES` (both spelled out in `tests/database-console/`, since the `query` step's safety rests on a query reaching nothing that writes) and `getSchemaStats`. default-setup's Database surface and query step and `apack db query`/`exec`/`repl` run code with them (`tests/database-console/`).
  **`Entity` and `RelKind` are `Proxy` objects that throw on a name they cannot account for**, naming what is known and the caller's `hint` (the CLI's is `--schema-from`; the app has no such answer and passes none). An unknown name read as `undefined`, and `query(undefined)` means every entity, so a query for one type answered with the whole database. The traps are shaped by what legitimate code does with the object: `db script` is handed it raw, so enumeration, spreading and `JSON.stringify` work; `in` answers rather than throwing, since asking whether a name exists is a question and not a use of it; and a symbol or a `then`/`toJSON` probe reads as absent, or awaiting any result carrying one would throw.
- `designations/`: role → the `FeatureRef` of the feature playing it (`getDesignated`, `hasDesignation`), over the registered packs; its system and its surface share that address.
- `repositories/` (`@apackdev/sdk/repositories`): the repositories of the SDK's entities, over the EARS engine, which is `@apackdev/ears` (`packages/apack-ears`, the SDK's one `@apackdev` dependency; the SDK's `EARS` and entity shapes are in `types/`): `flowRepository` (flows, nodes, edges, the root flow role, `reindexHandles`, `importFromDSL`), `actionRepository` and `promptRepository` (`all`, `byId`, `byLabel`, create, update, delete to the trash). They're plain exports, not registered as a pack's repositories, and they refuse with `RepositoryError` (`repository-error.ts`, exported here: `NOT_FOUND`, `VALIDATION_ERROR` or `OPERATION_FAILED`), which pack repositories throw too; SDK code (the flow applier, `reportError`, the harness's `importFlows`) calls them directly, and default-setup's flows, actions, prompts and brain repositories build their views over them. Soft delete is the engine's trash (`write(id).trash()`/`.restore()`, `query.withTrashed`, `query.trashed`), which actions, prompts, and default-setup's notes, thread messages and terminals use; what trashing means beyond that (a note's sub-notes, emptying the trash) stays with the feature. The engine (`createEarsEngine`: its operations, with `admin` beside them), and its typed helpers (`defineEars`) live there; SDK code reads the bound engine (`boundEars()`, or `untypedQuery`/`untypedWrite`) and never touches engine state.
- `ears/`: the app's engine — `boundEars()` and the host-only `_bindEars`, which `bindHost`, `startTestRuntime` and `openAppDatabase` call — and the operations over it pack code calls without holding an engine (`untypedQuery`, `untypedCreate`/`untypedUpsert`/`untypedWrite`, `transact`, `findRelations`, `wouldCreateCycle`, …). `@apackdev/ears` keeps no engine of its own, so this is where binding lives (`tests/ears/bound-ears.spec.ts`).
- `env/`: `resolveAppEnvironment()`, the single resolver for environment and data paths, `getAppVersion()` (the bound runtime's `appVersion`), and nothing about a running process: reading the API's port file and the liveness predicates behind it are the app's, in `@apackdev/host/process-liveness`. How to reach the API — `API_HOST` and `API_TOKEN_HEADER` — is in `utils/api.ts` instead, so the renderer's client takes them from `@apackdev/sdk/utils/pure` rather than keeping its own copy.
- `events/`: messaging (`untypedBroadcastToSurface`, `untypedSendToSystem`, `_sendToLocalSurface`, `onConnected`, `onIncoming`), `_replyTo(delivery)` — which builds the answer for a message, or nothing when it named no sender, and routes on whether that message came from a connection: with one the asker is a surface or a claimed participant and the answer goes out to that connection alone, without one the ask came from the backend and the answer goes **in**, to the asking system (the ref cannot decide it — a feature's system and surface share one) (`delivery.ts`: one plain variable, set and restored around the call that delivers a message — the same in a window and on the backend, since `reply` is read as a handler is entered rather than when it is called, which is what retired the `AsyncLocalStorage` the host used to install; `_runDelivery` and `_currentDelivery` are the `@internal` halves, and three doors set it: the bus routing a message to a system (`deliverAs`), `sendToSurfaceActor` — the one function in a window every send to a surface's actor goes through — and `useSurface`, which wraps the actor a component is given so a click is named like anything else). **Pack code never reads that scope.** A handler is *handed* its answer: `defineHandlers`/`defineSystem` (`framework/`) wrap a machine's action record so each handler receives `reply`, bound to the delivery it was entered in and absent when the message named no sender — or when the event the handler handles is not the one that delivery delivered (`_Delivery.event`, the object a door hands the receiver), since an event a machine makes while handling a message is not that message and its handler has nobody to answer — so "is there anybody to answer?" is a question the type asks rather than one a global is probed for, and an answer a handler stores keeps working wherever it is called. An exported `reply()` that read the scope itself is what this replaced; what the scope is still read for here is `createSends`' `Message.sender` stamp, which cannot be a parameter without every send in pack code carrying one — and which is therefore the one thing that now stops at the first `await`, deliberately: four sends in the repo are made after one, none of them answered — and `defineEvents`, which builds the typed `broadcastToSurface`/`sendToSurface`/`sendToSystem` a pack's `#generated/events` exports over them and stamps `Message.from` with its pack's id (the untyped ones leave it absent). Every send is built by `createSends(binding)`, so what travels beside the event is threaded there rather than added to each send and to every caller with nothing to pass: `defineEvents` binds a pack's id, `createActionEmitter` (`services/`) binds the pack running an action plus `via: action:<label>`, and `reportError` binds `via` alone. `senderSuffix(message)` is how a diagnostic names either — one format for the four places that report an undeliverable message. The `untyped` prefix is the rule in the root `CLAUDE.md`; `_sendToLocalSurface` keeps its underscore because it is host-only, not merely unchecked and the event map types (`HostSurfaceEvents`, `HostSystemEvents`: what the host's surfaces and systems take from packs). `untypedSendToSystem` takes a system's ref or a role (`{ role: 'brain' }`, resolved through the designations when sent). Frontend-safe: it sends over the bound runtime's bus (`HostRuntime.transport.rootEvents`), or in the renderer over the frontend port's `client`. `untypedBroadcastToSurface` emits a surface send (`emitSurfaceSend`), which the app's bus delivers only while a client is connected — to every window showing that surface, since a surface runs once per window. Its renderer half is `sendToSurface`, which goes straight to this window's actor for that surface (`_sendToLocalSurface`); each throws naming the other when only the other host is bound, since the two share a signature.
- `fe/`: surface contracts and the frontend state packs share with the host (`actor-system.ts`: `useSurface`, the surface a component belongs to, which `SurfaceScope` provides for a registered ref (`tests/fe/surface-scope.spec.ts`); it hands back the actor with its `send` run inside a delivery naming that surface, so an action the send reaches stamps `Message.sender` and the system it asks can answer *that* surface in the window it was asked from (`tests/fe/surface-send-scope.spec.ts`) — one wrapper per actor, everything but `send` passed through, and `subscribe`/`getSnapshot` — what a selector is built on — pinned to reach the real actor through it; `surface-state.ts`: `useUntypedSurfaceState(ref, selector)`, `readUntypedSurfaceState(ref, selector)` and `surfaceIsRunning(ref)`, which read *another* surface's state by ref for code with no `SurfaceScope` to read — an extension component the host renders wherever it belongs — over the shell's registry of running surfaces, handing back a value and never the actor. They are the untyped escape hatch beside the typed readers `#generated/fe` generates from each surface's contract, so both give `TSelected | undefined`: a ref is a name, and nothing about a name says the surface is running. The reactive one follows the surface until the calling scope is disposed and throws outside a scope, and follows the shell's snapshot too, so a surface arriving or reloading is picked up; the other takes the value once (`tests/fe/surface-state.spec.ts`), and `shell.ts`: `HostShell`, the app shell's contract (the state frontend code may read and the events it may send), which types the port's `application` and which the host's shell is checked against where it's defined, and `useShell()`, its state as read-only refs and named commands, which follow the shell until the calling scope is disposed and throw outside a scope (`tests/fe/use-shell.spec.ts`); `menu-state.ts`), the frontend editor bindings (`text-editor-extensions.ts`), catalog DSL readers (`dsl-reader.ts`) and `PackFERegistration` (`pack-fe-registration.ts`, executable frontend bindings). `navigation.ts` opens surfaces: `untypedOpenSurface(ref, event?)`, which the host and a ref that arrives as data (a link block's target) use directly, and which the `openSurface` a pack's `#generated/fe` builds wraps, and which throws only for a string that isn't a `<packId>/<featureId>`; it sends the shell `OPEN_SURFACE`, which waits for a surface whose pack's frontend is still loading and reports a ref no pack provides once loading has settled (`tests/fe/open-surface.spec.ts`; the waiting in `@apackdev/host`'s `tests/features/application/fe/open-surface.spec.ts`). `views.ts`: `untypedUseView(ref, view, args?)` and `ViewState`, a view followed over `FeClient.watchView` until the calling scope is disposed — `idle` while its arguments are `null` or `undefined`, subscribing again only when they ask for something different (`viewKey`), and ignoring whatever an ended subscription delivers late (`tests/fe/views.spec.ts`); the typed `useView` is a pack's `#generated/fe`. `view-actor.ts`: `untypedFromView(ref, view, read)`, the same subscription as XState actor logic a surface's machine spawns with the view's arguments and stops when it no longer wants them, for a surface drawn in several areas (`tests/fe/view-actor.spec.ts`); the typed `fromView` is the pack's `#generated/fe` too. `surface.ts` also declares `SurfaceLifecycleEvent` — `SURFACE_STARTED`, `SURFACE_ACTIVATED`, `SURFACE_DEACTIVATED`, what the shell hands each surface in a delivery naming it. `./fe/references` maps to `fe/reference-types.ts`.
- `framework/`: `defineViews` and the views' wire types (`views.ts`: `ViewRequest`, `ViewUpdate`, `viewKey` — the key two requests share — frontend-safe, so `fe/views.ts` and `@apackdev/host/views` import it alike), `defineSystem`, `packSystem` (a feature's system for its registration: adds the manifest's incoming events to its machine's; `tests/framework/pack-system.spec.ts`), the `PackRegistration` contract (`pack-registration.ts`: the pack's `features` keyed by feature id, from which the app derives every ref, system, surface and role, and its `appliers`), feature settings (`pack-settings.ts`: registered defaults and validators; declarations use JSON Schema) and the registered commands (`pack-commands.ts`).
- `helpers/`: `safeEvents` and `Simplify`.
- `ids/`: feature refs. A feature is `<packId>/<featureId>` everywhere, and the app itself is the pack `host` (`HOST_PACK_ID`). `PACK_ID_PATTERN` and `FEATURE_ID_PATTERN` are the ids' grammar, which `splitRef` and `resolveName` check. `resolveName(name, packId)` is the one conversion from a name pack code writes (its own feature by id, any other by ref) to its `FeatureRef`, and throws for a bare name with no pack to own it; `splitRef` takes a ref apart. `refProblem(kind, name, lookup)` says why a name stands for none of a set of refs (the form to write, the one it probably meant, what there is), and `resolveRegistered` is it plus a throw: the harness, `services.emitter` and `services.settings` all diagnose a name through them. `FeatureRef` is branded, so a hand-written string can't reach a call that takes one (`tests/ids/feature-ref.spec.ts`).
- `logger/`: `createLogger` (with the per-source debug toggle) and `onLog` (`logger.ts`): bound, a logger redacts each entry and emits it as a log event on the bus (meta made JSON-safe, an error entry's stack from `meta.error` or the call site); unbound (tooling), it writes to the console. `reportError` (`report-error.ts`): without `step`, a log event plus a `SYSTEM_ERROR` (`SystemErrorEvent`) to the `application` surface; with `step`, a step error logged, recorded on its run node and sent as `BRAIN_RUNTIME_ERROR`. Both sends carry `Message.via` — the source they were given, the same string the caller's logger is named — and no `from`: a report is made on behalf of a caller that is a source, never a pack.
- `runtime/`: the port to the app. `host-runtime.ts`: `HostRuntime` (`transport.rootEvents`, `ears` — the app's engine (`Ears` from `@apackdev/ears`, without `admin`), which `bindHost` binds for `@apackdev/sdk/ears`'s operations — `packs: PackRegistryView` (the registered packs, read-only), `appVersion`, `services`: the app's implementations, and the optional `redaction: SecretRedaction`, which `bindHost` installs as log redaction's secret-value matcher — the host owns the values, the SDK only reads the predicate, so no pack can install its own (`tests/utils/secret-matcher-reach.spec.ts`)), `bindHost` (once per process), `unbindHost` for tests (which also unbinds the engine) and `boundHost()`, which throws naming `bindHost`. `packs-view.ts`: `PackExtensionsView` (what backend and frontend both look up: `designation`, `step`/`steps`, `artifact`/`artifacts`, `block`/`blocks`), `PackRegistryView` (adds `getRegisteredServices`, `systemIds`/`surfaceIds` (the registered refs), `content.writers`, `appliers`, `settingsCatalog` (data-only settings definitions, including disabled installed packs), `onCatalogChanged` (committed contribution declaration changes), `surfaceDefaults` (navigation policy), `earsNames`) and the `@internal` `_boundPackExtensions()`: the frontend host's `packs` when one is bound, else the backend's, throwing naming `bindHost` and `bindFeHost` when neither is. Sends to systems (`sendToSystem`) follow the same rule: over the frontend's `transport` when it's bound, else onto the backend's bus (`tests/runtime/bound-transport.spec.ts`). `fe-host.ts`: `FeHostRuntime` (`application`, typed `HostShell`; `secrets`; `client: FeClient`, the window's client to the API, whose `send` the SDK's frontend sends use and which the host's shell extends as `ShellClient`; `packs: FePackRegistryView`, which adds `surfaces`, `textEditor`, checked step/artifact/block bindings and `appExtension`) and `bindFeHost`, `unbindFeHost` and `boundFeHost()`; the renderer binds it before it creates the application actor (`application` is a getter). `internals.ts` (`@apackdev/sdk/runtime/internals`) exports `unbindHost`, `boundHost`, `unbindFeHost` and `boundFeHost` for host code and tests; the package exports it only under the `@apackdev/source` condition, the one export with no published target — so the published manifest has no such entry at all (`publishedManifest` drops one the condition was the whole of), and packs can't unbind the app or reach its raw services, and the pack loader's bridge leaves it out (`tests/runtime/internals-entry.spec.ts`). `root-events.ts`: the `RootEvents` contract (public: `HostRuntime.transport` names it) and the `@internal` `_rootEvents`, which delegates each call to the bound bus. `fe/secrets-client.ts` delegates `secretsClient` to the frontend port's `secrets` (the `SecretsClient` contract); the SDK holds no general API client. Nothing else reads the app.
- `templates/`: runs prompt function bodies (`executeTemplate`, `createTemplateResolver`).
- `content/`: the content engine (see Content engine).
- `services/`: `HostServices` inventories supported APIs; generated pack facades expose only their accepted selection. `PackServiceAccess` carries the normal view and `servicesForAction(label)`, which keeps the same lifetime/selection and attributes logger/emitter messages. The host owns that factory; pack code supplies labels, not caller identity. No ambient `services` value is exported. Contracts cover `appData`, `onboarding`, `settings`, `runHistory`, `inference`, `secrets` and `filesystem`; `run-history.ts` also holds the one implementation (`_createRunHistory`) over the records the host or a test gives it; `createActionEmitter` is the underlying baseline send helper, and `./models` maps to `services/models.ts`.
- `testing/`: the in-memory runtime behind `@apackdev/testing/harness` (see Testing entry).
- `types/`: `EARS` (`entities.ts`: the engine's namespace with the SDK's entity types, relation kinds and roles), and the entities the SDK owns (`sdk-entities.ts`: `SDK_ENTITIES`, `SDK_REL_KINDS`, `SDK_ROLES` (the flow model's `root_flow` and `entry_event`), `SDK_ROW_RULES` (each SDK shape's required fields and short-code prefix, which the compiler holds to the shapes), `SDK_SHAPED_ENTITIES`): the flow model (Flow, Node, Action, Prompt) and the document model (Document, Collection). A flow run is a record in the run history, not an entity. Settings and the app's state (`AppState`) belong to the host.
- `utils/`: `index.ts` (Node), `pure.ts` (environment-agnostic), and `importCompiledContent` with the `ContentApplier` contract (`apply.ts`). CLI resolution isn't here: it's default-setup's code feature's (`features/code/be/utils/resolve-cli.ts`). `./cron` and `./utils/compare-versions` are single-file exports. `internals.ts` (secret redaction's host side) is exported only under `@apackdev/source`.

## Build pipeline (`src/build/`, `@apackdev/sdk/build`)

`apack pack build` (`packages/apack-cli/src/commands/build.ts`) runs these pieces in order: `parseManifest`, then codegen (`generatePackFiles`), then `buildPackConfigFromManifest` and `compilePack`. It writes the snapshot and bundles itself; the FE bundler is `apack-cli/src/build/fe-bundler.ts`, not an SDK module.

- **Manifest schema** (`../framework/declaration-schema.ts`): the Zod `ManifestSchema` is the single source for `apack.json`.
  - `manifest.ts` derives `PackManifest` and the other types with `z.infer`. It also defines `PackSnapshot` (with `provenance`: every entity, relation kind, command and surface the pack's tree declares, and which pack declares each), `PackProvenance`, `PROVENANCE_KINDS` and `_mergeProvenance()`/`_buildProvenance()` — one table and one reader, so a new kind of declared name is a line rather than a type pair and a reader — plus `PackFlowHelpers`, `contentFile`/`contentPath` and `CONTENT_COMPILERS_FILE`.
  - The cross-field rules live in `superRefine`:
    - A `content.sources` format must name a `content.formats` entry or `<dependency>:<name>`.
    - `content.writers` may name only the pack's own `entities`.
    - Feature/data entity keys are wire identities, with a shape reference or null as their value; they cannot redeclare SDK entities. `data.relations` lists unique snake_case wires, with uppercase EARS constants, and cannot redeclare SDK relation wires. Shared projections feed generators, provenance and host readers.
  - A feature id may not be a JavaScript reserved word (`RESERVED_FEATURE_IDS`), and `extensions.appExtensions` keys must be identifiers: both become names in generated code.
  - `SPECIALTY_CONTENT_KEYS` (`actions`, `prompts`, `flows`, `documents`, `commands`) take a path. Every other content key takes `{ path, format }` (optionally with `applier`: the pack module content the compiled records instead of the format applier) or `{ applier }` alone. No pack in this repo uses either form, so a change to them is covered by `tests/build/` and nothing else.
  - `apack.schema.json` is generated from the schema by `scripts/generate-schema.ts` (`zod-to-json-schema`). Run `schema:update` after changing the schema; CI runs `schema:check`.
- **Validation** (`validate.ts`): `parseManifest`/`validateManifest` run the schema. `validatePackSources` checks all declared module files without dependencies or activation and refuses duplicate feature designation claims. Validation and codegen share a declaration-derived target list with type, script and component resolution. A designation is a role, so it need not equal the feature id.
- **Codegen** (`generate-entries.ts`): `generatePackFiles(manifest, { packRoot, depTypes?, depSnapshots? })` returns `{ path: content }` for `src/__generated__/`. The CLI's `generate-entries` command writes the files; empty contents are dropped.

  **Contracts are declared types, and codegen reads them as types.** A feature names one per actor in `apack.json` — `features.<id>.system.contract` and `features.<id>.surface.contract`, each `"path#Export"` — and codegen reads it with `declaredTypeOf` (`module-exports.ts`), never by resolving the machine or the surface. A system's contract holds `context`, `incoming`, `internal` and `outgoing`; a surface's holds `state` and `inbox`. `internal` is what a system's own children send it: it reaches the machine's event union and no dependent's facade, and narrowing it changes nothing at runtime, since a system's accepted events come from its machine's transitions.

  Both contracts live in leaf modules (`be/contract.ts`, `fe/contract.ts`) that import no machine, no other feature and nothing generated but `types` and `ears`. That is not style: `#generated/events` imports both contracts and both actors import `#generated/events`, so a contract that can reach its actor closes a cycle. The `contract-leaves` pack rule (`apack-cli/src/build/pack-features.ts`) walks the closure of each leaf and fails on an import that does — for every pack, through `apack pack validate` and `apack pack build`, and for this repo's packs as `findContractLeafImports` through `npm run check:specifiers` and the chain's `typecheck`.

  It used to work the other way — a value carrying phantom `_incoming`/`_outgoing` properties, read with `propertyType(spec, '_outgoing')`. That is why an entry declared `const entry: SystemEntry = …` silently published no events at all: annotating the value widened it and dropped the phantoms. Nothing carries phantoms now, and `tests/build/no-phantom-contract.spec.ts` fails if any comes back. `MachineMatchesContract`, asserted per feature in the generated pack entry, is the other half: it fails the pack's typecheck when `defineSystem<C>()` is given a contract other than the one the manifest names.
  - Pack entries and ids: `pack-entry.ts` (the `PackRegistration`, its features in manifest order), `pack-entry-fe.ts` (surfaces, the default surface and designations keyed by feature), `ref.ts` (`ref(name)`, the ref a name in the pack's code stands for, bound to the pack) and `fe.ts` (`openSurface` and `SurfaceName`, taking the names pack code writes).
  - Typed facades: `ears.ts`, `events.ts` (a surface's key is what its own feature's system sends it, plus the inbox the surface's `Contract` declares, a type codegen reads from the leaf `apack.json` names at `features.<id>.surface.contract`; `PackSurfaceEvents` carries only the declared half into the facade, so a dependent sends what the owner published and never what passes between a feature's own halves), `services.ts`, `repository.ts` and `repositories.ts` (the pack's repositories by name, which `pack-entry.ts` puts in `PackRegistration.repositories`; nothing registers on import). A repository name a direct dependency declares fails codegen, the way a dependency's command name does, so the collision the app's registry refuses shows at build time.
  - `pack-types.ts`: the facade dependents import, which `apack pack build` bundles into `dist/types/pack-types.d.ts`.
  - Writing: `appliers.ts` (`appliers`, an applier per written key, which `pack-entry.ts` puts in `PackRegistration.appliers`, plus `setCompiledDir`/`getCompiledDir`) and `content-runtime.ts`.
  - Flows and steps: `flow-helpers.ts` (a helper per step `dsl`, trigger track builders read from the step's `trackField`, and dependencies' helpers) and `step-types.ts`.
  - Views: a feature's `views` export is checked to be an object and put in its registration (`pack-entry.ts`, `PackFeature.views`), and `fe.ts` types `useView` from it by a type-only import, so no backend code reaches the frontend bundle (`tests/build/generate-entries/compiles.spec.ts`, "generated views compile").
  - Other: `types.ts` and `references.ts`. No generated module registers anything when imported (`tests/build/generate-entries.spec.ts`).
  - A dependency's snapshot reaches codegen only in this CLI's `PACK_SNAPSHOT_FORMAT` (`manifest.ts`): the CLI's resolution passes over builds in another format (`_snapshotFormatMismatch`), and the test harness refuses one in its cache. Bump the format, once per release, with any change to what a dependent reads from a snapshot that another CLI would misread; unreleased changes share the next number; the codegen spec's "the snapshot format" case lists what it covers.
  - Per dependency, it also writes `deps/<id>.d.ts` and `deps/<id>.flow-helpers.{js,d.ts}` from the dependency's snapshot. `_depTypesVersion` reads the version header that the CLI's stale-deps warning uses.
  - `mergeRegistries` merges own, dependency and SDK entities/relKinds. It throws when the pack or a dependency uses an SDK name, and when two sources share a key or a value. `EntityName` lists the entity values; `PackStepNodes`, which `pack-types.ts` exports, is the pack's and its dependencies' step node types, so a dependent's `Node` rows are their union. `emitEARS` writes the `EARS` namespace.
- **`module-exports.ts`**: `createModuleExports(packRoot, files)` builds one TypeScript program over every file a manifest `"path#export"` names: services, repositories, `extensions.services`, `extensions.steps`' and `extensions.blocks`' facets, `content.writers`, entity shape type references under features or `data.entities`. Settings schemas and defaults are inline data, not executable exports. The program uses the pack's `tsconfig.json` and `types: []`, with no `customConditions`: a pack compiles against the `@apackdev` packages' published `dist`. `exportOf(file, name)` follows alias chains and returns `{ value?: 'object' | 'function' | 'class', type }`.
  - Codegen uses it to reject a missing export, a type-only export, or a service exported as a function or class (export the object or an instance).
  - It checks entity shapes (the export must be a type). The common JSON Schema compiler checks inline feature and pack-group defaults; generated value types derive from those declarations.
  - The program is created lazily, on the first `exportOf`. It needs the optional `typescript` peer and throws with an install hint when it is missing.
- **Pack config** (`manifest-bridge.ts`): `buildPackConfigFromManifest` resolves `content.sources` (`resolveContentSources`; a format entry keeps its `applier`). Its `loadDefinitions(importModule)` loads the definitions compiling validates against (`PackBuildDefinitions`), writing no registry:
  - Dependency step modules (`build/steps.build.mjs`) first, then the pack's own, from the `src/__generated__/steps-build.ts` codegen writes from its `steps` entries; its `artifacts` and `blocks` come straight out of the manifest, which declares each by type. A type's facets merge.
  - A pack step type that a dependency also defines throws.
- **Content compiler** (`content-compiler.ts`): `compilePack` first clears earlier output (`_clearCompiledContent`), then compiles each `content.sources` entry with the definitions it's given (`options.definitions`: the CLI passes its private registry's, the harness the test file's), else its pack config's `loadDefinitions(importModule)`, else none.
  - Specialty keys use `SPECIALTY_COMPILERS` (`compilers/standard.ts`). `documents` and `commands` are one compiler (`compilers/documents.ts`): a markdown tree into the SDK's Collections and Documents, with sections parsed by `content/document-sections.ts`, the syntax the Library's import and export also use; `commands` defaults `documentType` to a command list. A specialty compiler may declare the `identity` its key is matched on and a `media` directory in its source, copied to `media/<key>/`. Their appliers are SDK factories (`createDocumentsApplier`, `createCommandsApplier`, `content/document-appliers.ts`), which codegen emits as it does `createFlowApplier()`.
  - A format entry uses `compileBuiltinFormat` (`markdown-tree` or `json`, in `content/items.ts`) or its compiler module's export, loaded with `options.importModule`. Step definitions and flow modules use that same loader. The CLI executes TypeScript from its owned input tree with tsx; standalone SDK callers default to native import().
  - `{ applier }` entries are skipped because the pack's applier reads its own sources. A format entry with a `applier` is compiled and indexed as written even when its format names no entity.
  - Compile errors (`collectErrors`, `checkRecordEntities`) are collected and thrown together, before the cross-content `validate` step (flows against compiled action and prompt labels and the definitions' steps, `CompilationContext.steps`).
  - `CompilePackOptions.recordOutput` reports expected bytes at absolute output paths for each compiled JSON/index and regular media file. The CLI retains them in its existing output check until sealing; standalone compilation may omit the callback. Native link/special-file copying and installed regular-file validation keep their existing policy.
  - Output: `<key>.content.json` per key, `media/<key>/` per key, and `content.json` (`ContentIndex`: `packId`, and per key `written`, `identity`, `count`, preview `items`).
  - `content/resolve.ts` resolves format refs. A dependency's compiler is `<buildDir>/content-compilers.mjs#<name>`.
  - `content/markdown-tree.ts` walks markdown (YAML frontmatter, CRLF and BOM tolerated; only the `media` directory it's given is skipped). Records get a default `contentHash` (`withContentHashes`).
- **Action/prompt compilation** (`compile-utils.ts`): `compileSourceDir` scans for `.ts` files with `export const meta` and bundles each with esbuild (`bundleFile`, platform `neutral`).
  - Bare package imports are an error; `@apackdev/sdk/actions` is the only one allowed, and it is inlined.
  - Node globals (`require`, `process`, `Buffer`, …) in the bundle are warnings, found by walking the AST.
  - It extracts `meta` and the `action`/`template` function body, prepends inlined helpers, strips a `services` parameter from helpers that are only called directly, and hashes the result.
- **Flow DSL** (`compilers/`):
  - Loading: `loadFlowsFromDir` imports each `.ts` default export, skipping `_*.ts` and `*.example.ts`; duplicate names or more than one `root` throw.
  - Checking: `flow-dsl-validator.ts` (`validateFlowDSL`).
  - Compiling: `flow-compiler.ts` (`compileFlowDSL` turns DSL into entity and relation rows), `flow-to-dsl.ts` (`exportFlowsToDSL`, the reverse), and `hashFlows` (`contentHash` of `tracks` + `root`). Each takes the step definitions it works with (`steps`, and `validateFlowDSL`'s `steps`), else looks them up in the registered packs (`step-lookup.ts`); tooling passes them.
  - Track builders: `flow-helpers.ts` exports `entry`/`on`, which generated flow helpers re-export.

## Content engine (`src/content/`, `@apackdev/sdk/content`)

The user-facing rules (change tracking, import modes, content writers) are in `docs/public-facing/content.md`, whose "four
stages" section is the vocabulary: **a content item is a noun — the content, its identity, its shape and its configuration —
and the verb is `import`.** So `contentKey`, `content.formats`, `ContentItem` and `ContentIndex` name content, while
`importCompiledContent`, `ImportMode`, `ApplyResult` and a `ContentApplier`'s `apply()` name the act, what it needs and what it
produces. Nothing checks this: a spec scanned signatures for it until the rename finished, and was deleted
with it — `ImportResult` is an alias of `ApplyResult`, so which one a signature names is a label for the
reader rather than a fact a check can read.

Three functions import, in a caller relationship, and each name says its scope: `importCompiledContent({ compiledDir })`
here runs the registered appliers over one already-compiled directory; `@apackdev/host`'s `applyPacks(packs)`
orchestrates that across packs at boot; and `@apackdev/testing`'s `importContent({ keys, mode })` compiles the pack's
entries first, which is why it is the one pack authors call. The code:

- **Driver** (`utils/apply.ts`): a pack's appliers arrive in its registration (`PackRegistration.appliers`), which the host's registry keeps per pack, so they come and go with the pack. `importCompiledContent({ compiledDir, include, mode, applied, verbose })` reads the pack id from the directory's `content.json` (`contentPackId`, which throws when it names none) and runs only that registered pack's appliers (`boundHost().packs.appliers(packId)`); a key with an empty include set is skipped. `registeredContentKeys(packId)` lists their keys. `ImportMode` is `keep-existing` | `replace-on-collision` | `wipe-and-replace`.
  - **`applied` is what makes a run an apply rather than an import** (`ApplyRecord`, built with `applyRecord(before)`): `before`, what the last apply wrote per item (`AppliedItem`: the entity type, the content hash, a hash per part, and any outstanding `offer`/`dismissed`), and four containers the run fills — `defined` (every key the content declares, whatever the run then did about it), `written`, `removed` and `offers` (`ContentOffer`: `update` for a newer version waiting, `removed` for an item the content dropped, each with the parts that differ). The caller allocates it and reads it back, as the app's `applyPacks` does from each pack's `AppliedContent` row. A run given none reads nothing of what it wrote before, detects no edit and removes nothing: that is an **import**, the user asking for the pack's content back, and the modes are the whole of its policy.
- **The merge** (`merge.ts`) is the one place a verdict is reached, over (`applied`, `incoming`, `live`): `create`, `fast-forward`, `unchanged`, `user-owned`, `conflict`, `absent-by-deletion`, `kept`, `foreign-container`, and `remove`/`removed-but-edited` for an item the content has dropped (`resolveRemoval`). Both writers below are adapters that know only how to read and write their entity types; `tests/content/merge.spec.ts` is the table and is where a new outcome's row goes. Two more inputs ride beside it, and neither changes what is written:
  - **`onUserEdit`** (the entry's, from the manifest) and the item's `dismissed` hash decide whether a conflict or a kept removal is an **offer** — a decision put to the user — which the merge answers as `Merge.offer` rather than as a resolution of its own: the database outcome is the same either way, and only `theirs` versus `offer` decides whether anyone is told.
  - **`force`** is the user asking for the pack's version of one item, so it overrides the branches that protect them (their edit, an entity that was never ours, `keep-existing`, an entity they trashed) and not the two that protect somebody else (another item's container, and nothing being there to overwrite — which is a `create` like any other). `importCompiledContent` refuses it beside a record holding anything the last apply wrote, so it is out of an apply's reach by construction rather than by being remembered.

  Two of its rules are worth knowing before changing either writer:
  - **An entity we wrote with no recorded parts is adopted**, written once and re-stamped. Every entity written before anything recorded which part of one we wrote is in that state, so the alternative is freezing all of them for good; this is the rule that replaced a migration doing the same thing for one release's entities. An entity carrying no hash of ours at all is the user's and is never reached by it.
  - **An item's parts are read lazily**, because reading them means walking the entity: every branch above the drift check settles without asking.
- **`createFormatApplier(options)`** (`format-applier.ts`) is the generic item writer, used for `actions`/`prompts` (identity `label`) and every format entry.
  - Entities carry `contentHash` and `contentKey`. `contentKey` is `<packId>:<key>/…`, built by `childContentKey` per tree level, with `packId` read from `content.json` (`contentPackId`, which throws if it is missing). What the apply wrote is **not** on the entity: it is the pack's `AppliedContent` entry, a hash per field (`fieldParts`), which `driftedFieldParts` reads back.
  - `find` tries `contentKey` first, then the `find` hook or `identity` (with `parent` matched through `relKind`). An identity match that carries a `contentKey` is ignored, unless the entity's hooks make it a `container`, which is then reused as a parent.
  - **Every key the content declares is declared, whatever the walk did about it** (`declare`). The walk stops at an item it is leaving alone — the mode says to keep what is there, the user deleted it, or an error was thrown — and a key the walk never reached would otherwise read as content the pack had dropped, and the subtree the walk was being careful of would be removed.
  - Creation is transactional by hand. `createTracked` removes the entity if media copy or stamping throws, and takes its entry back out. `updateTracked` restores the previous `contentHash` and re-takes the entry over the fields that entry named, from what the entity holds now.
  - Per-item errors land in `counts.errors` instead of throwing.
  - `wipe-and-replace` removes all entities of the types in `options.entities` (the format's `entity`; codegen passes it), whoever created them, deepest first.
  - With `media`, `media/<file>` links are copied to the entity's media dir and rewritten to `media://<id>/<file>`.
  - **Removals** (`removals`) run after the walk, over the keys in `before` the content no longer declares: removed while still ours, kept and flagged once the user has edited one. Three clauses keep it right, and none is a threshold — a key whose compiled file did not load contributes none (the writer returns before reaching it), removal follows the parent chain so that keeping a child keeps the entities above it, and a `container` holding entities this entry did not write is never removed. An entry that is *kept* keeps its record entry too, so the next apply asks again; only a finished removal drops one.
  - **Removal is per entry key, and one thing follows that is worth knowing before renaming a `content.sources` key.** Each writer diffs only the keys under its own prefix, because removing an entity is type-specific (a hook, or the flow repository) and because a key whose file it could not read must contribute nothing — which a pack-wide pass could not tell from a key the pack dropped. So content whose **whole entry** the pack stops declaring has no writer left to remove it, and a renamed entry key orphans what the old one wrote. Rename one and the entities it wrote stay, with the new key's beside them.
- **`createFlowApplier()`** (`flow-applier.ts`) validates each DSL entry and reaches the same merge, with a flow's parts in place of an entity's fields: `fields` for its own values, `node:<id>` per node, and `edges` for the whole wiring with each edge's `info`.
  - **Both sides of that walk read the entities** (`graphState`), a moment apart — the apply that wrote the flow and the apply that reads it back — so they agree by construction. A stored list of the fields to hash was the other option and hid exactly the edit worth catching: a field the user added to a node was not in the list. `edges` is filtered to `GRAPH_REL_KINDS`, the two kinds `flow-compiler.ts` emits, so a relation a running app links from a node is not read as the user rewiring the flow.
  - It refuses an entry whose compiled ids collide with another pack's or a user's flow (`collidingOwner`).
  - A flow's whole-item write is a re-import through `flowRepository.importFromDSL`, which reconciles the flow in place: the file owns its fields, nodes and the relations leaving them, and what points into it — runs, subflows, the root role — survives. Only a flow whose stored id isn't its compiled one is deleted first. It then stamps `contentKey` and records the parts.
  - Subflow names resolve to this pack's written flows by content key, and to other flows by label.
  - `wipe-and-replace` deletes every flow.
- **Content writers** (`writers.ts`): `ContentWriter` (`find`/`create`/`update`/`remove`) are keyed by entity type. ContentAppliers read them with the `@internal` `_contentWriterRegistry.get` (the registered packs'); the host’s registry refuses writers for a type another pack owns.
- **`previewPackContent(dir)`** (`preview.ts`) reads `content.json` for the import dialog and lists only written keys.

Pack service consumption is declared as qualified refs in `consumes.services`.
`framework/service-consumption.ts` owns the host baseline/name inventory, direct provided-service
projection and selection validation used by codegen. Provider declarations are read without loading
source targets. The host checks the common catalog before importing a runtime and again at
registration; CLI validation checks locally available provider declarations without codegen. Generated
`Services` and backend `bindServices` use that selection. `packs/service-binding.ts` in the host owns
caller retirement, provider generations and scoped settings subscriptions. ActionService and steps use generated access. Flow execution captures `servicesForAction` directly;
a retained factory cannot follow a later rebind. Native host administration uses its existing capture
port, while SDK-only host tests inspect their private runtime directly.

## Registered packs

What packs registered isn't SDK state: the app that registers them owns it, an instance per app (`createPackRegistry()` and `createFePackRegistry()` in `@apackdev/host`; `tests/packs/registry-state.spec.ts` there fails if one of the lookup modules below keeps module-level state). The SDK defines the read-only views (`runtime/packs-view.ts`, `runtime/fe-host.ts`), the app binds them (`HostRuntime.packs`, `FeHostRuntime.packs`), and the SDK's lookups read the bound one on every call, so packs call the same functions whatever registered them. There are no write functions: everything a pack contributes arrives in its `PackRegistration` or `PackFERegistration`. A process still loads exactly one SDK instance (and one `@apackdev/ears`: `SHARED_INSTANCE_PACKAGES` in `@apackdev/host/build/shared-deps`), since the binding lives in it: the API's pack loader and the test harness map every `@apackdev/sdk` subpath to one copy through `withModuleBridge` in `@apackdev/host/packs`.

- Backend only: `stepRegistry` reads active providers for execution and retirement. `getStepDeclaration`/`getStepDeclarations` and `createNodeDefaults` read catalog metadata without activation; `getStepBinding` requires a current eligible provider for new work. Frontend readers use the `/fe` declaration and binding APIs.
- Backend and frontend (`_boundPackExtensions()`: the frontend host's when bound, else the backend's): `artifactRegistry` and `blockRegistry` (`get`, `getComponent`, `has`, `all`), and designations (`designations/index.ts`: `getDesignated`, which throws for an unknown role, and `hasDesignation`).
- Backend (`boundHost().packs`): `_contentWriterRegistry.get`, `importCompiledContent`/`registeredContentKeys` (a pack's appliers), `getSettingsCatalog` (`framework/pack-settings.ts`), `onPackCatalogChanged` (`framework/pack-catalog.ts`), `getCommands` (`commands/index.ts`, which derives the list from the stored documents — and reads the shell instead when a frontend host is bound) and pack services in `services`.
- Frontend (`boundFeHost().packs`): `textEditorExtensionsRegistry.getAll` (`fe/text-editor-extensions.ts`). The renderer reads its surfaces and app extensions from its registry directly. DSL declarations and compiled type text use `fe/dsl-reader.ts` over the common catalog; they have no frontend registration or runtime store.
- Repositories (`src/services/`): `repository` reads the bound app's `packs.repository(name)` — the registry's, beside the pack's other contributions, not the engine's — and throws for a name no registered pack declares; `services.repository` is the same object. A pack's arrive in its registration; `testPacks.repositories` holds a test's.
- The bound app (`runtime/host-runtime.ts`): `bindHost(runtime)` once per process. The `services` proxy (`services/index.ts`) resolves on every property read: the SDK's and the app's services plus the bound `packs.getRegisteredServices()`.
- Contexts without an app use the SDK's stand-in (`testing/packs.ts`), never host's registry.

## Testing entry (`src/testing/`, `@apackdev/sdk/testing`)

`nativeFrontendDeclarationFixture(registration)` composes declarative data from authored frontend test
stand-ins before host admission. It never calls providers, views or machines and refuses missing node
data. Use independently authored declarations when testing declaration/binding mismatches or getter
capture; deriving expectations from the binding would hide the behavior under test.

This is the in-memory runtime that `@apackdev/testing/harness` drives (see `packages/apack-testing/CLAUDE.md`). It lives in the SDK so tests bind the pack's SDK instance, whose lookups and engine the pack's code reads.

- `startTestRuntime({ entityTypes, packs?, appVersion?, onboarding? })` creates and installs an EARS engine (`createEarsEngine`) checking the SDK's entity types plus the given ones; calling it again adds types. Its first call binds the in-memory app (`bindTestRuntime`, `host.ts`): `testRootEvents` as the bus (its log events printed to the console, its `SYSTEM_ERROR` events recorded), `packs`: `testPacks` over the given registry (`testPacksView`; none by default; the harness passes the registry it creates, with its mocks), `appVersion` (`0.0.0-test` by default), `appData` (reset) and `onboarding` (in memory by default, the host's `AppState` in the harness), a run history in memory (`_memoryRecords`, `testRunHistory()`), `secrets`, and an `inference` that fails until mocked. `packs`, `appVersion` and `onboarding` count only on the first call; a later call giving different ones throws. A call after the host was unbound (`unbindHost`) binds the test app again, as first started, with a fresh engine.
- `testPacks` (`packs.ts`): the stand-in for the registered packs, plain maps tests fill directly (`designations`, `steps`, `artifacts`, `blocks`, `services`, `content.writers`, `appliers`; `clear()`), found before the registry `startTestRuntime` was given. SDK specs and pack tests that need a registry filled without registering a pack use it (default-setup's `layout-utils.test.ts`).
- `ContentRuntime` is the producer contract from `@apackdev/sdk/framework`. `registerContentRuntime(runtime)` in `/testing` registers a pack's entity types, and its repositories and content writers (in `testPacks`); the CLI's content runtime check uses it, while the harness uses the host registry's separate content-facet operation, which checks declaration identity and provided data operations without claiming backend systems/services. The generated `content-runtime.ts` exports it; `apack pack build` bundles it to `dist/build/content-runtime.mjs`.
- `startFeTestRuntime(options?)` / `stopFeTestRuntime()` (`fe-runtime.ts`): the frontend host for a test file, the counterpart of `startTestRuntime` for code that reads `boundFeHost()` (a surface, a tiptap or DSL registry). It binds `bindFeHost` with nothing registered and every member a test doesn't pass standing in as unusable (the shell's stand-in fails naming `startShell` from `@apackdev/testing/harness`, since the real shell is the host's), so an extension that registers itself on import shows up as one this returned; the start call returns the stop function (`const stop = startFeTestRuntime(); afterAll(stop);`). Packs bind and unbind per file, which the renderer never does, so this lifecycle lives here rather than in the host's `unbindFeHost`. `fakeSettings(document?)` (`fake-settings.ts`) is the usable `settings` to pass it: a port over an in-memory document, where a change a component makes is what the next read returns and `updates` records how each was addressed.
- `resetTestData` (installs a fresh engine, carrying over the registered repositories, so nothing is shared with the test before), `entityIds`, `dropAttribute`, `takeSystemErrors` (the recorded `SYSTEM_ERROR` events), `addTestSecret`, and `fakeInference` (`fake-inference.ts`). `testRootEvents` has no bus actor: a test of `broadcastToSurface` listens with `onSurfaceSend`, and `@apackdev/testing`'s `startApp` delivers them.

`nativePackDeclarationFixture(registration)` extracts declaration data from an authored native test
fixture before its runtime stand-ins register, including explicit step node data and executable slot targets.
A step fixture supplies its node declaration; the helper does not invent missing defaults. Native APIs use keyed `services` and `repositories` targets at their
feature owner, or at pack scope when no feature owns them. These are composition references, never
discovery-time imports. Native and authored registration share API-name/feature-service ownership
checks. The test helper records names before binding; direct registry fixtures must supply their own
API declarations and update them when a replacement changes the contributed names. It is a test
composition helper, never a production
discovery path. Host composition admits independent declarations before constructing runtime bindings.

## A pack on disk (`src/testing/pack-fixture.ts`, `@apackdev/sdk/testing/pack-fixture`)

`packFixture(options?)` writes a complete pack directory and returns its path — for the specs whose subject is
**pack tooling**: the import rules, the pack rules, the bundlers, the installer. It is a helper: what it saves
is the preamble eleven specs shared, `mkdtemp` plus a manifest plus a `package.json` plus a symlinked
`node_modules`, four of them written identically.

**It is a source-only export, and that is why it can live here.** The entry names
`./src/testing/pack-fixture.ts` under `@apackdev/source` and nothing else, so `publishedManifest` drops it from
the published manifest (`@apackdev/host/build/published-manifest`), no `etc/*.api.md` reports it so `api:check`
does not review it, and **nothing outside this repo can resolve it** — a consumer of the tarball has no such
entry, and a pack's config may not declare that condition, which `check:specifiers` enforces.
`./runtime/internals` is the same shape and the precedent.

What the shape does *not* do, checked: the compiled file still **ships** (`files` is `["dist", …]`, and
`publish/dist/testing/pack-fixture.{js,d.ts}` are staged, as `runtime/internals`' are). Dropping an entry hides
a file from resolution; it does not keep it out of the tarball. A doc-comment edit here costs nothing, because
`api:check` takes every report again and compares — there is no hash of the declarations to go stale, which is
what used to ask for an `api:update` that then rewrote no report. It is deliberately *not*
in `src/testing/index.ts`: that entry is published, and this is repo-internal test tooling that no pack author
materialises a pack to use.

**Not a workspace of its own**, which is the obvious-looking move and was tried: a private `@app/pack-fixtures`
costs seven files and six registration points for one function, and the premise that bought it — that living in
the SDK means living in the reviewed published surface — is false, because of the paragraph above. A workspace
per helper is also the precedent that gets you twelve of them. `packages/repo-checks/CLAUDE.md` has the
guardrail that keeps this the only way to write one.

**The condition that would make it public API** is a published pack-reading API. Every consumer of a pack
directory is private today — the pack rules and the source parser are `@apackdev/cli`'s, which publishes no
declarations, and the layout, subpath-imports and own-module-specifier readers are the private `@apackdev/host`'s —
so a fixture for them has no user outside this repo. A pack author tests their own pack, which is already a
directory (`PACK_DIR`), or its code through `setupPackTests`, which takes a registration rather than a tree.
Publish any of that surface and this goes public in the same change; until then, publishing it would fix the
default manifest's shape, the `manifest`/`rawManifest` split and the stub files as contract, and that default is
chosen to make *this repo's* pack rules fire.

**What "complete" means, and what it is not for.** It writes both subpath maps, a manifest declaring a
feature's two halves, and the files those paths name, so a case that adds one offending file gets a tree where
every rule can speak and need not work out which parts of a pack each rule reads.

**It is not the thing that catches a fixture too thin for a rule to fire.** That is
`import-specifiers.integration.spec.ts`, which asserts per rule that it found something in a tree written to
offend it — so a rule that cannot fire fails naming itself, whoever wrote the tree. That assertion predates
this fixture by five days (`1ee9b5a4c`), and reading the fixture as the protection is how a repo-wide rule
mandating it came to be built and then deleted (`487a8c115`). If a thin fixture is ever the worry again, the
answer is an assertion in the spec that would be wrong. Which module is a contract is
what `apack.json` says, not what a file looks like, so a fixture without a manifest is one several pack rules
cannot speak about at all.

**What it is not.** Not the in-memory harness: `setupPackTests` (`@apackdev/testing/harness`) takes a
*registration object* and runs a pack's code; this materialises a *directory*. Different axes, and conflating
them is the mistake [`one-pack-fixture.md`](../../docs/archive/plans/one-pack-fixture.md) was written to avoid.
Not a build and not an install either — `buildPack(dir)` builds one and the installer places one, both already
take a directory, so this composes with them rather than growing a `built` option. The *installed* shape (a
manifest beside `integrity.json`, a snapshot and `dist/runtime`) is a different build whose layout
`@apackdev/host` owns (`PACK_LAYOUT`), and host's tests build it in host.

**Converting a spec that writes its own pack.** Three things come up every time, in this order:

1. **Drop the caller's `mkdirSync(dir, 'src')`.** The fixture owns the tree and `files` creates any depth, so a
   non-recursive mkdir afterwards throws `EEXIST`. It bit three of the five conversions.
2. **A spread becomes the merge.** `JSON.stringify({ id, name, version, ...manifest })` is exactly
   `manifest: { id, name, ...manifest }` — two specs were already doing by hand what the option does.
3. **Check it still fails.** Break what the spec asserts and watch the converted version fail; a fixture that
   grows files can quietly stop a case from firing. `host-import-guard` was checked that way: with its
   offending import removed, two of its five cases fail.

**What not to convert.** The test is whether a spec needs a pack's *source tree* or a built pack — this
makes only the first — and these are the shapes that answer "built pack":

- a `'{}'` **discovery marker** — three in `import-specifiers.integration`, where a directory holding *any*
  `apack.json` is the subject and eight files of content would slow the walk it tests for nothing;
- a **patch** of a pack something else scaffolded (`apack pack init`, then a manifest edited) — a read-modify-write,
  not a fixture;
- a **manifest that is the subject** written with no tree around it (`pack-generate`, `pack-cli`'s
  `writeManifest`), where a pack directory would change what the command under test sees;
- the **installed or discovered shape** — a data dir's `packs/<id>/apack.json`, or a built built-in with a
  `dist/runtime/index.cjs` and no source. Measured 2026-10-02: 23 such sites, 20 in `@apackdev/host` and 3 in
  `packages/api`, whose subjects are discovery, staging, an update check or the loader. None wants a source
  tree, which is why the guardrail's population is the packages that *import* the fixture rather than every
  package that could.

## Scripts

Run these from `packages/apack-sdk`, or from the repo root with `-w @apackdev/sdk`.

- `npm test`: vitest over `tests/**/*.spec.ts` (files in parallel: each test creates or installs its own engine) (`build/`, `designations/`, `env/`, `events/`, `framework/`, `logger/`, `repositories/` (the SDK entities' repositories), `runtime/`, `content/`, `services/`, `testing/`, `utils/`), with `@apackdev/source` set in `vitest.config.ts`. The root `test:unit` runs it, as CI does.
- `npm run typecheck`: `tsc --noEmit`. `npm run build` is the same `tsconfig.json`, which sets `noEmit`, so it emits nothing.
- `npm run build:package`: the repo's `scripts/build-package.ts`, shared with `@apackdev/ears`, which builds the same way. It compiles `dist/` with `tsconfig.package.json`, copies hand-written `.d.ts` files, and checks that every bare import in `dist` is declared and every export target was built. The root `packages:build` runs it, and the root `packages:check` runs publint and `attw` over the staged `publish/` tree — where `./runtime/internals` is absent, being source-only, so nothing has to exclude it.
- `npm run api:check` / `api:update`: `api:build` emits declarations to `.temp/api-types`, then `scripts/api-reports.ts` compares or rewrites `etc/<entry>.api.md`, one per export with `types`.
- `npm run schema:update` / `schema:check`: regenerate or verify `apack.schema.json`.

## Gotchas

- `src/build/` and `src/content/` must not know any pack's entity types (library, notes, FAQs). `tests/build/no-pack-content-specifics.spec.ts` rejects those names; an exception needs a reason in its `ALLOWED` table.
- Changing codegen output affects every pack. Tests covering it: `tests/build/generate-entries.spec.ts`, plus `apack-cli/tests/build/` (`dep-types-version`, `trigger-track-helpers`) and `default-setup/tests/unit/content-parity/`. Regenerate default-setup with `npm run build:default-setup`.
- `esbuild` and `typescript` are optional peers. `compile-utils.ts` imports both at module load, and `module-exports.ts` loads `typescript` lazily. Pack runtime code must not import `@apackdev/sdk/build`.
- Written entities are found by `contentKey`, which starts with the pack id from `content.json`. Compiled content without `packId` fail to write until the pack is rebuilt.
- `compilePack` wipes its output directory's content files and `media/` before compiling, even if compiling then fails.
- `@apackdev/sdk/ears`'s operations (`untypedQuery`, `untypedCreate`, `untypedWrite`, the `defineEars` facades over `boundEars`, and the SDK code over them: repositories, appliers) throw when no engine is bound; tooling passes or binds its own (`exportFlowsToDSL(dir, { engine })`, `tests/build/compile-engine.spec.ts`).
- `services`, the sends, `onLog`, `reportError`, `getAppVersion()` and the registries of what packs registered throw naming `bindHost` (the frontend registries `bindFeHost`) when no app is bound, so SDK code calling them outside the app needs `startTestRuntime` or a host. `createLogger` doesn't: unbound, it writes to the console. The FE bundler fails a pack frontend that inlines the binding modules (`host-runtime.ts`, `fe-host.ts`) where a bound app is needed.

Help is declared by `apack.json` `extensions.help.path`. The build validates Markdown and materializes `HelpDocument[]` in the snapshot; the common declaration catalog qualifies articles by pack and exposes a `HelpCatalog`, including disabled installed packs. `openHelp()` opens the host Help feature from pack frontend code.
