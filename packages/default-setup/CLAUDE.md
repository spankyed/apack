# Default Setup

The built-in pack for apack. Ships everything the app needs out of the box: 11 features (each with a backend system and frontend surface), services, content, flow steps, artifact viewers, message blocks, tiptap extensions, and custom settings forms.

Declared as a pack via `apack.json`. Being shipped by the app is installation provenance, not a manifest privilege. Registered through `__generated__/pack-entry.ts` (backend) and `__generated__/pack-entry-fe.ts` (frontend). These are generated by `apack pack generate-entries` from `apack.json`.

## Package structure

```
src/
  __generated__/           # All generated from apack.json — do not edit
    event-contracts.json   # Static system incoming/outgoing and surface receive names
    pack-entry.ts          # BE entry — exports PackRegistration (repositories and appliers included)
    pack-entry-fe.ts       # FE entry — the PackFERegistration: surfaces, steps, tiptap + app extensions, DSL types
    ears.ts                # EARS entity/relation registry, generated from apack.json
    ref.ts                 # ref(name): the ref a name in this pack's code stands for, bound to the pack
    fe.ts                  # openSurface(name, event?), SurfaceName: the surfaces this pack's code can name
    events.ts              # SendableSurfaceEvents/PackSystemEvents + typed broadcastToSurface/sendToSurface/sendToSystem
    system-specs.ts        # Type-only: the events each system receives and sends, read by events.ts and types.ts
    types.ts               # Type barrel (per-feature types; a surface imports its system's events from be/contract.ts)
    services.ts            # Selected services, types and the lifetime-bound servicesForAction factory
    repository.ts          # repository, typed with the repositories declared in apack.json
    repositories.ts        # Those repositories by name, carried by pack-entry.ts's registration
    pack-types.ts          # Facade types apack pack build bundles into dist/types/pack-types.d.ts
    references.ts          # Per-feature executable reference bindings; editor metadata comes from the host catalog
    appliers.ts             # `appliers` for all content types, which pack-entry.ts carries; compiled dir accessors
    content-runtime.ts        # contentRuntime: entity types, relation kinds, repositories, content writers (unit tests; bundled to dist/build/content-runtime.mjs)
    step-types.ts          # Step type augmentation
    flow-helpers.ts        # Typed flow DSL helpers (entry, on, one per step with a dsl node)
  defs/                    # DSL type definitions (action.ts, prompt.ts, database.ts)
  features/                # 11 features (each has be/ and fe/ dirs)
  extensions/              # Cross-cutting concerns
    artifacts/             # Artifact viewer definitions + Vue components
    blocks/                # Message block definitions (display + input)
    steps/                 # Flow step definitions (action, llm, switch, fire, etc.)
    tiptap/                # Text editor extensions (reference node, command suggestion, viewer decoration)
    app/                   # Welcome screen app extension
    help/                  # Bundled Markdown help articles
  content/                   # Content sources: actions, prompts, flows, notes, commands
```

## Features

Each feature lives in `src/features/<name>/` with this layout:

- `be/system.ts` — XState backend system machine
- `be/contract.ts` — the feature's backend leaf: its system's `Contract` (`context`, `incoming`, `internal`, `outgoing`), which `apack.json` names at `features.<id>.system.contract`. Its own module rather than the types barrel, since `#generated/types` star-exports that and one `Contract` per feature would collide there; codegen reads it as a declared type, without resolving the machine
- `be/repository/` — EARS read/write layer: `xQueries`/`xCommands` objects declared in `apack.json` `features.<id>.repositories`, carried by the generated pack entry's registration and registered by the host with the app's engine; use them through `repository` from `#generated/repository`
- `be/services/` — Service modules, each exporting the `<key>Service` object exposed to systems and actions (see Services)
- `be/types.ts` — Shared types
- `apack.json` `features.<id>.surface` — presentation, state and component targets; codegen assembles the frontend binding
- `fe/state.ts` — XState frontend state machine
- `fe/contract.ts` — the feature's frontend leaf: its surface's published state, the events its `Contract` opens an inbox to, and the `Contract` itself. It imports no machine, no other feature and nothing from `#generated/*` but `types` and `ears`, which is what lets codegen read the contract without resolving the machine (`check:specifiers`); `apack.json` names it at `features.<id>.surface.contract`
- `fe/canvas/` — Main view components
- `fe/references.ts` — which of the feature's things are linkable from an editor, and how (if applicable)
- `fe/settings.vue` — Custom settings form; the definition is inline in `apack.json` `features.<id>.settings`

The 11 features: **threads**, **code**, **notes**, **browser**, **library**, **flows**, **actions**, **prompts**, **brain**, **database**, **logs**.

Settings persistence, validation and app preferences belong to the host (`host/settings` in
`@apackdev/host`); the renderer supplies the Settings view. This pack declares its shared assistant
name inline in `apack.json` `extensions.settings.assistant`, stored at
`packs['default-setup'].assistant`. Each feature declares its schema/defaults at
`features.<id>.settings`, stored under its fully qualified feature ref. Custom forms edit those values;
they do not supply defaults or assemble an app settings document.

Backend code uses `featureSettings.forFeature('<feature>')` or `packSettings.forGroup('<group>')`
from `#generated/settings`; frontend feature forms use `useSettings('<feature>')` from
`#generated/settings-fe`. App preferences follow the SDK `AppSettings` contract at `app`, with
host-owned defaults and validation. Settings are JSON data declared in the manifest, not compiled content.

Default surface is Threads.

Frontend components don't render untrusted text as markup: script injected into the app window reaches everything it can, the API token included. Markdown renders in a Tiptap viewer (`mode="viewer" variant="chat"`, which renders no raw HTML); `v-html` takes only the output of a function that escapes its input (`escapeHtml` from `@apackdev/sdk/utils/pure`, as `highlightSearchTerm` and `highlightMatches` do).

## Systems

Backend systems wired via `__generated__/pack-entry.ts`, each feature's with `packSystem()` from the SDK. Each system file default-exports a `SystemEntry` (the manifest names only the path, not an export name). The logs system is the bus's like any other: what the in-app viewer shows is what `onLog` delivers from the moment the bus starts it, so the boot lines before that — the boot reading, each `onInit`, the migrations, the content — reach stdout and the log file only.

Code names a system by feature id, and reaches another system with the typed `sendToSystem(name, event)` from `__generated__/events`, never its actor. Each system file defines its events with `defineSystem()`; its identity is its feature's, from `apack.json`. A feature's designation comes only from `apack.json` `features.<id>.designation`. It is a role, not a name: it need not equal the feature id, and every one default-setup declares happens to.

## What a system sends a surface: data is a view, a result is a reply, news is a broadcast

**A system sends a surface three kinds of thing, and each has one channel.** Which kind an event is decides how it
travels; getting that wrong is where every bug of this class came from — a terminal opened in every window, a flow
navigated every window, six features announced an import to windows that had not run one.

| the kind | the channel | correlation |
|---|---|---|
| **data** — what the feature stores, as a window shows it | a **view** (`useView`, `fromView`) | none: it is the window's own subscription |
| a **result** — the answer to one window's ask or write | **`reply`** | the envelope's call, which every ask already carries |
| **news** — something happened that every window should know | `broadcastToSurface` | none, and guarding one is a category error |

**Data is a view.** A feature declares its reads (`be/views.ts`, `apack.json` `features.<id>.views`); a window
subscribes with its arguments and is sent each changed result, and nothing that writes says who is looking. No
system broadcasts rows, and no surface keeps a copy it patches from events. The worked examples here: prompts and
actions (`list`, `byId`), flows (`list`, `graph`), notes (`tree`, `note`, `recent`, `search`, `trash`), library
(`index`, `folder`, `document`) and threads (`list`, `archived`, `recent`, `detail`, `chat`, `message`, `tab`).

- **Read what the window shows, and no more.** A view re-runs when anything it read changes. The threads chat page
  lists its messages by id and reads no message's content, so a streamed reply re-runs that message's view alone;
  the notes tree reads no note's text, so typing in a note re-runs nothing but that note's view.
- **A view reads the engine and nothing else.** What is on disk (a symlinked library folder), in the run history (a
  brain run's tree) or the result of a walk over the whole store (the database schema) is not a view: it is fetched,
  and its answer is a result. The library says so in its view (`{ onDisk: true }`), and announces a write it makes on
  disk as news (`FOLDER_CHANGED`) for the windows showing it to fetch again.
- **Arguments come from the window.** A view that read the settings would not re-run when they change, so the
  threads' recent list takes its limit and order as arguments from the settings the surface holds.
- **An editor holds its views behind its own writes** (`ViewWrites`, `@apackdev/sdk/fe`): it applies an edit at
  once, so a result from before the write landed would undo it. Once the last write is answered it reads the views
  again. Every write such a surface records must be answered, a refusal included. The commit panel does the same
  over a list it fetches: a staged file moves on the click to where git will list it (`apack-git/staging`),
  and no status is shown until the write is answered.
- **A surface drawn in several areas follows its views from its machine** (`fromView`, `#generated/fe`), since no one
  component is mounted for as long as it runs — threads is the example.

**A result is a reply.** A handler is handed `reply` (`spec.actions({ … })`), absent when the message named no sender,
and answering is the handler's whole job: the window that asked hears it, and no other. Where a result must still
reach someone when nobody asked — an action opening a thread — a feature's `answer(reply, event)` replies or
broadcasts, never both (`threads/be/answer.ts`), and takes only that feature's outcomes (its `Outcome` type), so a data
result cannot reach the fallback. Code's `answer` (`code/be/answer.ts`) has no fallback: a code result is data its asker
shows.

- **`reply` answers the message being delivered, and only that one.** An event a machine makes while handling a
  message — a system telling its children something of its own — is not that message, and its handler is handed no
  `reply`; the same object forwarded to a child still is.
- **A surface asks where a delivery names it.** A send from a machine's own entry, from a timer or after an `await`
  carries no sender, so its answer goes nowhere. A surface asks for what it starts from on `SURFACE_STARTED`, which
  the shell hands it in a delivery naming it, and asks again from the handler of whatever news says it should.
- **A pack asks about the call and never reads it** (`@apackdev/sdk/events`): `answersCall(event, outstanding)` where it
  holds one outstanding ask, `recordCall`/`settleCall` where it holds several, and `newCall()` to mint one before a
  send an `enqueueActions` body defers. `_callOf` is host-only: a raw call invites `===` against a stored one, which
  answers *true* when both are absent. **No event type declares a correlation field, and none should.**
- **A spec that drives a machine directly builds the answer with `answerTo(call, event)`** (`@apackdev/sdk/testing`);
  one driving a whole system through `startApp` passes `nextEmit`'s `answering`. The `reserved-event-keys` pack rule
  refuses the reserved key in `tests` as well as `src`.
- **A flow answers by the window's connection.** A flow run is no delivery, so an action has no sender to reply to.
  The system that starts the flow is handling a delivery, so it puts the asker's `client` in the brain event's
  payload, the flow maps it into the action's params, and the action answers that window alone with
  `services.emitter.sendToWindow(client, surface, event)` — the database's generated query, the commit panel's
  generated message. An action with no `client` fails saying nobody asked; it never broadcasts.

**News is a broadcast, and carries what happened rather than the rows it touched.** The brain's state
(`BRAIN_STARTED`, `BRAIN_PAUSED`), a file changed on disk (`explorer.FILE_CHANGED_EXTERNALLY`), the repository changed
(`commit.REPOSITORY_CHANGED`, on the watcher and on a write alike), the code surface's directory moved
(`BASE_DIRECTORY_CHANGED`), the data replaced (`DATABASE_REPLACED`), a flow's notifications to the chat (`SET_MODE`, `FLASH_CHAT_STATE`). Nobody asked for it, so
there is no request it could fail to match. A **feed** is news too: a terminal's output and a brain run's
`RUN_NODE_SPAWNED`/`RUN_NODE_UPDATED` patch what a window already holds, as streaming tokens would. What a system
holds in memory and a window shows — the logs buffer — is fetched like what is on disk. **A fetch nobody asked for is
answered to nobody**: it replies with `reply?.()`, and only a command's outcome, which someone must hear, falls back to
a broadcast through `answer`.

**Git is run by one engine, which is a package of its own: `apack-git`.** It runs every git process and keeps
the picture of one working tree, in a repository of its own that the pack depends on through `vendor/apack-git`
([the git engine](../../docs/references/git-engine.md)): its files named below are that repository's, under
`src/` and `tests/`. `apack pack build` bundles it into the pack's runtime, and its `apack-git/staging` entry,
which imports nothing of Node's, into the frontend. It has no dependencies and is handed how to run a process,
the environment git starts from and where to log (`RepositoryTies`). What the app decides stays with the app,
over the engine's reads (`code/be/services/app-git-repository.ts`): when to fetch unasked, which branch a pull
request is based on, a file as a data URL, and the words a failed push or pull is said in. The engine answers in
shapes of its own; the contract declares what crosses the bus (`be/types.ts`) and `be/git-shapes.ts` holds the
two to each other, and the system's context holds the repository as a handle (`repositoryOf`), so the published
contract names no type of the engine's.

**A file event is a hint, and whoever owns the truth says whether anything changed.** The code feature's
watchers are the worked example. The repository watcher (the engine's `watcher.ts`) reports only that a
checkout *may* have changed, and where; git is then asked, and `commit.REPOSITORY_CHANGED` goes out only when a part of the
repository differs from what the last check saw, naming the parts that do — its status, its files' diffs, its
history, stashes or worktrees (`GitRepository.refreshSnapshot`) — so a window asks again for those alone, and reads
again only the diffs it has open of the files the news names. The open-file watcher
(`open-file-watcher.ts`) compares each file with how it last looked. So an event for nothing announces nothing, and
neither watcher needs to be exact.

- **An event the platform never delivered is made up for by reading again**, when something says a change is
  likely: `CHECK_FOR_EXTERNAL_CHANGES`, sent when a window gains focus, a terminal command finishes and an agent's
  turn ends. A new source of change sends that event; it does not add a watch.
- **A check compares with the last check, not the last read.** One window's own ask can read a change first, and
  the check is what tells the others.
- **The watcher names the files it saw change, and only those are read.** A report carries the working-tree paths
  that changed (`ChangedPaths`), the repository notes them (`noteChanged`), and the next read asks git about those
  paths alone and puts its answer into the snapshot it holds (`loadNoted`): a tenth of a whole status over
  100,000 files. That is the truth only while each file's standing is its own, so everything is read when it may
  not be: the index, HEAD or a ref moved; a rename, or a file added without its content, is in play;
  `.gitignore`, `.gitattributes` or `.gitmodules` changed; more files changed than are worth naming. A reconcile
  and a write made here have no event to go by, and read everything. The engine's `noted-paths.spec.ts` holds every case to
  what a whole status says, and says which of the two was asked of git.
- **Git is not asked while nobody is looking.** Every window showing the repository asks for its status when
  told it changed, so when none asks after an announcement, none is showing it: a hint that arrives then is
  put off, and checked when a window next asks or gains focus (`statusRefresh`, `commit.ts`). An agent editing
  files with the code surface closed runs no status per file event. A window shows the repository while the
  code surface is its active one (`commit.SHOWN`, `commit.HIDDEN`): every surface's machine runs from the
  window's start, so a window showing another surface keeps what it was told changed and asks when it is
  shown, and asks nothing before.
- **One status may write git's index, at a moment chosen for it.** Every read runs with `GIT_OPTIONAL_LOCKS=0`,
  so git never keeps what it learns of the files: after a checkout or a formatter over the tree, each status
  reads every file again (about 1.75 s against 95 ms over 50,000 files, 2026-11-11, a busy machine). The check
  that follows a terminal command or an agent's turn ending lets git write it (`refreshSnapshot`'s
  `refreshIndex`), and only when a change too wide to name, or to git's own state, has been noted since the
  last time. Writing holds git's lock for as long as that status takes, in which a git run from a terminal is
  refused: never on a window's focus or ask, which may be the user on their way to that terminal, and not
  while a write made here is running or waiting, behind which the status and every read after it would wait.
- **A file as a commit has it is read through one git kept open** (the engine's `objects.ts`, `cat-file --batch`): a
  pull request's view reads two versions of every file it lists. Never the staged version, which that git
  would go on answering from the index as it first read it. It answers in the order it was asked, so it is
  watched while it owes an answer and ended when it does no work, as a git run for one read is.
- **One piece of a file's change is staged by a patch git made** (the engine's `hunks.ts`): the diff a window is sent
  carries the file's hunks, each with an id, and staging one is `git apply --cached` of the patch that applies
  it alone, `--reverse` to take it back out of what is staged. Git cut the patch and git reads it back, so line
  endings and filters are git's on both sides. Four things keep that true. The patch is bytes and never
  leaves the backend as text, since a file need not be UTF-8. It is cut with the format `git apply` reads,
  whatever the user told `git diff`. Alone, it is numbered for the index it is applied to, where the whole
  diff numbers it past the pieces above it. And its id is where it is on the side that stays put with what it
  holds, so a piece still on screen after another was staged is the piece git cuts now, and one whose file
  changed is refused. Only a plainly modified file has pieces: one that is new, deleted, renamed or binary is
  staged whole.
- **A folder git tracks nothing in is one row**, as git lists it unless the user told it to list every file
  (`status.showUntrackedFiles`): a folder of thousands of files nobody ignored is one line, and is not walked
  (30,000 files: 0.01 s and 65 bytes against 0.13 s and 916 KB, 2026-11-11). Its path ends with `/`, and the
  window lists what is in it when the row is opened (`commit.LIST_UNTRACKED`). Asked about a file inside such a
  folder git answers with the file, where a whole status has the folder, so the path-scoped read asks about the
  folder: the one held as a row, or for an untracked path it did not hold, that path's own folder, falling back
  to the whole status only when that folder too is one git tracks nothing in. Staging the row stages the
  folder, and discarding it removes what git lists there and leaves what it ignores. A row's path reaches git
  as that path from the top of the checkout, letter for letter (`rowSpec`): `app/[id]/` as a pattern is
  `app/i/` too. A folder that is a repository of its own lists nothing and is not removed, which is said.
  A folder row reads as changed whenever it is read, by a read of everything too, and a window reads again
  the diffs it has open under a folder the news names.
- **A repository cannot make git run a program before the user trusts it.** A repository's own configuration
  and hooks can name programs, and a plain status runs one: opening a folder was enough. The engine reads what
  a repository would run without running it (its `trust.ts`) and, while that names anything, refuses every
  command there with `untrusted` and the list. The panel shows the list in place of the status and offers to
  trust the repository (`commit.TRUST_REPOSITORY`), which is remembered in the code settings'
  `trustedRepositories` by where the repository's git state really lives, so its linked worktrees share it.
  The backend trusts only the repository the panel is over, whatever path a window names. A repository that
  names nothing is read as before, trusted or not. This is about the git the engine runs: a terminal and an
  agent run in the folder too, and are not gated by it.
- **A discard keeps what it removes, and the panel offers it back.** Before a changed file is checked out
  again, or an untracked file or folder deleted, the engine writes what is about to go into git's object store
  as a tree built with an index of its own (its `discards.ts`), and the answer to the discard carries its id:
  the panel offers Undo (`commit.RESTORE_DISCARDED`), which leaves alone and names what has changed or been
  made again since. The user's index, refs and stash are not touched. A file over 10 MB is removed without a
  copy, which the confirmation says before the discard (`commit.PREVIEW_DISCARD`). Nothing refers to the tree,
  so git keeps it for about two weeks, which the panel says; when the copy cannot be taken, nothing is removed.
- **A push, a pull and a checkout say how far along they are** to the window that asked (`commit.PROGRESS`):
  git is run with `--progress` and its error stream read as it arrives (the engine's `progress.ts`), and what it says of
  a failure is taken with the progress left out.
- **What a branch was made from is read where it was written down, and guessed otherwise** (`getPRBaseBranch`):
  `branch.<name>.apack-base`, which this app writes when it makes a branch; VS Code's `vscode-merge-base`; git's
  own record of the branch's first move, which names a branch only when it was made from one by name; then the
  nearest branch by commits. One that names a branch that is gone is passed over.
- **Every git command can be logged with how long it took** (the code surface's `logGitCommands` setting, the
  `git-commands` log source): off by default, since a status runs for most file events.
- **A watch that fails is said to the user.** `commit.STATUS_RECEIVED` carries `watching`, and the panel says live
  updates are off; the next check opens the watch again.
- **A tree is watched with Node's own `fs.watch`, and no native watcher library is loaded** (the engine's `directory-watch.ts`).
  macOS and Windows watch a tree natively, and Node's recursive watch is that watch. Linux has no watch over a
  tree, and Node's recursive watch there holds one per file and reads the whole tree before it returns, so a
  watch is held on each directory that is not ignored (`perDirectorySubscriber`): a directory is watched and then
  read, one that appears is watched the same way and reported again once its watches are in place, and one that
  goes has its watches closed with it. `@parcel/watcher` was measured on all three platforms and is used on none:
  heap corruption on macOS and Windows, and on Linux a close it refuses and inotify watches it leaves behind
  ([what was measured](../../docs/issues/ISSUE-dev-loop-file-watching.md#code-map)). A watcher that needs a
  native binding earns its place by surviving its directory being deleted as its watch closes, and holding no
  watch afterwards.

**Why a git command failed is read in one place, and travels as a code.** Git says why in prose, in English
because every git child is run in English, and `classifyGitError` (the engine's `errors.ts`) turns what
it printed on either stream into a `GitErrorCode`, by the lines git itself writes, each from its start: a
phrase found anywhere would be read out of a branch's name, a hook's output or another step's line. A caller that needs to know why reads `result.code`, never the
text; a failure thrown to a handler is a `GitError` carrying it, and `commit.ERROR_RECEIVED` hands it to the
panel. A new reason is a new entry in that module's list, most telling first, with a case in
the engine's `failures.spec.ts` that fails a real git that way.

- **A remote that asks for a sign-in is refused at once**, since git runs with its prompts off, so the refusal
  comes with what can be done about it (`SignInHelp`, `sign-in.ts`), read from the remote's address: for GitHub
  over HTTPS the panel offers to sign in to GitHub, and for a key or another host it says which sign-in is
  missing. A push or a pull refused that way is run again once the sign-in is set up.
- **Git signs in to GitHub with the app's own sign-in, given on each command and never written to a config**
  (`withGitHubSignIn`, `app-git-repository.ts`): a credential helper named through `GIT_CONFIG_COUNT`, answering
  from a variable only that git run sees, and asked after the user's own helpers, so a user whose git already signs
  in keeps that. Git hands a sign-in that worked to every helper to keep, so signing out has git forget the token
  too (`git credential reject`, `features/github.ts`).
- **The pull request panel calls GitHub's API with that sign-in** (`github-api.ts`, through `gitHubApiFor`): GraphQL
  for reads, in the shapes the panel takes, and REST for most writes. A refusal comes back as the reason the
  panel acts on (`GitHubApiFailure`), never as GitHub's prose to match.

**The guards that remain, and what each got wrong first.** Every correlating guard in this pack went through this,
and they failed in four different ways — which is the argument for reading the list rather than copying the one you
land on.

**A guard needs an invariant every asker holds.** `answersSelectedNode` admits a reply only for the node in
`selectedStepNode`, so every asker must select before it asks — stated over two of its four askers and broken by the
fourth, which asked for an erroring node's details and never selected it.
`tests/features/brain/fe/run-node-correlation.spec.ts` asks each asker rather than describing them, which is the thing
to copy if a guard stays.

**A guard cannot correlate on what the answer does not carry.** `answersCurrentPage` matched a flow while
`FLOW_EVENTS_RESULT` echoed no `offset`, so re-selecting a flow while a later page was in flight let that page replace
the whole list. The answer carries its offset now; `loadMoreEvents` keeps one page in flight, which the correlation
requires rather than prefers.

**A guard's invariant is not "who writes this" but "what else could satisfy it".** A slot with one setter says nothing
about whether anything other than its own answer matches it. Set the slot before the ask, clear it on the answer,
reply rather than broadcast, and read it with `answersCall`, which refuses an empty slot. A row a window shows needs
no slot at all: it is a view.

**And a clock is not a correlation.** `code/be/features/pull-request.ts` stamped a module-scoped counter on every
`pr.PR_DETAILS_RECEIVED`, compared in the renderer, which outlives the backend: an API restart or a pack reload put
it back to zero and every later answer read as older. The PR number was always the key; what the tie-break wanted was
a clock, so it is `fetchedAt`. The PR diff is keyed by what was asked (`diffsByRef[refKey(base, head)]`), and its
answer must **not** write `prBaseBranch`, half the key the view reads under; the file-diff half keeps an in-flight
check beside its key because its answer opens a tab (`tests/features/code/fe/features/pull-request/pr-correlation.spec.ts`).

## Services

Service aggregation generated in `__generated__/services.ts`. Feature services are declared in `apack.json` `features.<id>.services` and live in `src/features/<name>/be/services/`; the pack declares no pack-level `extensions.services`. Systems and actions call them through `services.<key>`, next to the host's (`logger`, `emitter`, `repository`, `onboarding`, `appData`, `runHistory`, `inference`, `secrets`, `filesystem`):

`chat`, `artifact`, `threads`, `cli`, `codex`, `library`, `action`, `prompt`, `brain`, `scheduler`, `database`

`services.settings` is the host's, not one of these (`@apackdev/sdk/services/settings.ts`).

Each service entry names one value export, `"<key>": "<path>.ts#<key>Service"`, and the module exports it as `export const <key>Service = { ... }` (or a class instance). No factories and no whole-module services. `Services` is `typeof featureServices`, so that object is the contract dependent packs build against:

- List only what callers use through `services.<key>` (actions, steps, systems, tests). Helpers used inside the pack stay plain exports and are imported directly (`hooks.ts` imports `clearAllSchedules`/`removeAllListeners`; the brain system imports `notify`)
- Don't re-export `query`/`create`/`write`/`EARS` or other SDK modules: pack code imports those itself. Actions can import nothing but `@apackdev/sdk/actions`, so they read and write entities through `services.repository`
- No third-party types in the contract: the published facade may import only `@apackdev/*` and the SDK's peers. Give the export an explicit type when inference would name one, so the third-party types stay inside the service module and raw handles surface as `unknown` or an opaque branded type

Model calls go through the host's `services.inference` (AI SDK 7, `provider:model` ids): the `llm` step calls it with the node's `model`, and the pack has no model code or `ai` dependency of its own.

## EARS (Entity types + Relations)

Entity types and relation kinds come from `__generated__/ears.ts`, generated standalone from `apack.json` by `apack pack generate-entries`. The pack-entry registers the entity types and relation kinds `apack.json` declares. `ears.ts` also names the SDK's own: the flow model (Flow, Node, Action, Prompt; contains, transitions_to, instance_of) and the document model (Document, Collection; parent_of). The SDK defines their shapes (import `ActionEntity`, `PromptEntity`, `FlowEntity`, `NodeBase` from `@apackdev/sdk`) and owns their repositories (`flowRepository`, `actionRepository`, `promptRepository`, `documentRepository`, `collectionRepository` from `@apackdev/sdk/repositories`): the flows, actions and prompts repositories here (`flowsQueries`/`flowsCommands`, `actionQueries`/`actionCommands`, `promptQueries`/`promptCommands`) expose their methods by reference (`byId: actionRepository.byId`, never a wrapper re-declaring the signature), so this pack's code reaches all its data through `repository`, and add the surfaces' views (`connectedData`, `extendedData`, paging, a flow created with its entry node). The root flow is only the flow with the root role: the flows `list` view carries it beside the flows, a write changes it on `SET_ROOT_FLOW`, and the brain sends the root flow it started with (`BRAIN_STARTED`'s `rootFlowId`), which the Flows and Brain settings compare to offer a restart. No setting records either. Exporting actions and prompts to write files isn't a view: `export-actions.ts` and `export-prompts.ts` beside the repositories read through them. Note is default-setup's, declared in `apack.json` with its shape (`NoteEntity` in `features/notes/be/types.ts`). Document and Collection are not: they are the SDK's, and `features/library/be/types.ts` re-exports their shapes rather than declaring them, this feature being their editor. Settings isn't either: the host declares and owns its persisted row beside `AppState` (`HOST_ENTITY_TYPES`). A note's links are derived from its text (`syncReferences`, `features/notes/be/repository/link-utils.ts`): `linkTargets`, every note id they name, which the value index answers "who links here?" from, and a `REFERENCES` relation per named note that exists; both are rebuilt from the text at start and after the data is replaced, so neither is ever the only record of a link.
The effective document has three owners: `app`, `packs[packId][groupId]`, and
`features[featureRef]`. The common catalog supplies definitions even for disabled installed packs;
the host writer composes defaults and explicit overrides and validates each effective value.
Reset removes an override; an explicit value equal to a default remains a choice until reset.
The pack uses owner-bound handles from `#generated/settings`; app-wide replacement and backup
coordination belong to host services. Forms receive correlated save/refusal results; the host settings system
publishes feature change notifications after accepted writes. Onboarding completion is lifecycle
state accessed through `services.onboarding.isComplete()`/`complete()`, not an assistant preference. Which tabs show and the surface last open are the host's, in `AppState`. A flow run is not an entity: the brain records it in `services.runHistory`. API keys aren't entities: Settings → Secrets manages them through the host's `secrets` procedures and `services.secrets`, and the code feature keeps its GitHub sign-in as this pack's own secret (`services.secrets.own`, `features/code/be/features/github.ts`), and CLI path overrides live in the code surface's settings (`features['default-setup/code'].cliPaths`), which the code feature's CLI resolution reads (`features/code/be/utils/resolve-cli.ts`: `resolveForService`, `testCli`).

Import `EARS` from `#generated/ears` by default. The SDK's `EARS` (`@apackdev/sdk`) is fine for `EntityId`, SDK-owned constants and shared EARS types (build facets use it), but its `EARS.Entity` type is open: annotate with it only when any entity name is intended, as the create step's `entityTypeTarget` does (see `packages/apack-sdk/TYPED-EARS.md`).

Typed facades (no module augmentation):
- `__generated__/ears.ts` — `PackShapes` (entity type → attribute interface; a numbered entity's shape gains the `shortCode` the engine writes, typed from its `apack.json` entry, so `ThreadEntity` declares none), `ShortCodeOf<E>` (a numbered entity's code type, `ShortCodeOf<'Thread'>` is `` `THR-${number}` ``), `EntityName`, and the typed `query`/`create`/`upsert`/`write`/`transact`/`newId`/`getAttr` helpers built with `defineEars`. Feature code imports its writes from here; migrations write with the unchecked `untypedCreate`/`untypedUpsert`/`untypedWrite` from `@apackdev/ears`, as does the Database console's transaction code (which exposes them to console code as `create`, `upsert` and `write`), which runs through `@apackdev/sdk/database-console` (`features/database/be/execute/`)
- `__generated__/events.ts` — `SendableSurfaceEvents` (receiving surface ID → the events it gets: its own system's, plus the inbox that surface's `Contract` declares — the flows surface takes the three action events it handles, the logs surface `LOG_ADDED` from any pack), `PackSystemEvents` (system → the events it receives), and typed `broadcastToSurface`/`sendToSurface`/`sendToSystem` built with `defineEvents`. Frontend state machines and systems send to systems with `sendToSystem` (to the brain's role with `{ role: 'brain' }`); backend code sends to surfaces with `broadcastToSurface`, which reaches every window, and frontend code with `sendToSurface`, which reaches this window's actor. Don't import these from `@apackdev/sdk/events`; a surface that takes events from anywhere but its own system declares them in its `Contract`'s `inbox` (`fe/contract.ts`). Subscriptions (`onConnected`, `onIncoming`) come from `@apackdev/sdk/events`, `onLog` from `@apackdev/sdk/logger`. A system answers whoever asked with the `reply` its handler is handed (`spec.actions({ … })`, built by `defineSystem`), which is absent when the message named no sender — there is no `reply` to import
- `__generated__/services.ts` — the `services` proxy typed as `Services` (with `services.repository` typed as `Repositories`, and `services.emitter`'s sends typed with the pack's events; actions name systems `default-setup/<feature>`)
- `__generated__/repository.ts` — `repository`, typed with every repository in `features.<id>.repositories`

Logging and actions:
- Log with `createLogger(source)` from `@apackdev/sdk/logger`. The brain and step runtimes use `createLogger('brain', { debug: true })`, whose debug messages follow the brain surface's inspect switch (`setDebugEnabled('brain', …)`). Errors go through `reportError`, with `step` context in step runtimes. Backend code has no `console.*` (`check:specifiers`)
- Action code runs through `runActionCode` (`extensions/steps/action/sandbox.ts`), for the action step and `services.action` alike: `params`, `services` (its `logger` named `action:<label>`, and its `emitter` stamping that same string as `Message.via` beside this pack's id as `Message.from`), `z` and `flowId`. The action names every feature `<packId>/<featureId>` all the same — the stamp says who sent a message, and changes nothing about what a name means

## Content

Content sources compiled to JSON by `apack pack build`, as `apack.json` `content.sources` (and, for notes, `content.formats`) describe them. Located in `src/content/`:

- `actions/`, `prompts/`, `flows/` — compiled by the SDK's own compilers (the manifest names their paths and `onUserEdit: "offer"`, the only three entries that declare it: these are the pack's, customised, so a user who has edited one still gets its fixes offered. Every other entry is `theirs`)
- `notes/` — welcome note, compiled with the `notes` format (`markdown-tree` for `Note`: frontmatter fields, `index.md` directories)
- `commands/` — the chat's slash commands (`internal/{chat,claude-code,codex}.md`, which that directory nests in an `internal` Library folder), under the SDK's `commands` key, which compiles markdown into Collections and Documents with `commands` as the default document type, so a file there need not say what it is and any document that declares `type: commands` is served too. Documents are the SDK's, so this pack declares no format or writer for them, and a pack that ships documents needs nothing of this one's: it declares the SDK's `documents` or `commands` key. The app derives the list from the stored documents itself (`commandsFromDocuments`, `@apackdev/sdk/commands`), so this pack declares nothing to serve them and plays no role for them: a command is content like any other, and this feature is where the user edits one
- `src/extensions/help/` — Markdown articles contributed through `apack.json` `extensions.help.path`, bundled into the runtime and displayed by the host Help feature
- `writers/` — the content writer for Note (`notes.ts`), registered through `content.writers` in `apack.json`. Document and Collection have writers too, but they are the SDK's: a pack declares writers only for entity types it owns, so these are named by `sdkContentWriters` (`apack-sdk/src/content/writers.ts`) and need no registration. Collection is a `container`, so another pack's documents nest in the existing folders instead of forking them, and both `find`s match a name within its parent folder

Rows go through those hooks, which call `noteCommands`/`libraryCommands`, whatever pack writes them. A pack depending on default-setup writes content with its formats by naming them (`{ "path": "src/content/notes", "format": "default-setup:notes" }`) and gets the same rows. `tests/content` compares written entities against goldens recorded from the previous pipeline; [its CLAUDE.md](tests/content/CLAUDE.md) says what belongs in a golden, what must not, and when to re-record one. Its `default-setup.json` follows the pack's own sources; the v1/v2 scenario goldens follow fixture sources, so only a change in writing moves those. An action inlines its `_helpers/` at compile time, which makes one thing surprising and worth knowing whether or not a test notices: **editing one helper re-hashes every action that imports it** — two helper edits once changed 47 of 62 rows' `contentHash`, and each new hash rewrites that row for every user who hasn't edited it. The golden no longer records those hashes, so a cosmetic edit leaves it alone; `tests/content/compiled-bodies.spec.ts` covers what the hashes used to cover by accident, that every action and prompt compiled to a body that parses.

ContentAppliers: `__generated__/appliers.ts` exports `appliers` (the SDK's format applier for actions, prompts and notes, its flow applier and its commands applier), which the pack's registration carries; importing it registers nothing: everything the pack contributes arrives in its registration, and no generated module has a side-effect import (`apack-sdk/tests/build/generate-entries.spec.ts` checks every generated file for one). The host's apply (`applyPacks`, `@apackdev/host/packs/runtime`) hashes the compiled content files under `dist/runtime/content`, records that hash as the pack's `AppliedContent.revision` beside a hash per part of every item it wrote, and skips the pack when the revision still matches. See `docs/public-facing/content.md` for entry fields, hooks and change tracking.

See `src/content/CLAUDE.md` for authoring details.

## Flow steps

Step definitions in `src/extensions/steps/`. Each step directory contains:

- `build.ts` — build facet: `export const <name>StepBuild` (or `<name>TriggerBuild` for schedule and listener) with `build: { compile, validate, getLabel, decompile }` or a trigger facet, and no FE or runtime imports
- `apack.json` `fe` — inline presentation, explicit lazy component targets and calculated layout bindings
- `types.ts` — step-specific types (the `DSL…Node` interface a flow helper is generated from)
- `form.vue` — optional editor form component
- `runtime.ts` — optional runtime handler (action, create, fire, llm, query, schedule, switch, transform, update)

A new step is one directory and one `apack.json` entry under `extensions.steps`, keyed by its type.
The entry holds inline `node: { label, defaultLabel?, defaults? }` data for both processes; no node-data export is needed. `build.ts` exports
its `StepBuildFacet` (a trigger's exports its `TriggerFacet`), and `runtime.ts` the handler the entry names.
`types` and `dsl.helpers` explicitly declare their modules; no neighboring files are inferred. There are no barrels — codegen sends each facet where it is used, and writes
`src/__generated__/steps-build.ts`, bundled to `dist/build/steps.build.mjs`, which packs depending on
default-setup use to validate their flows.

**The handler and a trigger's `register` are named, not imported**, so their modules load on the step's
first run rather than at pack load — which is also what keeps `vue` and the icon set out of
`dist/runtime/index.cjs`, since a step's `fe` facet never reaches the backend registration at all.

13 steps: **action**, **llm**, **switch**, **fire**, **transform**, **query**, **subflow**, **create**, **update**, **keep_alive** (in `keep-alive/`), **kill**, **schedule** (trigger), **listener** (trigger).

## Artifacts

Declared in `apack.json` under `extensions.artifacts`, keyed by type: each entry names a `lucide-vue-next` icon and the
viewer that opens it. 16 types, each with a viewer component in `src/extensions/artifacts/viewers/`:

text, code, review, image, slack, todo, project, json, graph, table, markdown, claude-session, codex-session, diff, plan, note

Both facets are frontend ones, so codegen puts them in the pack's frontend entry alone and the backend
registration carries each type and nothing else.

**An interactive viewer is self-contained, and does it in three moves.** Most viewers only render, but one that
the user can act on — `todo-artifact.vue`, `claude-session-artifact.vue`, `codex-session-artifact.vue` — holds
its own state and logic over generic mechanisms, so **no feature carries artifact-specific code**. That is the
whole point of an artifact: a new type is a definition and a component, never a case in somebody's system.

- **Derive the backend's answer from `props.artifact`; mirror only what the user edits.** `status` is a
  `computed` over `props.artifact.content?.status`, so the row is the single source of what was decided — a
  `ref` written once from the prop shows the user an approval the backend never recorded. What the user types or
  ticks does need local state (`todo-artifact.vue`'s `tasks`), and then it needs a `watch` on the prop to
  resync, or it goes stale the first time anything else writes that row. The test is who owns the value: the
  backend's is read, the user's in-progress edit is held.
- **Read another surface's state with `useSurfaceState`** (`#generated/fe`), which is a value and not an actor, so
  it follows that surface arriving and reloading.
- **Raise what the user did as an event, with `sendToSystem` to the feature hosting you** —
  `sendToSystem('threads', { type: 'FORWARD_BRAIN_EVENT', eventType, payload })`. The threads system forwards
  any `eventType` to the brain and a flow listens for it, so the decision travels without threads knowing what
  a todo is.

**A viewer addresses a surface by its ref, and that is the whole of its reach.** It is rendered by the host in
no `SurfaceScope`, and by no single surface — the same viewer can be shown by several — so `useSurface()` has no
answer for it. `useSurfaceState` reads by ref and `sendToSurface` sends by ref; both are sanctioned here
(`apack-sdk/src/fe/surface-state.ts` states the rule). This is why the `component-sends` pack rule refuses
`sendToSurface` from a *feature's* component and not from a viewer: a feature's component has `useSurface()` and
somewhere better to send, and a viewer does not. What a by-ref send lacks is a return address, so the surface it
reaches cannot answer it — fine for the notification these are, and the thing to solve first if one ever needs
an answer.

## Message blocks

Declared in `apack.json` under `extensions.blocks`, keyed by type: each entry names the component that draws it and,

**Display blocks** (default): prompt, note, markdown, link, tool-activity, thinking, tool-input, context-usage, session-list

The components live under `src/extensions/blocks/{display,input}/`, which is where `apack pack add block` puts

`display/`.

## Build

- `apack pack build` writes the Monaco DSL definitions the renderer imports, one `dist/defs/monaco/<name>-defs.d.ts` per `apack.json` `dsl` entry with a `monaco` target
- `npm run build:default-setup` from the repo root runs this package's `npm run build`
- `npm run build:dev` runs `apack pack build --skip-fe`
- **The pack names its own modules one way: `#` subpath imports.** `#generated/*`, `#features/*`,
  `#extensions/*`, declared in `package.json` `imports` — a Node standard that Node,
  Vite and esbuild all resolve with no configuration, and private to this package by construction. It replaced
  a `@/…` TypeScript `paths` mapping that no runtime reads, which four separate bundler configs each had to
  re-implement; `check:specifiers` refuses a `@/` specifier here now.
  **The mapping is declared twice, and has to be.** `package.json` `imports` is what the runtimes read, and
  `tsconfig.json` `paths` mirrors it because `tsc` under `moduleResolution: bundler` will not resolve a `#`
  specifier from `package.json` alone — spiked 2026-09-26, and `apack pack init`'s scaffold carries the same pair
  with the same comment. Changing `moduleResolution` invalidates that, so don't.
- **A specifier names the file that is there, extension and all** — `#generated/events.ts`, `./contract.ts`,
  `./repository/index.ts`, `../fe/panel.vue` — for a `#` import and a relative one alike. Not nothing, which
  no runtime resolves in ESM and which only worked while a build guessed the suffix; not the `.js` generated
  code used to write, which names a file a pack never emits, since a pack ships one bundle rather than a
  module per source. `check:specifiers` refuses both (`findExtensionlessOwnModules`, `findJsSpecifiers`), and
  `apack pack build` refuses them for every other pack through the same rule
  (`@apackdev/host/build/own-module-specifiers`), as `apack pack test` does for a pack's tests. This is what `allowImportingTsExtensions` in `tsconfig.json`
  is for; nothing looks for a missing suffix any more.
- `npm run typecheck` runs `vue-tsc` over the `.ts`, `.vue` and `src/defs/` files
- Vitest config at `vitest.config.ts`, which resolves the path aliases from `tsconfig.json`: the one tsconfig, whose `include` covers the tests, so `npm run typecheck` checks them with the source. Unit tests run on `@apackdev/testing/harness` (`tests/setup.ts`: `setupPackTests({ contentRuntime, registration })`), in memory, with no `@apackdev/host` or API imports (`check:specifiers` rejects them). Systems run with `startApp`, flows with `importFlows` (a root flow, `root: true`, or default-setup's own through `tests/_support/flows.ts`) and `runFlow`, as the app runs them, and services the code under test reaches outside the process (CLIs, Codex, `inference`) are mocked with `mockService` (`inference` with `mockInference`). The registered packs are the harness's registry for the test file: a test that needs another pack registers one with the harness's `registerPack`/`unregisterPack`, and frontend layout tests supply explicit declaration entries and accepted callback bindings through `startFeTestRuntime` (`features/flows/fe/canvas/layout-utils.spec.ts`)
- Installation does not run pack codegen: npm can run a workspace `prepare` hook before the CLI is linked, even with `--ignore-scripts`. For direct codegen, run `npm run packages:ensure` followed by `npm run generate:entries -w @app/default-setup` after installing dependencies. The root typecheck and `npm run build:default-setup` already build the public packages and generate entries before reading them.
- `apack pack build` gates the facade types it bundles into `dist/types/pack-types.d.ts` (`packages/apack-cli/src/build/facade-gate.ts`): the bundle must type-check on its own and import only `@apackdev/*` modules the published packages export, `@apackdev/sdk`'s peers and Node built-ins. `etc/pack-types.api.md` is the reviewed report of that facade: when a change moves it, run `npm run facade:update` and commit the report. That command needs no build — it regenerates the barrels and re-bundles the facade itself, so what the report is held to is what `src/` describes now — and the `facade:check` chain step and CI run `npm run facade:check`, the same thing without the write. A build that notices the report has fallen behind says so and carries on
- `npm run build` is `apack pack build`, the same command every pack is built by. Among its outputs is `dist/runtime/index.cjs`, the pack's backend runtime, which the API loads in development and the app publishes with the snapshot and `build/` for packs depending on default-setup. `apack pack build --watch` rebuilds that one output on every source change and asks a running app to reload it, which is the backend edit loop `npm run dev` runs
