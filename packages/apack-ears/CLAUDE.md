# @apackdev/ears

EARS, the entity-attribute-relation graph store behind apack's data: the engine, the core `EARS` types, the typed facades, the persistence port, and the LMDB store (`@apackdev/ears/lmdb`). It's the bottom layer: it imports no `@apackdev/*` package and knows no packs and no SDK entity names (those are the SDK's, in `@apackdev/sdk/types`). The SDK, host, api, packs and tests import it. The root `CLAUDE.md` ("SDK packages", "Data layer") has the one-paragraph view; this file covers how the package works.

## Package basics

- Published like `@apackdev/sdk`: each export in its `package.json` resolves `src/` under the `@apackdev/source` condition and `dist/` otherwise, and the build stages a derived manifest with no source branches under `publish/`, which is what npm publishes. Exports: `.` (the engine, types and persistence port) and `./lmdb` (the LMDB store). It's in the changesets fixed group (`.changeset/config.json`) and supports TypeScript 5.7 and later (`packages/typescript-floor`).
- `lmdb` is an optional peer dependency (a dev dependency here). Only `src/lmdb/` loads it; the app installs it (`packages/api` depends on it).
- Relative imports name the `.ts` source; `tsc` (`rewriteRelativeImportExtensions`) writes `.js`. `sideEffects: false`, and no module does anything on import.
- It's a shared-instance package (`SHARED_INSTANCE_PACKAGES` in `@apackdev/host/build/shared-deps`): packs, dependency runtimes, the app and tests load one copy, so an engine created by one is usable by all. The pack loader's bridge and the harness bridge provide every export except `./lmdb` (`APP_ONLY_EXPORTS`). Pack frontends don't share it: they inline the constants and helpers they import.

**A range is a live cursor, and an environment has 126 reader slots.** `getRange`/`getKeys` hold a read
transaction until the iterator is closed, and the language closes it for you — `for…of` (break or return
included), array destructuring and `.find()` all call `return()`. Taking the iterator by hand
(`it[Symbol.iterator]().next()`) does not, and each call that finds a row leaks a slot: measured, the 127th
throws `MDB_READERS_FULL`, after which every read fails with "No transaction to renew" and every write with
`EINVAL`, for the life of the process. `getAttrLength` did exactly that. Where the body *removes* the keys it
is walking, materialise first (`[...]`) — `removeAttrRange` is the one copy of that rule.

**A reverse range starts at the high bound.** `{ start: prefix, end: prefix + '\xFF', reverse: true }` walks
away from the data and yields nothing; `getAttrLength` returned 0 for every array it was ever asked about
because of it, and had no caller to notice.

**A write is stored when it returns, or it throws and memory forgets it.** Every write is made in a unit — one
`transact`, or a unit of its own (`journal.unit`) — and `makeLmdbAdapter` commits each unit as one synchronous
transaction when it ends. A unit LMDB refuses throws to the code that wrote, and the journal runs its undos, so the
engine never holds a write the files do not; nothing is buffered, dropped or reported later. Hydration loads only
records with a type, and logs how many it skipped: an attribute written to an id no entity was created with
(`admin.putAttr`) is kept under no type, as older formats kept it without an entity row.

## Naming: a name carries the operation, structure carries the rest

Four facts describe an engine operation, and only one of them belongs in its name
([`ears-naming-axes.md`](../../docs/archive/plans/ears-naming-axes.md) has why each other place is the wrong one):

| fact | carried by | not by |
|---|---|---|
| **operation** — what it does | the name: `create`, `write`, `transact` | — |
| **capability** — anyone, or the engine's creator | the `admin` sub-object beside the operations | a second face with a name of its own |
| **binding** — which engine | who you ask: `engine.create(...)`, or the SDK's bound engine | a free function per operation, or a twin of one |
| **checkedness** — checked against a pack's shapes | the `untyped` prefix, on the SDK's pack-facing surface only | anything in this package |

**Give a new operation a name that says what it does, and nothing else.** A name that also says who may call
it, which engine it acts on or whether it was checked is a fact welded into the wrong place, and the next one
is welded beside it. **That holds where people type by hand too**: the Database console injects the library's
own names (`READ_HELPER_NAMES`, `@apackdev/sdk/database-console`), so console code reads like pack code and
there is no second name for one operation to learn. `packages/apack-host/tests/query-vocabulary.spec.ts` holds
the console's vocabulary to the same rule as the exports.

## Vocabulary

**A member is held to rules it is classified by on its own — its type and its name — not to a list of members.**
Name it by the convention and it is checked the moment it compiles; break the convention and
`tests/vocabulary.spec.ts` names it. The only list there is the exceptions, each with its reason, and an exception
that no longer excuses anything fails as stale. What the surface *is* is reviewed in the API reports (`etc/*.api.md`).

Checked off the types (compile time, in `typecheck`):

- **`is*` answers a boolean; `find*` answers a list**, empty when nothing matches.
- **No member takes a boolean flag.** A direction or a mode is a name: `out`/`in`, `linkedTo`/`linkedFrom`,
  `trash`/`restore`.
- **Writes chain.** Every write builder member returns the builder, except what ends a chain: `destroy`,
  and `id` and `row`, which read the builder.

Checked off the names, on a real engine:

- **Pairs are complete.** A negation has its positive (`unlinkedTo`/`linkedTo`, `unlink`/`link`), a `…To` its
  `…From`, an `out…` its `in…`, and `ancestors` its `descendants`.
- **Absence is `undefined`.** A `get*` asked about an id no entity has never answers `null`, on the engine or its
  `admin` face; `null` is only ever a stored value.

Held by the types and the engine specs, which say more than a rule over names could:

- **One entity row**, `{ id, entityType, ...attributes }`, wherever a read returns one.
- **One relation row**, `{ id, kind, source, target, info }`, wherever a read returns one; a match and a patch use
  its field names.
- **The subject comes first**: the entity, type or relation an operation is about is its first argument.

## The engine

- **An instance.** `createEarsEngine({ persistence, isEntityType, isRelationKind, isRole, rowRules })` returns a new, empty engine that owns its stores, indexes and caches. Each module is a factory closing over its state (`createAttributeStorage`, `createRelations`, `createQuery`, `createWrites`, …), and `engine.ts` passes each its dependencies (the sink, the journal, the relations, the entity-type checker). No module keeps anything at module scope, not even a reference to an engine. `persistence` defaults to `noopSink`. `isEntityType` says which names are entity types, `isRelationKind` which are relation kinds and `isRole` which are roles. `rowRules(type)` says what a type's created row is held to (`RowRules`) — nothing by default, since an engine given no shapes knows of no rule: its `required` fields, which `create` refuses a row without and `delete` one of (`REQUIRED_FIELD`), before anything is written, and its `shortCode` prefix, which `create` numbers every row's `shortCode` with, `<prefix>-<n>` — once every check has passed, so a refused create takes no number. The short code is the engine's, like the id: `shortCode` is a reserved attribute, so no write sets or deletes it; a created row may bring one only as identity (`ShortCodeIdentity`, an import keeping its code), held to the type's `<prefix>-<n>` (`INVALID_SHORT_CODE`) and to no other entity holding it (`SHORT_CODE_IN_USE`), and an upsert's row may repeat the entity's own and no other. A code is unique, so `query(type).where('shortCode', code)` finds its entity, answered by the value index; which type a bare code belongs to is the registered packs' answer (`entityTypeOfShortCode`, `@apackdev/sdk/services`), since the prefixes are theirs and the engine knows none. The admin face's loads take any row. Codegen writes the rules: the required fields read off a pack's shapes, the prefix from its manifest entry's `shortCode`; the shape declares no `shortCode`, which a pack's `#generated/ears` adds to the shape from that same prefix (`ShortCodeOf<E>`).
- **One argument, one meaning.** Each entry point makes one claim about its argument and is held to it, throwing an `EarsError` (`errors.ts`) with a code otherwise: `query(type)` and `query([types])` take registered types and refuse anything else, `undefined` included (`UNKNOWN_ENTITY_TYPE`); `query.ids(ids)` takes ids and drops absent ones; `query.all()` is every entity but the engine's numbering sequences; `create(type, row)` takes the whole row in one object — its fields, and its `id`, `createdAt` and `updatedAt`, which no field can be named, so nothing can land in the wrong argument — and refuses an unregistered type, an id in use (`ID_IN_USE`), an id naming another type (`TYPE_MISMATCH`) and any other of the engine's own fields, before the entity exists; `write(id)` refuses an id no entity has (`NO_SUCH_ENTITY`) — a relation's included, which the compiler refuses there too (`WriteTarget`: an `EARS.RelationId` carries a marker `write`'s parameter can't take), the runtime refusal naming `updateRelation` and `removeRelation` for an id given untyped; a relation is read by `getRelation` and `findRelations`, changed by `updateRelation` and removed by `removeRelation`, each refusing an id no relation has (`NO_SUCH_RELATION`); `upsert(type, { id, ...row })` writes the row to the entity with its id or creates the entity with it — `create`'s row, the id always given; a link, and every read or walk that names a relation kind, refuse one the creator's `isRelationKind` doesn't know (`UNKNOWN_RELATION_KIND`), and `grant`, `revoke`, `grantExclusive` and `withRole` a role its `isRole` doesn't (`UNKNOWN_ROLE`), since a read naming a name nothing declared would answer as if nothing held it — the admin face's direct writes and loads take any, which is how data a removed pack left is read. An engine that took one string for a type or an id had to read an unknown name as an id, so a typo found nothing and a write to it made an orphan; separate entry points ask the caller which was meant, which is what lets each refuse. The untyped twins' name parameters are `TypeName<E>` (`write.ts`), so a dashed literal or an `EntityId` passed as a type fails to compile.
- **One value per attribute.** An attribute holds exactly one value, and a list is one array value, so a read (`getRow`, `getAttr`, `pick`, `pickAll`, `pickOne`, a write's `row()`) gives back exactly what was written, a one-element list as a list. Roles are the `role` attribute's list. Storage never changes a stored value in place (`attribute-storage.ts`: every write is one `assign` of the next value, and an undo is a `place` of the value before), so a value a read handed out, an undo and a held sink call each keep the value they saw. `where(k, v)` matches a value equal to `v` or a list holding it (`holds`); a predicate is given the whole value.
- **The write builder** (`WriteBuilder`, `runtime.ts`): `set`, `setMany`, `append`, `merge`, `delete`, `removeAt`, `removeValue`, `link(kind, target, { info, replace, acyclicIn })`, `unlink(kind, target?)`, `unlinkAll`, `grant`, `revoke`, `grantExclusive(role, among)`, `trash(at?)`, `restore()`, `destroy()`, `id`. Every attribute write refuses `RESERVED_ATTRIBUTES` (`id`, `entityType`, `shortCode`, `createdAt`, `updatedAt`, `role`, `trashedAt`), which only the engine writes; `setMany` refuses before writing any field. `append`, `removeAt` and `removeValue` work on the attribute's list and refuse a value that isn't one (`NOT_A_LIST`); `merge` merges into an object value. `link` is idempotent on the whole edge: kind, target and `info` (no `info` matches any edge between the ends), so linking an edge again keeps its id and its place; `link` refuses an options object with keys it doesn't know, which is what `info` passed positionally looks like. **A relation has two ends when it is committed** (`NO_SUCH_ENTITY`): outside a unit `link` refuses a target that isn't there before writing anything; inside one the check is deferred to the unit's commit (`journal.atCommit`), so a unit may link to an entity it creates later — a forward reference — and a link whose target it destroyed meanwhile went with it. `updateRelation` is held to the same rule for the ends it moves a relation to. A relation loaded from files can still have a missing end (`admin.addRelation` and `admin.updateRelation` take any), and the readers step around one.
- **The engine owns `updatedAt`.** `create` stamps it with the creation time (a row's own `updatedAt` keeps an import's), and a builder's attribute writes (`set`, `setMany`, `append`, `merge`, `delete`, `removeAt`, `removeValue`) stamp it once per builder; links, roles, the trash and the admin's direct writes don't. `write(id, { touch: false })` writes without stamping it — a view, a position kept for later. `null` is a stored value; `setMany` leaves a field whose value is `undefined` alone, `set(k, undefined)` refuses (`NO_VALUE`), and `delete(k)` is the one way to remove a field.
- **One verb per job in the query builder.** A filter keeps the current set — `where`, `has`/`lacks`, `withRole`, `ofType`, `within(ids)`, and by an edge `linkedTo(kind, other?)` (X → other, or X → any entity the query could reach), `linkedFrom(kind, other?)` (other → X, or any → X), their negations `unlinkedTo`/`unlinkedFrom` (a tree's roots are `unlinkedFrom(parentKind)`), and `linkedWith(other)` (any kind, either way). A walk moves to an edge's far end — `out(kinds, type?)` and `in(kinds, type?)`, typed to `type` — or any number of edges deep: `descendants(kinds, type?)` and `ancestors(kinds, type?)`, nearest first, each entity once, so a cycle ends the walk. `outEdges`/`inEdges` return each edge as a relation row. No step takes a direction flag. **A builder is a recipe**: chaining a step runs nothing, and each terminal runs the whole query against the data as it is then (`query.ts`, `builderOver`), so a builder kept across writes answers as one made after them and a predicate runs once per entity per terminal. Steps that keep or walk ids visit them as they come, so `first`, `exists`, `count` and `limit` stop early; `orderBy`, `reverse`, `distinct`, `descendants` and `ancestors` collect the set before them when they run.
- **One row shape.** A row is `{ id, entityType, ...attributes }` (`EntityRow`) wherever a read returns one: `getRow(id)`, which reads through the trash and is `undefined` for an id no entity has, and `pickAll`, `pickOne()` and a write builder's `row()`, which are rows of `getRow`.
- **One relation shape.** A relation is `{ id, kind, source, target, info }` (`RelationRow`) wherever a read returns one — `findRelations`, `outEdges`, `inEdges` — and `findRelations` and `updateRelation` take its field names (`{ kind?, source?, target? }`, `{ source?, target?, info? }`). The persistence port speaks the same names; only the stored LMDB row keeps its own (`{ kind, src, tgt }`).
- **The value index.** Storage keeps, per attribute kind, a value → the entities holding it, a list's elements each indexed (multikey); an object is never a key. A kind's index is built on its first read (`holders`) and kept by `place`, the one memory write — so a unit's undo, hydration and a destroy keep it too. A query started from types stays unwalked until a step needs its ids, so `where(k, v)` with a primitive and `withRole` read the index and give the matches in the order a walk of the types would (each entity's ordinal is its value in its type's index); a predicate, an object, `NaN` and `entityType` are walked. Short codes skip a taken number through it, so only a sequence's first use walks the type.
- **The trash is the engine's.** `write(id).trash(at?)` writes `trashedAt` (kept the first time), and storage keeps the trashed ids in a set that `place` maintains, so undo and hydration keep it right. No query reaches a trashed entity — `query(type)`, `query.ids`, `query.all`, a link's far end (`out`, `in`, `outEdges`, `inEdges`) — and a query kept across a trash no longer reaches it, since every terminal runs the query against the data as it is then. `query.withTrashed` is the same entry points over the trash too (`builderOver(hasEntity)` against `isLive`), and `query.trashed` is those entry points starting from only the trashed entities (`trashed(type)`, `.ids(ids)`, `.all()`). A write reaches a trashed entity, so `restore()` works; relations and attribute reads by id see it, and the numbering counts it, so a trashed row's short code is never handed out again.
- **Operations, and `admin` beside them; holding the engine is the capability.**
  - The engine's own members (`Ears`): `query`, `create`, `upsert`, `write`, `transact`, attribute and role reads, the relation operations (`getRelation`, `findRelations`, `updateRelation`, `removeRelation`) and `wouldCreateCycle`. A program is handed the engine typed as `Ears`, which has no `admin`; a pack reaches the app's through the SDK (`@apackdev/sdk/ears`).
  - `engine.admin` (`EarsAdmin`): `clear`, the loads hydration makes (`bulkLoadAttr`, `bulkLoadRelation`), unchecked direct writes (`putAttr`, `deleteAttr`, `addRelation`, `updateRelation` — any kind between any ids, either end missing included, which is how a spec makes the data a check would refuse), the raw listings (`getAllEntities`, `getEntitiesOfType`: every id, the engine's own and the trash included) and `repositories()`. Only the creator holds it: the api's composition root (hydration through `/lmdb`, and `createHostRuntime`'s `appData` reset, backup and restore), the CLI's flow compiler and decompiler (a private engine per compile), and `@apackdev/sdk/testing`.
- **Binding is the SDK's.** This package has no free function that acts on an engine: an operation is a member of the engine you hold. Which engine the app's code acts on is `@apackdev/sdk/ears`: `boundEars()`, and the operations over it pack code calls without holding an engine (`untypedQuery`, `untypedCreate`, `findRelations`, `wouldCreateCycle`, …). `bindHost` binds the app's engine there, `startTestRuntime` a test's, and tooling binds its own with the host-only `_bindEars` or passes one (`exportFlowsToDSL(dir, { engine })`).
- **Units.** `transact(fn)` (`engine.transact`, and the SDK's `transact` over the bound engine) runs `fn` as one unit. Writes inside it change memory at once, so `fn` reads its own writes, and each first records how to undo itself (`journal.ts`: attribute storage and the relations module call `journal.touch` before a change, and check `journal.open` first, so a write outside a unit builds no key and costs nothing). If `fn` throws, the undos run in reverse and the sink hears nothing; if it returns, the sink receives the unit's calls between `onUnitStart` and `onUnitEnd`, and the undos are kept until the sink has stored them: a sink that throws (`onUnitEnd`) gets the unit undone in memory and the throw passed on. A unit inside another commits into it and rolls back only its own writes. An `async fn` is refused, since an `await` would split the unit — but only once it has started, so what it writes after its first `await` lands outside any unit; its rejection is handled, so it is not an unhandled one. `admin.clear()` inside a unit is refused too. A held sink call carries a copy of its value list, so a later write in the unit, or a nested unit that rolls back, cannot change what is sent. A write outside `transact` is a unit of its own: each storage and relation mutator, and each operation of the write builder (`create`, a builder call, `updateRelation`), goes through `journal.unit` (`unitWrites`), so it is stored whole or not at all.
- **Repositories are not the engine's.** A pack's repositories arrive in its registration (`PackRegistration.repositories`) and are kept by the host's pack registry with its other contributions; pack code reads them through `#generated/repository` or `services.repository`, which read the bound app's packs (`@apackdev/sdk/services`' `repository`). An engine knows nothing of them.
- **Typed facades.** `defineEars<Schema>(engine)` returns `query`, `create`, `upsert`, `write`, `transact`, `newId` and `getAttr` typed against a schema (`EarsSchema`: its entity shapes, and the names, relation kinds and roles they take; `UntypedSchema` checks nothing), each acting on the engine the `engine` getter returns when called. Packs don't call it: `apack pack generate-entries` writes `#generated/ears` with it, over the pack's shapes, its dependencies' and the SDK's, bound to the SDK's `boundEars`, declaring the pack's `PackSchema`.
- The trust model: packs run in-process. The faces define the contract, not a security boundary.

## Persistence

- `PersistenceSink` is the port: the engine calls it on every create, destroy, attribute write and relation write (`onCreateEntity`, with the type `create` gave it; `onPutAttr`, an attribute's value after each write; `onDropAttr`, `onAddRelation`, …). Every method is required: a sink that stores nothing implements it as a no-op (`noopSink`). Bulk loads (`admin.bulkLoadAttr`, `admin.bulkLoadRelation`) don't. A destroy comes after the entity's relations were removed (`onRemoveRelation` each), so the LMDB sink deletes only the entity's row and its attributes, reading them per attribute kind (one row each) rather than scanning the store.
- `openLmdbStore({ path, engine, readOnly?, log? })` (`@apackdev/ears/lmdb`) opens the environment at `path` and returns the store: `sink` (the LMDB sink, which the engine is created with), `env`, `path`, `readOnly`, `isOpen()`, `hydrate()` (loads the database into `engine()`, the admin face), `read()` (`LmdbReader`), `copyTo(targetDir)` (LMDB's own copy of one read transaction into `targetDir/data.mdb`, which is what a backup takes, so a copy made while the app writes is one moment of the database rather than a file read caught mid-commit; nothing is buffered, so it holds every write that returned before it), `close()` (flushes what was committed to disk and closes), `reset()` (empties the data databases in one transaction, keeping the format stamp, with the store open throughout) and `replaceWith(dir)` (puts the database at `dir` in its place, checked like any, in one transaction); both leave the engine's memory to the caller, which clears or hydrates it in the same turn. A closed store refuses every write. **Durability:** a unit commits without waiting for the disk (`NO_SYNC_FLUSH`, on an environment opened with `overlappingSync: false`, which every process opening it shares through `openEnvAt`), so it survives the app crashing at once; a background `root.sync()` once writes pause for `SYNC_IDLE_MS` (100 ms), at the latest `SYNC_INTERVAL_MS` (1 s) after the first unsynced commit, and a flushed write on `close()` bound what an OS crash can take. A caller that cannot lose a write to one waits for it: `engine.durable()` resolves once a sync that began after the last commit has finished (the sink's `durable()`), and `transact(fn, { durable: true })` commits flushed, which makes every commit before it durable too (`tests/lmdb/durability.spec.ts`). `engine` is a function because the engine is created after the store, with its sink. Nothing opens on import. `readOnly` opens existing environments without writing: LMDB opens them read-only, the sink throws on a write, and `reset()` throws. `log` takes the store's lines (hydration counts, relations it skipped, closing, and errors closing or syncing), which go to `console.log` by default. Nothing else in the package writes to the console.
- **A unit is stored whole or not at all.** Between `onUnitStart` and `onUnitEnd` the LMDB adapter collects the unit's writes in the order they were made, and at the end runs them in one `transactionSync`: a refused row throws, nothing of the unit is stored, and the engine undoes it in memory.
- **Storage format.** `LMDB_FORMAT_VERSION` (`envs.ts`) is how this version encodes rows. Every environment records it in its own `meta` database, and `openEnvAt` checks it: files that record another format are refused, naming it and, when the format is newer, saying to update apack; files that record none and hold data were written before formats were recorded, which is format 1, and are refused too, naming the conversion; a new, empty environment is stamped by its first writable open, before anything is written to it, and a stamp that fails (a full disk) refuses that open: unstamped, this version's rows would read as format 1 to the next open, which would refuse them, while refusing an empty environment costs nothing (`tests/lmdb/format-stamp.spec.ts`). The environment is closed again when the check refuses it. **Format 4 keeps an entity as one record**, so boot decodes a row per entity and reads no large value: `rows` holds an `EntityRecord` per id — its type (null for attributes written to an id no entity was created with), its small fields as `[kind, value]` pairs, and its large ones (`isLarge`, `values.ts`, the rule the engine keeps out of memory by too) as `[kind, size, length]`, each value in `values` under `kind␟entityId`; `relationRows` holds a `RelationRecord` per relation, with no entity row; msgpack throughout. The adapter edits a working copy of each record a commit touches and puts each once. `entityType` is read from the id (`entityTypeOf`, the one parser) and stored only as the record's type. There is no upgrade at boot: `convertToCurrentFormat` (`lmdb/convert.ts`) converts an older environment in place a step per format (`convertToFormat2`: format 1's second records removed; `convertToFormat3`: format 2's rows per list index joined into one row, a role always a list, and a `deleted: true` mark turned into `trashedAt`; `convertToFormat4`: format 3's entity and attribute rows gathered into records, its large values into `values`, and its databases dropped), each step recording its own format, and only `scripts/ears-convert.ts` calls it, on a copy.
- The api's composition (`openAppStore()`, `packages/api/src/runtime/index.ts`) is the one production caller: it opens the store, creates the engine with `store.sink` and binds the app. Host code (`@apackdev/host/services`, `/backup`) takes the store and the admin face as arguments.

## Tests (`tests/`)

- `engine/`: black-box specs of the public API: `writes` (`create`, `upsert` and `write`, each entry point's refusals, the builder's attribute writes, the reserved names, the ids and fields returned), `relations` (link, unlink, `out`/`in`, `linkedTo`/`linkedFrom`/`linkedWith`, the hierarchy walks, cycle detection, roles), `queries` (the entry points and their refusals, filters, terminals and ordering), `transact` (every write undone by a unit that throws, the sink's bracket, nesting) and `persistence` (the exact order and payload of sink calls, hydration through bulk load). They reach the engine only through `engine-under-test.ts` (`freshEngine`); `helpers.ts` has `recordingSink()`. A few specs pin existing quirks; they say so.
- `vocabulary.spec.ts`: the rules in Vocabulary, over every member of the engine, `admin`, a query builder and a write builder — off the types for `is*`, `find*`, flags and chaining, off a real engine for pairs and absence — each with a case showing it names a member that breaks it.
- `engines.spec.ts`: a typed facade acts on whichever engine its getter returns; two engines in one process share nothing. The bound engine's operations are the SDK's, and its spec is `apack-sdk/tests/ears/bound-ears.spec.ts`.
- `lmdb/`: `persistence` (the LMDB adapter and its units, `LmdbReader`), `convert` (format 1 to 2 to 3 to 4, and the refusal of another kind's files), `store` (`openLmdbStore`: writes reach LMDB through `store.sink`, and a store opened again hydrates them), `format-stamp` (the kind and format each environment records and is refused by) and `record-store` (`openRecordStore` and the memory store, the cases both share run against both).
- Test files run in parallel (`fileParallelism: true`): each creates its own engines.

## Benchmark

`bench/ears.bench.ts` hydrates an app-sized graph (50k entities, 200k attributes, 100k relations) into an engine's admin face, then times `query` by type with a `where` and `pickAll`, lookups by a unique value and by role (the value index), a relation traversal, `orderBy`, `first()` over a type, `getRow`, `pickAll`, `linkedWith`, a 10k-edge hub, short codes, and 1,000 creates, alone and as one unit (`transact`). It times the engine in `dist`, the build that ships: `npm run bench -w @apackdev/ears` builds the package first. `npm run bench:heap -w @apackdev/ears` (`bench/heap.ts`) reads the heap with the same graph loaded. The same bench times writes on an LMDB store of its own, a durable unit and `durable()`. `npm run bench:budget -w @apackdev/ears` (`bench/budget.ts`) writes data of the production data's shape (`bench/production-shape.ts`, its large values included) at its size and twice it to an LMDB store, boots each in a process of its own, and exits 1 when the heap after boot passes `HEAP_BUDGET_MB` a scale; boot time is printed and never gated, since load inflates a duration. What the engine holds is `admin.memoryStats()` (per type in memory, out of memory, the cache's hits and misses) and what the store did `store.stats()` (hydrate time, commits, syncs); hydration logs its out-of-line values, closing its commits and syncs, and `apack db inspect` with no argument prints both. The baseline is recorded in `docs/plans/ears-storage-layout.md` (Step 4); the tolerance is +10% median per case, and anything beyond it needs investigating before an engine change lands.
