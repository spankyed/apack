# @apackdev/ears

EARS, the entity-attribute-relation graph store behind apack's data: the engine, the core `EARS` types, the typed facades, the ordered key-value store the engine is written on, and its LMDB backend (`@apackdev/ears/lmdb`). It's the bottom layer: it imports no `@apackdev/*` package and knows no packs and no SDK entity names (those are the SDK's, in `@apackdev/sdk/types`). The SDK, host, api, packs and tests import it. The root `CLAUDE.md` ("SDK packages", "Data layer") has the one-paragraph view; this file covers how the package works.

## Package basics

- Published like `@apackdev/sdk`: each export in its `package.json` resolves `src/` under the `@apackdev/source` condition and `dist/` otherwise, and the build stages a derived manifest with no source branches under `publish/`, which is what npm publishes. Exports: `.` (the engine, types and the key-value seam with its memory backend) and `./lmdb` (the LMDB store). It's in the changesets fixed group (`.changeset/config.json`) and supports TypeScript 5.7 and later (`packages/typescript-floor`).
- `lmdb` is an optional peer dependency (a dev dependency here). Only `src/lmdb/` loads it; the app installs it (`packages/api` depends on it).
- Relative imports name the `.ts` source; `tsc` (`rewriteRelativeImportExtensions`) writes `.js`. `sideEffects: false`, and no module does anything on import.
- It's a shared-instance package (`SHARED_INSTANCE_PACKAGES` in `@apackdev/host/build/shared-deps`): packs, dependency runtimes, the app and tests load one copy, so an engine created by one is usable by all. The pack loader's bridge and the harness bridge provide every export except `./lmdb` (`APP_ONLY_EXPORTS`). Pack frontends don't share it: they inline the constants and helpers they import.

| `engine.ts` | `createEarsEngine({ kv?, isEntityType, isRelationKind, isRole, rowRules?, warn? })` and the faces' types (`EarsEngine`, `Ears`, `EarsAdmin`). It composes the factories below over one store |

| `attribute-storage.ts` | `createAttributeStorage`: entities and their attributes in the store's keys (`['v', id, kind]`, `['i', id]`, a type's live and trashed ranges, its count, its indexes, the numbering sequences); `entityTypeOf`, the one reader of an id's type. It holds nothing of relations |
| `relations.ts` | `createRelations`: every relation's row (`['r', relId]`) and its edge keys (`['o'\|'n', entity, kind, seq]` holding the far end, `['b', source, kind, target, seq]` the edges between two ends), with every relation write and read. | `query.ts` | `createQuery`: the query entry points (`query(type)`, `query.ids`, `query.all`; exported untyped as `untypedQuery`) and the builder, `b64Encode`/`b64Decode` |

| `journal.ts` | `createJournal`: `transact` runs a unit of the store (which keeps nothing of a unit that throws) and its commit-time checks (`atCommit`) |
| `numbering.ts` | The numbering behind `create`'s short codes (`generateShortCode`, the engine's own) and `nextLabel(type, base)` (a default label that must be unique), which take numbers from a stored sequence per key (`['s', key]`), so a number is never handed out twice (a destroyed row's included) and a unit that throws returns its numbers |
| `hierarchy.ts` | `wouldCreateCycle`, visiting an entity once, so a cycle in the data ends the walk (the hierarchy walks themselves are query steps, `ancestors`/`descendants`) |

| `records.ts` | Record stores, which are not the engine: `RecordStore` (whole records by id, found through declared indexes in id order), `RecordIndexes` (each index a function deriving the value a record is filed under, so a computed one needs no stored field), and `createMemoryRecordStore`, the one in memory, which encodes through JSON as LMDB does; `openRecordStore` (`/lmdb`) is the same interface on disk |
| `lmdb/` | `@apackdev/ears/lmdb`: `store.ts` (`openLmdbStore`, and `openEnvironment`, the one way an environment is opened), `kv-backend.ts` (`createLmdbKVBackend`, the seam's backend over one LMDB database), `stamp.ts` (`checkStamp`: the kind and format stamp both kinds of environment are opened through, so each refuses the other's files and an older or newer format the same way), `convert.ts` (the format conversions, run only on a copy), `record-store.ts` (`openRecordStore`: a `RecordStore` in an LMDB environment of its own — what the app keeps run history in — stamped with the `records` kind and its own format) |
| `utils.ts` | Private helpers (`isPlainObject`, the id suffix) |

**A read is one read transaction, and an environment has 126 reader slots.** The LMDB backend takes a read
transaction per `read` and releases it in `finally`, however the read ends — early, by a predicate that throws, or
by a visit answering false — so no cursor outlives the call that opened it (`tests/lmdb/store.spec.ts` runs a
thousand reads that stop early or throw and counts the slots). Taken by hand and left open, the 127th throws
`MDB_READERS_FULL`, after which every read and write fails for the life of the process. Where a body removes the
keys of a range it walks with lmdb-js directly (the conversions, `replaceWith`), it collects them first.

## Naming: a name carries the operation, structure carries the rest

Four facts describe an engine operation, and only one of them belongs in its name
([`ears-naming-axes.md`](../../docs/archive/plans/ears-naming-axes.md) has why each other place is the wrong one):

| fact | carried by | not by |
|---|---|---|
| **operation** — what it does | the name: `create`, `write`, `transact` | — |
| **capability** — anyone, or the engine's creator | the `admin` sub-object beside the operations | a second face with a name of its own |
| **binding** — which engine | who you ask: `engine.create(...)`, or the SDK's bound engine | a free function per operation, or a twin of one |
| **checkedness** — checked against a pack's shapes | the `untyped` prefix, on the SDK's pack-facing surface only | anything in this package |

**Give a new operation a name that says what it does, and nothing else.** A name that also says who may call
it, which engine it acts on or whether it was checked is a fact welded into the wrong place, and the next one
is welded beside it. **That holds where people type by hand too**: the Database console injects the library's
own names (`READ_HELPER_NAMES`, `@apackdev/sdk/database-console`), so console code reads like pack code and
there is no second name for one operation to learn. `packages/apack-host/tests/query-vocabulary.spec.ts` holds
the console's vocabulary to the same rule as the exports.

## Vocabulary

**A member is held to rules it is classified by on its own — its type and its name — not to a list of members.**
Name it by the convention and it is checked the moment it compiles; break the convention and
`tests/vocabulary.spec.ts` names it. The only list there is the exceptions, each with its reason, and an exception
that no longer excuses anything fails as stale. What the surface *is* is reviewed in the API reports (`etc/*.api.md`).

Checked off the types (compile time, in `typecheck`):

- **`is*` answers a boolean; `find*` answers a list**, empty when nothing matches.
- **No member takes a boolean flag.** A direction or a mode is a name: `out`/`in`, `linkedTo`/`linkedFrom`,
  `trash`/`restore`.
- **Writes chain.** Every write builder member returns the builder, except what ends a chain: `destroy`,
  and `id` and `row`, which read the builder.

Checked off the names, on a real engine:

- **Pairs are complete.** A negation has its positive (`unlinkedTo`/`linkedTo`, `unlink`/`link`), a `…To` its
  `…From`, an `out…` its `in…`, and `ancestors` its `descendants`.
- **Absence is `undefined`.** A `get*` asked about an id no entity has never answers `null`, on the engine or its
  `admin` face; `null` is only ever a stored value.

Held by the types and the engine specs, which say more than a rule over names could:

- **One entity row**, `{ id, entityType, ...attributes }`, wherever a read returns one.
- **One relation row**, `{ id, kind, source, target, info }`, wherever a read returns one; a match and a patch use
  its field names.
- **The subject comes first**: the entity, type or relation an operation is about is its first argument.

## The engine

- **An instance.** `createEarsEngine({ kv, isEntityType, isRelationKind, isRole, rowRules, warn })` returns a new engine over the ordered key-value store `kv` (`kv.ts`; a new, empty memory one by default), which holds everything it knows: it keeps no copy of the data, so a read reads the store and two engines over one store see one database. Each module is a factory closing over the store's access (`createAttributeStorage`, `createRelations`, `createQuery`, `createWrites`, …), and `engine.ts` passes each its dependencies (the access, the journal, the relations, the entity-type checker). No module keeps anything at module scope, not even a reference to an engine. `isEntityType` says which names are entity types, `isRelationKind` which are relation kinds and `isRole` which are roles. `warn` hears what will be slow with more data (an unindexed `where` past `UNINDEXED_WALK_WARNING` rows, once per call site). `rowRules(type)` says what a type's created row is held to (`RowRules`) — nothing by default, since an engine given no shapes knows of no rule: its `required` fields, which `create` refuses a row without and `delete` one of (`REQUIRED_FIELD`), before anything is written, and its `shortCode` prefix, which `create` numbers every row's `shortCode` with, `<prefix>-<n>` — once every check has passed, so a refused create takes no number. The short code is the engine's, like the id: `shortCode` is a reserved attribute, so no write sets or deletes it; a created row may bring one only as identity (`ShortCodeIdentity`, an import keeping its code), held to the type's `<prefix>-<n>` (`INVALID_SHORT_CODE`) and to no other entity holding it (`SHORT_CODE_IN_USE`), and an upsert's row may repeat the entity's own and no other. A code is unique, so `query(type).where('shortCode', code)` finds its entity, answered by the value index; which type a bare code belongs to is the registered packs' answer (`entityTypeOfShortCode`, `@apackdev/sdk/services`), since the prefixes are theirs and the engine knows none. The admin face's loads take any row. Codegen writes the rules: the required fields read off a pack's shapes, the prefix from its manifest entry's `shortCode`; the shape declares no `shortCode`, which a pack's `#generated/ears` adds to the shape from that same prefix (`ShortCodeOf<E>`).
- **One argument, one meaning.** Each entry point makes one claim about its argument and is held to it, throwing an `EarsError` (`errors.ts`) with a code otherwise: `query(type)` and `query([types])` take registered types and refuse anything else, `undefined` included (`UNKNOWN_ENTITY_TYPE`); `query.ids(ids)` takes ids and drops absent ones; `query.all()` is every entity but the engine's numbering sequences; `create(type, row)` takes the whole row in one object — its fields, and its `id`, `createdAt` and `updatedAt`, which no field can be named, so nothing can land in the wrong argument — and refuses an unregistered type, an id in use (`ID_IN_USE`), an id naming another type (`TYPE_MISMATCH`) and any other of the engine's own fields, before the entity exists; `write(id)` refuses an id no entity has (`NO_SUCH_ENTITY`) — a relation's included, which the compiler refuses there too (`WriteTarget`: an `EARS.RelationId` carries a marker `write`'s parameter can't take), the runtime refusal naming `updateRelation` and `removeRelation` for an id given untyped; a relation is read by `getRelation` and `findRelations`, changed by `updateRelation` and removed by `removeRelation`, each refusing an id no relation has (`NO_SUCH_RELATION`); `upsert(type, { id, ...row })` writes the row to the entity with its id or creates the entity with it — `create`'s row, the id always given; a link, and every read or walk that names a relation kind, refuse one the creator's `isRelationKind` doesn't know (`UNKNOWN_RELATION_KIND`), and `grant`, `revoke`, `grantExclusive` and `withRole` a role its `isRole` doesn't (`UNKNOWN_ROLE`), since a read naming a name nothing declared would answer as if nothing held it — the admin face's direct writes and loads take any, which is how data a removed pack left is read. An engine that took one string for a type or an id had to read an unknown name as an id, so a typo found nothing and a write to it made an orphan; separate entry points ask the caller which was meant, which is what lets each refuse. The untyped twins' name parameters are `TypeName<E>` (`write.ts`), so a dashed literal or an `EntityId` passed as a type fails to compile.
- **One value per attribute.** An attribute holds exactly one value, and a list is one array value, so a read (`getRow`, `getAttr`, `pick`, `pickAll`, `pickOne`, a write's `row()`) gives back exactly what was written, a one-element list as a list. Roles are the `role` attribute's list. A value is encoded as it is written and decoded as it is read, so a value a read handed out is the reader's own copy, and changing it changes nothing stored; a memory store created with `freeze` (the SDK's test runtime) hands out frozen values, so code that mutates a read fails there rather than appearing to work. `where(k, v)` matches a value equal to `v` or a list holding it (`holds`); a predicate is given the whole value.
- **The write builder** (`WriteBuilder`, `runtime.ts`): `set`, `setMany`, `append`, `merge`, `delete`, `removeAt`, `removeValue`, `link(kind, target, { info, replace, acyclicIn })`, `unlink(kind, target?)`, `unlinkAll`, `grant`, `revoke`, `grantExclusive(role, among)`, `trash(at?)`, `restore()`, `destroy()`, `id`. Every attribute write refuses `RESERVED_ATTRIBUTES` (`id`, `entityType`, `shortCode`, `createdAt`, `updatedAt`, `role`, `trashedAt`), which only the engine writes; `setMany` refuses before writing any field. `append`, `removeAt` and `removeValue` work on the attribute's list and refuse a value that isn't one (`NOT_A_LIST`); `merge` merges into an object value. `link` is idempotent on the whole edge: kind, target and `info` (no `info` matches any edge between the ends), so linking an edge again keeps its id and its place; `link` refuses an options object with keys it doesn't know, which is what `info` passed positionally looks like. **A relation has two ends when it is committed** (`NO_SUCH_ENTITY`): outside a unit `link` refuses a target that isn't there before writing anything; inside one the check is deferred to the unit's commit (`journal.atCommit`), so a unit may link to an entity it creates later — a forward reference — and a link whose target it destroyed meanwhile went with it. `updateRelation` is held to the same rule for the ends it moves a relation to. A relation loaded from files can still have a missing end (`admin.addRelation` and `admin.updateRelation` take any), and the readers step around one.
- **The engine owns `updatedAt`.** `create` stamps it with the creation time (a row's own `updatedAt` keeps an import's), and a builder's attribute writes (`set`, `setMany`, `append`, `merge`, `delete`, `removeAt`, `removeValue`) stamp it once per builder; links, roles, the trash and the admin's direct writes don't. `write(id, { touch: false })` writes without stamping it — a view, a position kept for later. `null` is a stored value; `setMany` leaves a field whose value is `undefined` alone, `set(k, undefined)` refuses (`NO_VALUE`), and `delete(k)` is the one way to remove a field.
- **One verb per job in the query builder.** A filter keeps the current set — `where`, `has`/`lacks`, `withRole`, `ofType`, `within(ids)`, and by an edge `linkedTo(kind, other?)` (X → other, or X → any entity the query could reach), `linkedFrom(kind, other?)` (other → X, or any → X), their negations `unlinkedTo`/`unlinkedFrom` (a tree's roots are `unlinkedFrom(parentKind)`), and `linkedWith(other)` (any kind, either way). A walk moves to an edge's far end — `out(kinds, type?)` and `in(kinds, type?)`, typed to `type` — or any number of edges deep: `descendants(kinds, type?)` and `ancestors(kinds, type?)`, nearest first, each entity once, so a cycle ends the walk. `outEdges`/`inEdges` return each edge as a relation row. No step takes a direction flag. **A builder is a recipe**: chaining a step runs nothing, and each terminal runs the whole query against the data as it is then (`query.ts`, `builderOver`), so a builder kept across writes answers as one made after them and a predicate runs once per entity per terminal. Steps that keep or walk ids visit them as they come, so `first`, `exists`, `count` and `limit` stop early; `orderBy`, `reverse`, `distinct`, `descendants` and `ancestors` collect the set before them when they run.
- **One row shape.** A row is `{ id, entityType, ...attributes }` (`EntityRow`) wherever a read returns one: `getRow(id)`, which reads through the trash and is `undefined` for an id no entity has, and `pickAll`, `pickOne()` and a write builder's `row()`, which are rows of `getRow`.
- **One relation shape.** A relation is `{ id, kind, source, target, info }` (`RelationRow`) wherever a read returns one — `findRelations`, `outEdges`, `inEdges` — and `findRelations` and `updateRelation` take its field names (`{ kind?, source?, target? }`, `{ source?, target?, info? }`). The stored relation row (`['r', relId]`) keeps `source` and `target` too; only format 3's tables, which a conversion reads, named them `src` and `tgt`.
- **Declared indexes.** A type indexes the fields its row rules declare (`RowRules.indexes`, written by codegen from a manifest entry's `indexes`), and every type indexes `role` and `shortCode`. An index is keys, one per value and entity (`['x', type, kind, value, seq]`), a list's elements each indexed (multikey); it holds `null`, booleans, finite numbers and strings up to 256 characters (`isIndexKey`). An index is built from its type's rows on its first read (`holders`), which records it built (`['xb', type, kind]`), and every attribute write keeps it in the same unit — so a unit that throws, a load and a destroy keep it too. The build is a unit of its own and a cache of the walk that read made, so a store that refuses it (read-only, or full) leaves the index unbuilt and the read answers from the walk. A `where(k, v)` or `withRole` on a type start reads the index where the type declares the field and gives the matches in the order a walk of the types would; where it doesn't, it filters the type's rows, finding the same matches, and past `UNINDEXED_WALK_WARNING` rows tells the engine's creator through `warn`, once per call site. Short codes skip a taken number through the index, so only a sequence's first use walks the type.
- **The trash is the engine's.** `write(id).trash(at?)` writes `trashedAt` (kept the first time), and moves the entity from its type's live range (`['e', type, seq]`) to its trashed one (`['d', type, seq]`) in the same unit. No query reaches a trashed entity — `query(type)`, `query.ids`, `query.all`, a link's far end (`out`, `in`, `outEdges`, `inEdges`) — and a query kept across a trash no longer reaches it, since every terminal runs the query against the data as it is then. `query.withTrashed` is the same entry points over the trash too (`builderOver(hasEntity)` against `isLive`), and `query.trashed` is those entry points starting from only the trashed entities (`trashed(type)`, `.ids(ids)`, `.all()`). A write reaches a trashed entity, so `restore()` works; relations and attribute reads by id see it, and the numbering counts it, so a trashed row's short code is never handed out again.
- **Operations, and `admin` beside them; holding the engine is the capability.**
  - The engine's own members (`Ears`): `query`, `create`, `upsert`, `write`, `transact`, attribute and role reads, the relation operations (`getRelation`, `findRelations`, `updateRelation`, `removeRelation`) and `wouldCreateCycle`. A program is handed the engine typed as `Ears`, which has no `admin`; a pack reaches the app's through the SDK (`@apackdev/sdk/ears`).
  - `engine.admin` (`EarsAdmin`): `clear`, the loads a conversion makes (`bulkLoad`, one unit in which `bulkLoadAttr` and `bulkLoadRelation` skip the checks a write makes), `countEntities` (the rows per type, keys only), unchecked direct writes (`putAttr`, `deleteAttr`, `addRelation`, `updateRelation` — any kind between any ids, either end missing included, which is how a spec makes the data a check would refuse), the raw listings (`getAllEntities`, `getEntitiesOfType`: every id, the engine's own and the trash included) and `repositories()`. Only the creator holds it: the api's composition root, a backup's read (`readBackup`) and the format conversions, the CLI's flow compiler and decompiler (a private engine per compile), and `@apackdev/sdk/testing`.
- **Binding is the SDK's.** This package has no free function that acts on an engine: an operation is a member of the engine you hold. Which engine the app's code acts on is `@apackdev/sdk/ears`: `boundEars()`, and the operations over it pack code calls without holding an engine (`untypedQuery`, `untypedCreate`, `findRelations`, `wouldCreateCycle`, …). `bindHost` binds the app's engine there, `startTestRuntime` a test's, and tooling binds its own with the host-only `_bindEars` or passes one (`exportFlowsToDSL(dir, { engine })`).
- **Units.** `transact(fn, { durable? })` (`engine.transact`, and the SDK's `transact` over the bound engine) runs `fn` as one unit of the store: one LMDB write transaction, so a reader sees all of it or none. Writes inside it read their own writes. If `fn` throws, the unit keeps nothing (`kv.ts`: a memory store discards its pending overlay, LMDB aborts the transaction); if it returns, it commits. A unit inside another is a savepoint: it commits into it and rolls back only its own writes. `durable: true` commits with a sync rather than leaving it to group commit (see Persistence). An `async fn` is refused, since an `await` would split the unit — but only once it has started, so what it writes after its first `await` lands outside any unit; its rejection is handled, so it is not an unhandled one. `admin.clear()` inside a unit is refused too. Outside a unit each write is its own unit, committed as it returns.
- **Repositories are not the engine's.** A pack's repositories arrive in its registration (`PackRegistration.repositories`) and are kept by the host's pack registry with its other contributions; pack code reads them through `#generated/repository` or `services.repository`, which read the bound app's packs (`@apackdev/sdk/services`' `repository`). An engine knows nothing of them.
- **Typed facades.** `defineEars<Schema>(engine)` returns `query`, `create`, `upsert`, `write`, `transact`, `newId` and `getAttr` typed against a schema (`EarsSchema`: its entity shapes, and the names, relation kinds and roles they take; `UntypedSchema` checks nothing), each acting on the engine the `engine` getter returns when called. Packs don't call it: `apack pack generate-entries` writes `#generated/ears` with it, over the pack's shapes, its dependencies' and the SDK's, bound to the SDK's `boundEars`, declaring the pack's `PackSchema`.
- The trust model: packs run in-process. The faces define the contract, not a security boundary.

## Persistence

- **The store is the database.** An engine reads and writes its `kv`, an `OrderedKV` (`kv.ts`): ordered keys of
  strings, numbers, booleans and `null` in the seam's own codec, values in `msgpackr` (`mapsAsObjects: false`, so a
  field named `__proto__` is a field). Its operations are `read` (a snapshot, or the unit open) and `write` (a unit,
  savepoints inside one). Two backends implement it: `createMemoryKV` (tests and tooling) and the LMDB one.
- `openLmdbStore({ path, readOnly?, syncIdleMs?, syncIntervalMs? })` (`@apackdev/ears/lmdb`) opens the environment at `path` and
  returns the store: `kv` (which an engine is created on), `path`, `readOnly`, `syncs`, `readers()`, `durable()`,
  `copyTo(targetDir)` (LMDB's own copy of one read transaction into `targetDir/data.mdb`, which is what a backup
  takes; compacted, without the pages deletes freed, only when `COMPACT_COPIES` is on. It is off: a compacted copy of
  multi-page values aborts the process when it is emptied, an lmdb-js 3.5.9 bug fixed by kriszyp/lmdb-js#381
  (`docs/references/evidence/lmdb-compacted-copy-crash.md`); turning it on is that flag, once `lmdb` is a release with
  the fix), `replaceWith(dir)` (every entry replaced by another database's, in one durable unit, the store
  staying open), `reset()` (every entry removed, in one durable unit; both empty the database with the writer's
  `clear()`, which on LMDB is `clearSync` — `mdb_drop`, run in the unit's transaction — rather than a delete per key) and `close()`. Nothing opens on import.
  `readOnly` opens existing files without writing: a write, `reset()` and `replaceWith()` throw naming why.
- **A unit is visible as it commits, and durable within the window.** Each unit commits without a sync, which is what
  makes a write cost microseconds, and survives the process crashing once it returns (`tests/lmdb/store.spec.ts`
  kills a writer with `SIGKILL` the moment its write returns). What survives the machine failing is a sync: group
  commit syncs once writes pause for `syncIdleMs` (`SYNC_IDLE_MS`, 100ms), and `syncIntervalMs` (`SYNC_INTERVAL_MS`, 1s) after
  the first unsynced commit at the latest, so a steady stream of writes can't hold it off; each sync runs off the main
  thread and makes every commit before it durable. `durable()` resolves once every unit committed
  before it is on disk, and rejects when the sync it waits on fails, which leaves those commits owed for the next
  sync (one a timer starts is caught, so a failure never reaches the process); `transact(fn, { durable: true })` commits with the sync. `close()` syncs what is owed.
  Content an apply writes rides group commit: a lost apply is applied again on the next boot.
- **Storage format.** `LMDB_FORMAT_VERSION` (`store.ts`) is how this version lays out an environment: format 4, one
  database (`kv`) holding the engine's keys. Every environment records its format in its own `meta` database, and
  `openEnvironment` checks it: files that record another format are refused, naming it and, when the format is newer,
  saying to update apack; files that record none and hold data in an older format's tables were written before
  formats were recorded, which is format 1, and are refused too, naming the conversion; a new, empty environment is
  stamped by its first writable open, before anything is written to it (`tests/lmdb/format-stamp.spec.ts`). There is
  no upgrade at boot: `convertToCurrentFormat` (`lmdb/convert.ts`) converts an older environment in place a step per
  format — `convertToFormat2` (format 1's second records removed), `convertToFormat3` (rows per list index joined, a
  role always a list, a `deleted: true` mark turned into `trashedAt`), `convertToFormat4` (format 3's three tables
  loaded through an engine into the engine's keys, entities in the order they were created, relations under their
  ids, numbering rows as sequences) — each recording its own format, and only `scripts/ears-convert.ts` calls it, on
  a copy. With `COMPACT_COPIES` on the script then compacts the file (`compactEnvironment`): LMDB never shrinks one,
  and a conversion writes the new format beside the old tables before emptying them, so the file holds both until a
  compacting copy takes its place (what it saves on the production copy: `docs/plans/ears-storage-layout.md`, Step 5).
  It refuses an environment any process has open, read off LMDB's reader table, and refuses outright while the flag
  is off, so nothing can make a file this lmdb can't safely empty.
- The api's composition (`openAppStore()`, `packages/api/src/runtime/index.ts`) is the one production caller: it
  opens the store through `openDatabaseStore` (`@apackdev/host/database`), creates the engine on `store.kv` and binds
  the app. Host code (`@apackdev/host/services`, `/backup`) takes the store as an argument.

## Typed contract

`entities.ts`, `runtime.ts` and `typed.ts` are part of the typed EARS contract with the SDK's `types/entities.ts` and `types/sdk-entities.ts` and the generated `PackShapes`/`EntityName`. Editor completions and error messages depend on their exact form. Read `packages/apack-sdk/TYPED-EARS.md` and follow its checklist before changing them. The SDK's `EARS` namespace aliases this package's types and adds the SDK's entities and relation kinds.

## Guards

- `check:specifiers` (`scripts/check-import-specifiers.ts`): `findUpwardImports` (this package imports no `@apackdev/*`, in sources, tests, scripts and its `package.json`), `findLmdbImports` (only `src/lmdb/` imports `lmdb`; host, api, packs and pack tests never import `lmdb`, and packs never import `@apackdev/ears/lmdb`), `findSharedPackageLists` (the shared-instance list's consumers derive from `SHARED_INSTANCE_PACKAGES`).
- `tests/no-module-state.spec.ts`: no module-level `new Map`/`Set`/`WeakMap`/`WeakSet`/`Array`, `[]`, `{}` or `let` in `src/`, with no exception.
- The typed-EARS specs live in default-setup (`typed-query-builder`, `branded-entity-id`, `entity-shape-registry`, `sdk-type-safety`) and in the CLI (`facade-typing.integration.spec.ts`, against workspace source and the published packages); `published-exports.integration.spec.ts` and `published-sdk-types.integration.spec.ts` cover the packed package.

## Tests (`tests/`)

- `engine/`: black-box specs of the public API: `writes` (`create`, `upsert` and `write`, each entry point's refusals, the builder's attribute writes, the reserved names, the ids and fields returned), `relations` (link, unlink, `out`/`in`, `linkedTo`/`linkedFrom`/`linkedWith`, the hierarchy walks, cycle detection, roles), `queries` (the entry points and their refusals, filters, terminals and ordering), `transact` (every write undone by a unit that throws, one commit per unit, nesting) and `bulk-load` (the admin face's loads). They reach the engine only through `engine-under-test.ts` (`freshEngine`), and run twice: the `ears` project on the memory store and `ears-on-lmdb` on an LMDB store per engine (`EARS_KV=lmdb`, `vitest.config.ts`). A few specs pin existing quirks; they say so.
- The correctness harness (`_harness/`: a reference model, random workloads from `fast-check`, a backend that refuses a commit while an op runs): `engine/model-based.spec.ts` checks the engine against the model after every op, on a memory backend and an LMDB one — the rows, every refusal, a savepoint rolling back alone, and the derived reads the engine keeps in keys of their own (a type's entities, count and trash, an indexed and an unindexed `where`, `withRole`, each kind's `out`/`in`). Each run creates every id first and mixes in an edge linked, unlinked and linked again, since a workload over an empty store refuses nearly everything; and `lmdb/crash.integration.spec.ts` kills a child mid-workload with SIGKILL and checks the reopened files hold the model's state after the writes it acknowledged, or one more. The crash spec is the integration half (`vitest.integration.config.ts`, `npm run test:integration -w @apackdev/ears`), which the root integration pool runs.
- `vocabulary.spec.ts`: the rules in Vocabulary, over every member of the engine, `admin`, a query builder and a write builder — off the types for `is*`, `find*`, flags and chaining, off a real engine for pairs and absence — each with a case showing it names a member that breaks it.
- `engines.spec.ts`: a typed facade acts on whichever engine its getter returns; two engines in one process share nothing. The bound engine's operations are the SDK's, and its spec is `apack-sdk/tests/ears/bound-ears.spec.ts`.
- `lmdb/`: `ordered-kv` (the seam's contract, run against both backends), `convert` (format 1 to 2 to 3 to 4, and the refusal of another kind's files), `store` (`openLmdbStore`: what a unit commits is on disk however the process ends, read-only refusals, reset and replace, the copy, group commit's pause and cap, `durable()`, durable units, reader slots), `durability` (which sync each `durable()` waits for, a sync shared, a sync queued behind a failed one, and failures, with each sync finished or failed by the spec), `format-stamp` (the kind and format each environment records and is refused by) and `record-store` (`openRecordStore` and the memory store, the cases both share run against both).
- Test files run in parallel (`fileParallelism: true`): each creates its own engines.

## Benchmark

`bench/ears.bench.ts` loads an app-sized graph (50k entities, 200k attributes, 100k relations) through the admin face's bulk load, on an LMDB store in a temp dir (`EARS_BENCH_KV=memory` for the memory one), then times `query` by type with a `where` and `pickAll`, lookups by a unique value and by role (the value index), a relation traversal, `orderBy`, `first()` over a type, `getRow`, `pickAll`, `linkedWith`, a 10k-edge hub, short codes, and 1,000 creates, alone and as one unit (`transact`). It times the engine in `dist`, the build that ships: `npm run bench -w @apackdev/ears` builds the package first. `npm run bench:heap -w @apackdev/ears` (`bench/heap.ts`) reads the heap with the same graph loaded, then what opening its store again costs (the app's boot) and `getSchemaStats`; both run on LMDB, `EARS_BENCH_KV=memory` on `MemoryKV`. The readings are recorded in `docs/plans/ears-storage-layout.md` (Step 5); the tolerance is +10% median per case, and anything beyond it needs investigating before an engine change lands.
