# Successful WAL sync without an application acknowledgement

Run `python3 packages/apack-ears/bench/sqlite/lost-ack.py --output <new-evidence-directory>` in disposable Linux after matching package/dependency production. It requires the C compiler, the prepared Node/tsx runtime and a fresh output path. Source/helper digests and actual Node, architecture, SQLite, WAL and FULL-sync settings enter the report.

The interposer calls the real `fsync`/`fdatasync`, then stops only when that successful call targets the exact owned WAL and a one-shot arm file exists. The fixture first commits an incumbent, so the WAL header is already established. After arming, an ordinary EARS write, outer unit, bulk load or schema change attempts its actual commit. No JavaScript SQL or COMMIT method is replaced. The parent requires the actual stopped state, successful-sync event, absent acknowledgement file/output and SIGKILL exit. A fresh process must recover the complete candidate with exactly one sequence increment, preserve negative zero and the incumbent, then accept one explicit next write. The outer unit must recover both of its rows atomically. Schema recovery must expose the new declaration and permit the next write to its newly declared type.

A disabled-injector control must return its normal acknowledgement and fail the same missing-acknowledgement witness function used by the positive cases, preventing vacuous certification. Evidence retains raw logs and a completed/failed report; temporary compiled libraries and database payloads are removed from this newly reserved scratch directory.

This is process-death and acknowledgement-loss evidence. A successful kernel sync followed by process death is not physical power loss, a faulty device, an ambiguous COMMIT error response or a certification of arbitrary filesystems. The existing actual EIO-return matrix and driver-level unknown-outcome tests remain separate requirements/evidence. The write/unit/bulk-load revision passes on Linux x64 at 5142047f77; the added schema and shared-witness revision still requires qualification. These observations do not close all phase-6 requirements.


## Error returned after successful sync, before connection cleanup

`lost-ack.py --return-sync-error` is a separate unqualified physical-outcome probe.
The same one-shot shim performs the real WAL sync and records success, then returns EIO.
The child must observe the application operation throwing, records its error/quarantine
outcome, and stops without closing the database. The parent verifies both the syscall and
returned-error witnesses, kills the stopped child, and opens a fresh process to inspect the
actual complete-or-refused state, sequence, negative zero and a usable next write.
A persisted error-returned commit is acceptable only if the old handle was quarantined.
The disabled injector is rejected by the same witness checker. No COMMIT method is mocked.

Default successful-sync/lost-ack behavior remains required and is rerun alongside this mode.
The error mode may still observe complete rollback; it must report that outcome rather than
claim an ambiguous persisted commit occurred. This is not physical power-loss certification,
and the new mode needs actual disposable Linux execution before any recovery claim.
