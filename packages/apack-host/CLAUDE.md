# @apackdev/host

Host-only modules shared by the API, the renderer, the Electron main process, the CLI and `@apackdev/testing`. This package is the app runtime: the app's own state (`AppState`), pack registration, discovery, install and update, the pack runtime the app runs (loading, lifecycle, reload, writing), the backend bus, the migrations runners, the user's API keys, host service implementations and the one place the app's `HostRuntime` is assembled, backups and build-time helpers. The API (`packages/api`) keeps only transport, process boot and composition, and calls into it. Packs never import it, and it never imports transport (`fastify`, `@trpc/*`, `ws`) or `virtual:*` modules: the CLI and the pack test harness run it without a server. The root `CLAUDE.md` ("SDK packages") lists the subpaths and their one-line roles. This file covers how each area works. For the pack runtime (loader, `SDK_BRIDGE`, lifecycle, reload, writing, boot sequence), see [`src/packs/runtime/CLAUDE.md`](src/packs/runtime/CLAUDE.md).

## Package basics

- The package is private and has no build step. Every `exports` entry in `package.json` points at `src/*.ts`, so consumers compile or bundle it: the API's tsup build, and `scripts/bundle-package.ts` for the CLI and `@apackdev/testing`. `bundle-package.ts` inlines `@apackdev/host` and removes it from the published dependencies.
- Relative imports name the `.ts` file (`./staging.ts`), and host modules import each other by relative path, never as `@apackdev/host/*`. The tsconfig sets `allowImportingTsExtensions` and `customConditions: ["@apackdev/source"]`, so `@apackdev/sdk` and `@apackdev/ears` resolve to their source. Host imports only those two `@apackdev` packages, and never the API (`check:specifiers`).
- `npm run check:specifiers` (`scripts/check-import-specifiers.ts`) rejects `@apackdev/host` in pack sources, pack unit tests and CLI templates. `apack pack build` also fails a pack bundle that imports it.
- Scripts: `npm run typecheck:host` (`tsc --noEmit` over `src` and `tests`) and `npm test -w @apackdev/host` (vitest, `tests/**/*.spec.ts`, with the source condition set in `vitest.config.ts`). `npm run test:unit` includes this package.

## Layout

`src/` holds two kinds of thing, and the top level is where you see which. `features/` is the pack `host` itself,
laid out as any pack is; everything beside it is the runtime those features, and every other pack, run on
(`tests/boundaries.spec.ts` holds the two rules that carry it: feature implementations live in `{be,fe}` with pure contracts beside them, and no folder is named for a layer):

| | |
|---|---|
| `features/` | the pack `host`: `application/{be,fe}` (the app shell), `packs/{be,fe}` (installing and loading packs), `settings/{be,fe}` (the app's settings: the row, its one writer, and the system and machine behind the Settings view the renderer draws), `help/be` (the catalog delivered to Settings; article navigation lives in `settings/fe/help.ts`), `registration.ts` (what it registers) and `index.ts`, the `./features` export the API composes its registration from. Each feature's frontend is its own, and answers to the same `check:specifiers` rule a pack's does: what the package offers of them is named in `src/fe/index.ts`, its `./fe` export, and a feature reaches no other feature's `fe/` at all. A port both sides need lives at the seam instead (`src/fe/pack-frontends.ts`) |
| `packs/`, `bus/`, `services/`, `secrets/`, `app-state/`, `database/`, `migrations/`, `backup/` | the runtime: running *other* packs, routing events, the services, the app's keys and stored data |
| `fe/` | what a frontend needs that isn't a feature: the registered pack frontends, the API client's contract, app extensions, a window's migrations |
| `build/` | what tooling needs before anything runs, and **what it needs to know about *this app*** — packs, published manifests, shared instances, source resolution. That second half is the test for a new member: a helper that would make sense in any TypeScript repo belongs beside its caller, however many callers would find it convenient here. `declaration-text.ts` was added in `0cd3548e4` and removed the same day for failing it — it sorted union members, knew nothing about apack, and was here only because a repo script and a package's `src/` cannot reach each other. The reachable home is the one thing this folder must not be chosen for |
| `refs.ts`, `logs.ts`, `process-liveness.ts`, `exclusive-lock.ts`, `private-file.ts` | one module each, too small for a folder. `refs.ts`'s `HOST` holds the app's own refs, two of which are not features: `bus`, the machine every system runs under, and `drive`, which an agent driving the app claims on its connection |

A feature's halves sit together: `features/packs/be/system.ts` answers `features/packs/fe/machine.ts`. They lived in
`bus/`, `packs/runtime/` and `fe/` before, which is why `bus/` used to export a feature's system. Folders are named
for what they hold, never for a layer — no `core/`, `shared/`, `lib/` or `utils/`, at any depth, as in the API and
the renderer.

## Data dirs

All paths come from `resolveAppEnvironment()` (`@apackdev/sdk/env`). The context gives `userDataDir`, `packsDir` (`packs/`), `installedPacksFile` (`installed-packs.json`) and `appName`. The database, media and secrets file paths come from `@apackdev/sdk/utils` `paths.ts` (`ears-db`, `run-history`, `media`, `secrets.json`). No path is resolved at import time: each is resolved on the call that needs it, because the environment isn't known until then. Files this package writes under `userDataDir`:

- `host.json` holds `{ version, packFormat }` (`packs/host-info.ts`): the app's version and the pack snapshot format it reads (`PACK_SNAPSHOT_FORMAT`). `recordHostCompatibility` writes it at boot (`prepareHostDataDirs`), using a temp file and a rename. `readHostCompatibility` lets `apack pack install` and `apack pack dev` check a pack's `hostVersion` and build format without the app running; a field it lacks reads as unknown.
- `installed-packs.json` (`packs/installed.ts`) holds install state, `enabled`, `installedFrom`, update-check results and `lastError`. It is kept outside the database because the installer and the CLI's pack commands read and write it without opening the database.
- `pack-dev-servers/<packId>.json` holds `{ port, pid }` (`packs/dev-server.ts`). It is kept outside `packs/`, because an installed pack dir holds exactly the verified pack.
- `secrets.json` plus `secrets.key` (file vault only) sit in the same directory (`secrets/index.ts`).
- `packs/<id>/` holds installed packs — every pack, the ones the app ships included, which the installer places there at first boot (see Pack layout).

## App state (`app-state/`)

- The app's own state is one `AppState` row (`AppState-app`): `hasOnboarded`, `version` (the app version the data was migrated to), `packVersions`, `failedAgainst` (for a pack whose last apply of its content failed, the state of the packs it depends on at the time, which is what lets that apply be retried without re-importing it every boot), and the app shell's state: `surfaceVisibility` (the tabs the user showed or hid, by surface ref) and `lastActiveSurface`. Host declares the entity type (`HOST_ENTITY_TYPES`), which the engine's entity-type check and the test harness include and no pack may declare. What a pack's content last wrote is **not** here — it is the pack's own `AppliedContent` row below, so the revision and the per-item record that must agree about it cannot be recorded apart.
- Only host code reads and writes it, through `appState` (`get()` fills defaults; `update()` creates the row on the first write): the migrations runners, pack writing (`packs/runtime/apply.ts`, `lifecycle.ts`, `reload.ts`, the API's boot), `createAppBus()` (the application surface's `CLIENT_CONNECTED` carries `hasOnboarded`, the tabs' visibility and the surface last open), the host `application` system (`features/application/be/system.ts`, which records `SET_SURFACE_VISIBILITY` and `SET_LAST_ACTIVE_SURFACE` and sends `SURFACE_VISIBILITY_UPDATED` on a change and whenever it is asked to publish) and `services.onboarding` (`isComplete()`, `complete()`, which default-setup's onboarding calls).
- **Beside it, one `AppliedContent` row per pack** (`AppliedContent-<packId>`, `app-state/applied-content.ts`):
  `revision`, the compiled content it was applied from, and `items`, one entry per content item the pack has
  written — its entity type, its `contentHash`, a hash per **part** (a field's name for an entity;
  `fields`, `node:<id>` and `edges` for a flow), and, while one is outstanding, the **offer** the last apply
  left the user plus the version they have `dismissed`. `applyPacks` records it after every apply, failed or not,
  since what a run wrote is written either way, and keeps the entry of every item an apply left alone. It is
  an entity in the database, so a backup carries it: without it a restore would make every entity read as the
  user's own or as one they deleted.
- **An offer is a decision the user has about one item, and the record is where it waits.** An apply raises
  one for an item whose content moved and whose entity the user has edited (`update`), and for an item they
  edited that the content no longer declares (`removed`) — only where the entry's `onUserEdit` is `offer`,
  since under `theirs` the edit is their own writing. The next apply that reaches the key clears it; the user
  resolves one by taking the pack's version (`RESTORE_CONTENT_ITEM`, the one write in the app that overwrites
  their work, and the same call as "reset to factory"), keeping theirs (`DISMISS_CONTENT_OFFER`, which stores
  the hash they declined so only a later *change* asks again) or deleting the item
  (`DELETE_CONTENT_ITEM`). The Packs view draws them from `InstalledPackSummary.contentOffers` and `contentKept` — a count on the pack's row in the list, the rows themselves in its detail.
- **It is what the merge reads, and the revision is also the skip gate.** Deciding what to do with one item
  is a three-way question — what we applied last, what the pack declares now, what the database holds — and
  this is the only record of the first of those, which is why the revision lives with the items rather than
  beside them: a revision recorded without the items, or the other way round, is the state in which every
  item of a pack reads as the user's. The question only a **part** can answer is *which piece* of an item
  the user changed, and without it a digest over a whole item can say no more than that something in it
  moved — which is a freeze on everything else in it with nothing to explain it. The merge is one function
  (`@apackdev/sdk/content`'s `resolve`), and every verdict in the app is reached through it;
  [`pack-content-apply.md`](../../docs/archive/plans/pack-content-apply.md) has what the partial records it replaced
  each cost.
- Packs never read it, and their settings don't hold it: resetting settings leaves it alone (`default-setup/tests/settings-reset-app-state.spec.ts`). `appData.reset()` clears it with the rest of the database; the migrations the reset runs record the version again.

## Packs

**Registration** (`packs/registry.ts`): `createPackRegistry()` returns a new, empty registry of packs, an instance: the API's composition root creates the app's (`openAppStore()`), the pack test harness one per test file, and the CLI one per build. It owns everything packs registered (their registrations, the host's among them, the lookups the SDK reads, shutdown hooks and derived caches), with no module-level state (`tests/packs/registry-state.spec.ts` checks this module, `extensions.ts`, `backend-extensions.ts` and `fe/`), and it holds the only writes to it. It implements the SDK's `PackRegistryView` (`@apackdev/sdk/runtime`), which the composition root binds as `HostRuntime.packs`; the SDK's lookups (`getDesignated`, `stepRegistry`, `artifactRegistry`, `blockRegistry`, `_contentWriterRegistry`, `importCompiledContent`, `getSettingsCatalog`, `services`) read the bound one. Two registries in one process share nothing (`tests/packs/two-registries.spec.ts`). Settings declarations belong to the contribution catalog (`packs/catalog.ts`), independent of runtime registration. Its settings projection contains host app definitions, namespaced pack groups and qualified feature definitions, including disabled installed packs. Source authoring and native test/host declarations enter the same projection through explicit catalog operations; executable registration does not own their stored values. The SDK reads `settingsCatalog()` and subscribes through `onPackCatalogChanged()`.
- An installed origin's backend binding must match its accepted manifest (`packs/declaration-binding.ts`): feature IDs, roles, system/surface presence, surface visibility and provided service/repository names. The loader checks before initializing compiled content, and the registry checks before publishing registrations or settings authority. A declaration stamp identifies data; it does not prove membership. Native registrations without an installed origin require prior data admission through `nativeDeclarations` or `catalog.setNative()`. Binding checks feature identities, dependencies and settings; runtime failure/unload preserves those declarations. Their removal is an explicit catalog operation. Tests can compose authored fixtures with `createNativePackTestRegistry` from `@apackdev/host/testing`; production must supply its declarations independently.
- `registerContentRuntime(runtime, origin, appliers?)` binds a pack's content facet: declared entities, relation kinds, repositories, writers and optional source-key appliers. It requires the same accepted declaration identity and uses the registry's collision, rollback and teardown machinery. It claims no backend actors, roles or services; its complete manifest stays in the catalog. The testing harness uses this operation for data-only tests rather than assembling a fake backend registration.
- It throws on a duplicate pack id, an entity type or relation kind the app declares (the SDK's, or the host's `HOST_ENTITY_TYPES`) or another pack registered, a designation role another pack holds, a repository name another pack registered, or a service key that clashes with another pack or with `_HOST_SERVICE_NAMES`. A compile-time check fails when `HostServices` gains a key that list lacks. These checks run before anything is stored.
- Admission captures contribution addresses/membership once and builds candidate lookup tables without changing accepted state. Steps have exclusive wire ownership; designations and content writers also reject conflicting owners. Artifact, block and app-extension lookups use last-wins maps. Every change rebuilds these tables from the accepted owners, so removing a pack restores earlier contributions without undo logs or per-key removal histories. Commands are catalog data in stable declaration-admission order; the execution picker checks enabled declarations against accepted runtimes, and candidate admission still refuses collisions. Settings definitions remain in the independent contribution catalog.
- A host-owned backend service binding (`packs/service-binding.ts`, generated `bindServices`) starts pending, permits operations only after publication, and revokes authority/subscriptions on refusal or unload even if a generated hook throws or omits cleanup. Accepted registration maps and lookup tables commit once; `replacePack` then retires the incumbent binding and returns cleanup diagnostics instead of treating a committed replacement as refusal. Frontend registration also captures lookup data and stages its host-owned settings binding. `preparePackFE` and `prepareUnregisterPackFE` publish through a revision-checked commit; replacement failure preserves accepted forms, components and authority. The loader commits prepared CSS before lookup notification and retires old resources after acceptance.
- Backend service types and runtime access share the normalized declaration selection: own services,
  logger/emitter/repository/scoped settings, and consumed host/dependency APIs. Direct provider
  readiness uses accepted declarations and runtime generations, preserving an incumbent when a
  prospective replacement refuses. Provider handles never redirect to its replacement. The coordinator
  owns caller retirement after actor cleanup; failed scheduling revokes immediately. Host binding
  generations change even when the same host object is rebound. Inference agent methods are new calls;
  already-started calls/streams can settle on their original implementation. Ordinary results are not
  wrapped. `PackServiceAccess.servicesForAction(label)` supplies the same selection with guarded
  action logger/emitter attribution. Facades refuse structural mutation of shared services and diagnose
  unselected service names with the owning caller and `consumes.services`. Host identity comes from admission.
  Accepted step bindings carry their own `servicesForAction`; the flow executor supplies that factory to
  each handler, preserving its provider's selection, sender identity and retirement lifetime.
  Harness mocks overlay this selection, never expand it. Frontend `bindSettings` remains the
  separate settings-port contract.
- `unregisterPack` removes captured contribution keys and disposes its binding; it never re-reads authored getters to discover what to remove. `getDesignated(role)` resolves the accepted feature ref, `<packId>/<featureId>`. Reentrant registration changes are refused while admission or retirement is in progress. Initialization, migrations, content effects and actor restart remain the runtime caller's responsibility.
- Every pack's systems and surfaces are addressed `<packId>/<featureId>`, built-in packs included, so two packs can each have a `notes` feature. The host is the pack `host`, and registers like one (`hostRegistration` in `features/registration.ts`: the `application`, `packs` and `settings` features, their surfaces always and their systems where the caller runs them); its refs are `HOST` (`refs.ts`: `bus`, `application`, `packs`, `settings`), and no other pack may take its id. That makes surface ownership structural rather than checked: a registration names its own features and whoever reads one resolves it (`resolveName`, `@apackdev/sdk/ids`), pack ids are unique and neither id may hold a `/`, so no pack can produce a ref in another's namespace and there is no shadowing left to refuse.
- `getPackRuntime(packId)` returns the accepted installed origin and host-issued registration ID, or `null`. The ID belongs to captured registration state: replacement changes it even for identical build bytes, refusal preserves it, and removal deletes it. It is an identity, not a content revision, so compare it for equality only. `packs.loaded` carries it separately from the declaration and build revisions. Frontend settings issuance checks all three; existing grants also check the current registration ID, including when an origin object is reused. The ID is public lifecycle identity, not a credential or an authored manifest field.
- `getRegisteredEntityTypes()` (the engine's entity-type check) is the SDK's entity types, the host's (`AppState`) and the registered packs'.
- `getEventValidationMap()` maps each registered system (the host's among them) to the incoming event types it accepts; `receiveClientEvent` (`bus/client-events.ts`, the API's `bus.send`) checks against it. It's cached, and `registerPack` and `unregisterPack` drop the cache, so nothing else invalidates it.
- `getSurfaceEventValidationMap()` is its outgoing counterpart: surface id → the event types that surface receives. Each pack declares its own surfaces' (each feature's `surface.receives`, generated by `generate-entries` from its systems' specs), the host included (`HOST_SURFACE_EVENT_TYPES` in `@apackdev/sdk/events` and `PACKS_SURFACE_EVENT_TYPES`, each pinned to its union by `eventTypes`). The bus checks every `OUTGOING` against it and, on a miss, reports a `SYSTEM_ERROR` naming the surface and the type and drops the event — reported rather than thrown, because the caller is a running system, and `takeSystemErrors` already fails any pack test that leaves one (`tests/bus/outgoing-events.spec.ts`). Only a pack's own surfaces: a dependency's and the host's are declared by whoever owns them, so no pack widens another's contract.
- `runAppMigrations(registry)` (`migrations/index.ts`) runs every registered pack's `app`-line migrations and `runPackMigrations` their `pack`-line ones, both through `packMigrationTargets(line)`. Which line a migration is on is what its pack declared, so neither runner asks where a pack came from.
- Load problems: `recordLoadProblem(packId, problem)`, `loadProblem(packId)`, `clearLoadProblem(packId)` — why an installed pack isn't running although it is enabled. The loader records one for each pack it skips (`loadExternalPacks(registry)`, `activatePack`, a reload of a pack not running), and `registerExternalPacks` for one the registry refuses; `registerPack` and `teardownPack` clear it. The host `packs` system lists it as `InstalledPackSummary.loadProblem`, which the Packs view shows as "Failed to load: …" in place of the enabled state.
- Shutdown hooks: `registerShutdownHook(hook, key?)`, `runShutdownHooks()` (the API on exit), `runShutdownHooksForKey(key)` (a pack stopping) and `removeShutdownHooksForKey(key)`. Only the app calls them; packs declare `boot.onShutdown`.

**Discovery and registry** (`packs/discovery.ts`, `packs/installed.ts`)
- `readInstalledPackBuilds(packsDir)` lists visible directories and reads each through the common installed admission boundary: validated snapshot/manifest, receipt verification, directory-owner agreement and a receipt-owned backend entry. Invalid builds return explicit problems and remain installation evidence.
- `discoverPacks()` selects admitted builds; `installedPacks()` joins them to user choices/update provenance. Catalog consumers retain refusal diagnostics and the last accepted declarations.
- Boot prunes installation records for directories that are gone, retaining deliberate removal markers; a malformed manifest never erases a disabled choice or update source. Hidden install candidates are unpublished.
- `packContentOrder(packs)` applies in dependency order; cycles are reported and still applied. See [the pack runtime guide](src/packs/runtime/CLAUDE.md).

**Pack layout** (`packs/layout.ts`): the one layout used for `dist/`, release archives and installed packs. The layout is documented in the file header, with paths in `PACK_LAYOUT`.
- `stagePack(packRoot, stageDir)` validates current-format snapshot data and its agreement with `apack.json` before touching the destination, then verifies the producer-owned `dist/integrity.json`, copies its recorded installation files without `.map` files into a sibling stage and verifies the copied bytes before replacement. `sealPackBuild` writes the manifest and receipt before the build publishes `dist`; staging never recomputes expected checksums from edited output. Optional `packFormat` checks the target app's format before interpreting data. Foreign formats remain opaque. Versions are never substituted: the manifest must agree with the retained build.
- `verifyPack` throws on a format major other than `PACK_LAYOUT_VERSION`, a missing file, a checksum mismatch, or an unexpected extra file.
- `readPackBuild(dir)` captures current-format declarations and compiled content against the verified file receipt before runtime loading. It checks manifest agreement, required runtime entries and compiled content membership; discovery imports no pack modules. `packBuildProblem(dir, appFormat)` returns a `kind` (`format`, `declarations`, or `unreadable`) and `message`, or absence. The installer always refuses malformed/mismatched readable declarations. A format mismatch names which side to update; it is refused when the target app's format is known, otherwise warned about. A matching foreign format remains opaque to this CLI. `InstallOptions.packFormat` comes from the app or its `host.json` record. Staging failures clean up temporary files before returning; the accepted installation and `beforePlace` teardown stay untouched. The loader reports installed refusals to the Packs view.
- `createPackArchive` writes a reproducible `<id>-<version>.tgz` (no mtimes or uids, entries prefixed `<id>/`) plus a `.sha256` file. `extractPackArchive` checks the sha256 when one is given (`assertChecksum`, case-insensitive) and requires exactly one top-level dir.
- `packFileHashes(layoutDir)` hashes completed output when sealing its receipt. `stagedFileHashes(integrity)` projects the verified receipt into published files; it does not hash an authored source directory. App-managed refresh compares `shippedRevision` against the offered source; `verifyPack` checks installed build health independently.

**Installer** (`packs/installer.ts`): every install goes through stage, then verify, then place.
- Entry points:
  - `installPack(slug, sourceKind?)` dispatches by sourceKind: `local`, `url`, an `http(s)` URL, or otherwise a GitHub `owner/repo[@tag]` slug.
  - `installPackFromLocal` accepts a directory, a `.tgz`/`.tar.gz` (extracted with `extractPackArchive`) or a `.zip` (extracted by shelling out to `unzip`, with `findPackRoot`). An `sha256` option is checked (`assertChecksum`) before either archive is unpacked, so it covers the `.zip` path too.
  - `installPackFromGitHub` picks the release's first `.tgz` asset and requires its `<asset>.sha256` (or an `sha256` option): a release publishing neither is refused, as is a checksum file that isn't 64 hex digits.
  - `installPackFromUrl` warns when it has no `sha256` to check, and downloads under `DOWNLOAD_TIMEOUT_MS` (`packs/github.ts`, two minutes; the signal bounds the body too). `githubFetch` gives metadata requests 10s and release-asset downloads that same two minutes.
- `installFromDirectory` validates the source hint and stages built source when needed. It verifies the receipt, then `preparePack` copies the complete layout into a private `.<id>.installing-<pid>-XXXXXX` candidate and verifies both its bytes and equality with the accepted receipt. The copied manifest, compatibility and snapshot are checked before `options.beforePlace`; that hook receives its own metadata copy, so it cannot edit the installation target or result.
- Publication uses `replaceDir` after preparation and the hook. Optional `accept` receives a separate result copy with the candidate at its final path while the previous directory is retained. Acceptance is synchronous: refusal restores the previous files, or removes a refused first install; successful acceptance retires the previous directory. Rollback refuses to delete a destination replaced by another owner and retains the old backup for recovery. These filesystem guarantees do not undo callback effects or later initialization. Live app install/update use transactional runtime acceptance; download, load and registration refusal preserve the incumbent. Startup runs after filesystem acceptance; disabled updates retain enablement and only refresh declarations.
- `checkDependencies` reports the manifest's dependencies that aren't installed, which is one lookup in `packsDir`: a dependency is there or it isn't, and a pack the app ships is installed like any other. A directory counts only when it holds an `apack.json`, since `preparePack` copies into `.<id>.installing-*` before renaming.
- Install callers pass the target `installedPacksFile` to accept user ownership before publication. CLI source recording and runtime registration run in the same acceptance region; refusal restores the previous installation decisions and files. Metadata callbacks must not throw after committing runtime replacement.
- Boot discovery reports all competing entity-destination owners as pack problems before importing either runtime. Their builds and user enablement stay intact; disabling one resolves the conflict on refresh. Explicit candidate admission still refuses collisions atomically.
- `installShippedPacks` requires an explicit target record file. Missing packs install with `updatesWith: 'app'`, except those marked `suppressAppInstall: true`. Existing unrecorded or user-owned builds are preserved, even with identical bytes. App-owned refresh compares a deterministic `shippedRevision` of the published source files and layout version; it does not repair edited installed files on every boot. Build admission diagnoses invalid files. Outcomes distinguish `unchanged`, `preserved` and `suppressed` from actual installation; none certifies runtime health.
- Live replacement coordinates incumbent binding retirement through `PackReplacementOptions.retireBinding`. Publication still checks the candidate before touching the incumbent; `replacePackRuntime` stops its actors and disposes the captured binding after actual completion. Teardown likewise unregisters only after actor/subscription cleanup. XState's queued `stopChild` is not an immediate resource-lifetime boundary.
- `updateShippedPack` consumes a selected source revision and requires a current app-owned installation, checking ownership again at acceptance. It preserves enablement; disabled app updates only refresh builds/declarations. Offers compare verified source identity with `shippedRevision`, including same-version changes; user forks have no app-update offer. GitHub checks and remote update routes exclude app-owned records.
- `restoreShippedPack(id, source, packsDir, options)` deliberately selects the verified named app build, re-enables it and clears removal suppression while preserving database overrides. Identity/compatibility/refusal failures retain the incumbent or removal marker. Ownership-record preparation shares boot's helper; no executable pack code runs for offline restoration.
- `readAppPackSources` is the shared data-only reader for boot and CLI restore. It checks built source/snapshot/receipt consistency and refuses every duplicate id claimant. The registry's `appPackSourcesDir` feeds separate immutable catalog offers/diagnostics; offered defaults never define installed settings or help. Consumers carrying a selected offer into `restoreShippedPack` pass `expectedSourceRevision` so a changed candidate is refused during filesystem acceptance.
- `uninstallPack(id, packsDir, { installedPacksFile })` saves a deliberate-removal marker before deleting the build, restoring the prior record if deletion fails. Boot pruning retains the marker; disable remains a separate choice. Live controls distinguish install, named replacement, selected-revision restoration, disable and uninstall; advertisement grants no disable/uninstall privilege. Settings overrides remain in the database.


**Staging recovery** (`packs/staging.ts`)
- `stagingDirName(id, kind)` produces `.<id>.<installing|previous|retired>-<pid>-<hex>`. A previous tree is uncommitted; successful synchronous acceptance renames it to retired before cleanup.
- `recoverStagingDirs(dir, installedPacksFile?)` recovers stale previous trees even when a candidate reached its final path. Installation-record recovery requires the explicit target profile record path and restores only that pack's row. Stale installing/retired directories are cleanup litter; live owners and ambiguous previous copies are retained. Failed recovery never sweeps the previous tree, and installed discovery refuses a candidate with unresolved stale previous copies. Failures are reported without terminating boot.
- If retirement cannot be recorded after runtime acceptance, `replaceDir` warns and retains the previous copy. Recovery conservatively restores it on the next boot; filesystem failure cannot undo already committed runtime side effects.
- `prepareHostDataDirs({ userDataDir, packsDir, version })` records the host version and recovers staging dirs in `packsDir`. The API calls it before discovery.

**Updater** (`packs/updater.ts`, `packs/github.ts`)
- `checkForUpdates({ hostVersion })` covers enabled installed-packs entries that have an `installedFrom`. The API sets `installedFrom` only for GitHub installs. It runs when the Packs view asks (`CHECK_FOR_UPDATES`), nothing else, and caches nothing: each run replaces the entry's `availableVersion`/`availableTag`, or sets `updateCheckError` saying why there's nothing to offer (the check failed, the newest release's compatibility couldn't be confirmed, or no release supports this apack).
- `findLatestRelease` ignores drafts, non-semver tags and versions that aren't newer. It includes prereleases only when `resolveAppEnvironment().env === 'beta'`.
- With a `hostVersion`, `findLatestRelease` reads each candidate's range, newest first, from the `*.integrity.json` release asset, falling back to `apack.json` at the tag, and takes the newest one this app can run. Only releases newer than the installed version are candidates, so a check reads few manifests. A candidate whose range it couldn't read comes back with `hostVersionUnverified`, and the install checks the range again.
- The update installs `availableTag`, so it gets exactly the release the check found.
- `githubFetch` sends `GITHUB_TOKEN`/`GH_TOKEN` when set, which covers private repos and the higher rate limit, with a 10 s timeout. It throws `GitHubRequestError` with a `reason` of `rate-limited`, `not-found`, `unauthorized` or `failed`.

**Module bridge** (`packs/module-bridge.ts`)
- `withModuleBridge({ modules, hostPackages, resolveFrom, stubMissing, bridgedPackages, appOnly }, fn)` patches `Module._resolveFilename` while `fn` runs. Bridged specifiers map to cache entries under `__module_bridge__/<specifier>`, and each specifier's real resolved path also points at the same entry. `hostPackages` resolve from `resolveFrom`.
- The patch is restored in `finally`, but the cache entries stay, so lazy requires still get the bridged modules.
- `stubMissing`, used by the harness, turns unresolvable bare specifiers into proxies that throw when used.
- `bridgedPackages` (the pack loader passes `SHARED_INSTANCE_PACKAGES`): a module of those packages that `modules` lacks throws "<specifier> isn't provided by this apack: rebuild the pack…" instead of loading another copy, so a pack built against an SDK entry the app no longer has fails with that message.
- `appOnly` (the pack loader and the harness pass `APP_ONLY_EXPORTS`): requiring one of those specifiers throws "<specifier> is only for the app (…); pack code can't import it".
- The pack runtime wraps this in `withHostResolution` (`packs/runtime/bridge.ts`). `@apackdev/testing` uses it for dependency runtimes.

**Dev server** (`packs/dev-server.ts`)
- `writeDevServerMarker` writes the marker with a temp file and a rename. `removeDevServerMarker` deletes it.
- `devServerUrl(userDataDir, packId, filePath)` returns `null` when there is no marker or the process that wrote it is gone (`recordIsStale`), and throws on invalid JSON, a bad port or a missing pid. A marker outlives a crashed `apack pack dev`, and a dead port looks like a live one from here: without the check the pack's frontend fails to load with a connection error and nothing names the marker. `packages/main/src/modules/pack-protocol/PackProtocol.ts` calls it.
- A marker means a dev server was running and its process still is, never that anything on disk is current. Don't use it to skip a build.

## Bus composition (`bus/`)

`createBusMachine(options)` returns the XState machine that the app starts with systemId `bus` (`host/bus`, exported beside it). The options are:
- `onOutgoing` is the client sink.
- `registry` is the registered packs whose systems the bus runs (`getRegisteredSystems`, `getRegisteredPackSystemIds`).
- `listen(send)` feeds `INCOMING`, `CLIENT_CONNECTED` and `PACK_CLIENT_CONNECTED`, and returns an unsubscribe function.
- `systems` defaults to the registry's `getRegisteredSystems`. Every lookup goes through it, so a bus given a subset never reaches past that subset.
- `clientLoadedPacks` lists the packs whose systems wait for `PACK_CLIENT_CONNECTED`.
- `connectedEvents` lists outgoing events sent after each connection.

- On entry, the bus spawns every system with `id` and `systemId` equal to the system id. The `listen` actor is spawned as `bus-listen`. Distinct ids matter: with shared keys, stopping the bus stops only the last child.
- The bus routes `INCOMING` (client events, and `sendToSystem`, `fire` and schedule ticks from backend code) in every state. It starts in `awaitingClient`, where it drops `OUTGOING` (sends to surfaces) and `SYSTEMS_SPAWNED`. The first `CLIENT_CONNECTED` moves it to `clientSeen`, and entering that state sends `CLIENT_CONNECTED` and then `SEND_STATE` to every system except the systems of `clientLoadedPacks`. The same happens on each later connection. Nothing reports a client leaving, so the bus never goes back: `clientSeen` means a client has connected since boot, and a reconnecting client gets the startup data again (`tests/bus/app-bus.spec.ts`).
- `RELOAD_PACK`, `TEARDOWN_PACK`, `ACTIVATE_PACK`, `PACK_CLIENT_CONNECTED`, `PACK_CHANGED` and `DATA_REPLACED` are handled in both states. Each delivers its fact to the running systems and then asks ready systems to publish (`SEND_STATE`) — the ask only once a client has connected, since entering `clientSeen` asks everyone anyway, and always after the fact, so a system drops work held over rows that are gone before it describes itself.
  - `PACK_CHANGED` goes to every running system (a system that isn't running doesn't get it, without a warning).
  - Reload stops the listed systems and respawns current registrations. Packs with frontend code wait for a revision-checked readiness acknowledgment before `CLIENT_CONNECTED`/`SEND_STATE`; other packs raise `SYSTEMS_SPAWNED` while connected. The bus tracks waiting owners per actor instance and defers state requests after pack/data facts until readiness.
  - Activate raises `SYSTEMS_SPAWNED` only for packs that aren't client-loaded.
- Systems are stopped by reference, through `system.get(id)`.
- `routeIncoming` strips `systemId` and warns when the target isn't running, which can happen mid-reload.
- The app's composition is `createAppBus(registry)` (`bus/app.ts`), which the API starts in `runtime/index.ts`. It uses the SDK's bound `rootEvents` (`@apackdev/sdk/runtime`: the bound `HostRuntime`'s transport, the API's `transport/emitter`) for outgoing events, `CLIENT_CONNECTED`, `PACK_CLIENT_CONNECTED`, sends to surfaces from outside a system (`onSurfaceSend`, fed to the bus as `OUTGOING`, so they're dropped until a client connects) and incoming events, `getPacksWithClientLoadedFrontends(registry)` (`packs/layout.ts`) as `clientLoadedPacks`, and sends the `host/application` surface `CLIENT_CONNECTED` with `hasOnboarded`, `surfaceVisibility` (each feature's declared `visible`, with the user's choices over it) and `lastActiveSurface` (`ApplicationConnectedEvent`, read from `AppState`) after each connection. The API registers the backend `host/application` system beside the `packs` one. The harness composition is `packages/apack-testing/src/app.ts`. Behaviour tests live in `tests/bus/app-bus.spec.ts`, `tests/packs/runtime/reload.spec.ts` and `packages/api/tests/runtime/bus-client-connected.spec.ts`.

- `receiveClientEvent(registry, event)` (`bus/client-events.ts`) is what the API's `bus.send` procedure delegates to: it checks the event's `systemId` and `type` against the registry's `getEventValidationMap()` (a `*` entry accepts any type) and throws `UnknownClientEventError` otherwise — naming who sent it, as the bus's drops and the shell's refusals do, through `senderSuffix` (`@apackdev/sdk/events`) — logs it through the `app-events` logger (arrays over 5 items become `{ count, sample }`), and emits it on the SDK's bound `rootEvents` (`tests/bus/client-events.spec.ts`).

Native `steps` use the same `StepEntry` grammar as authored `extensions.steps`. The common catalog's
`steps()` projection and a window's `PackCatalogView.steps()` retain native, disabled installed and unbuilt
source metadata without code loading. Entries identify `(packId, type)`; inactive claims remain visible,
but two active packs cannot share a step wire. Backend native admission checks node data and executable
slots before settings binding. Step data is captured before validation; node/default/presentation/slot/
layout data is immutable, while executable component/function identities remain intact. Full native
frontend admission authority is the next required discovery checkpoint, before palette consumer changes.

## Packs frontend (`features/packs/fe/`)

Frontend registry writes require `FrontendAdmission`: either native declarations or the accepted backend
`LoadedPackEntry`. Delivery through a dev server does not change that authority. Capture metadata,
component-slot maps and declaration-directed routes before checking; preserve executable identities.
Retire provisional settings on declaration/capture refusal too. `stepBindings()` retains accepted owner,
declaration and host revisions independently of catalog lifetime. Native test operations compose explicit
declarations (`createNativeFrontendTestRegistry` from `@apackdev/host/fe/testing`, with
`nativeFrontendDeclarationFixture` from `@apackdev/sdk/testing`); production never infers them.

The host `packs` feature's frontend, beside the system that answers it (`features/packs/be/system.ts`), for the
reason that system isn't in the API: installing, updating and loading packs is what the app does, and a window only
renders it. The renderer pairs these with the Packs view's components (`packages/renderer/src/packs/surface.ts`),
which is all that is left there.

- `machine.ts` — the Packs surface's machine: the system's events (`PACKS_LIST`, `PACK_INSTALL_*`, `PACK_UPDATE_*`, …)
  and what the view asks for (`INSTALL_PACK`, `UNINSTALL_PACK`, `TOGGLE_PACK_ENABLED`, `UPDATE_PACK`,
  `CHECK_FOR_UPDATES`, `GET_INSTALLED_PACKS`). On `PACK_DEACTIVATED` it tells the shell `PACK_SURFACES_UNLOADED` and
  unloads nothing itself: the shell loads a pack's frontend and the shell unloads it, so there is one owner.
- `frontends.ts` — `createPackFrontends(io, packs)`, the shell's `packFrontends`: a pack's file URLs (with the
  revision, so an updated pack isn't served from the cache), what a default export must declare to count as a
  registration, and what unloading takes back. The window's two acts arrive as `PackFrontendIO`
  (`importModule`, `styles.prepare`/`remove`), so no browser global is reached here. A prepared style lease
  loads inert CSS and owns its readiness, commit and disposal; only accepted frontends apply it, and
  candidate failure disposes its own lease while retaining accepted styles. Its failure log,
  `[pack-loader] Failed to load FE entry pack://<id>/…`, is matched by the E2E fixture to fail a pack under test
  fast: its text is a contract, not a message.
- `install-url.ts` — `installFromProtocol(params)`, what `apack://install?pack=…&sourceKind=…&sha256=…` asks for; a window
  subscribes to the protocol and passes on the parameters. An optional checksum is validated and carried through
  `INSTALL_PACK` to the installer; malformed pins are refused rather than treated as absent. Checksum verification
  happens before the running copy is torn down or its files replaced.

## App shell (`features/application/fe/`)

The host `application` feature's surface: the frontend half of the feature whose backend half is `features/application/be/system.ts`. `createShellMachine({ packs, client, packFrontends, storage, notify, target })` builds it over the I/O it's given (`features/application/fe/types.ts`); the renderer composes it with the window's (`createAppShell`, `packages/renderer/src/core/app-shell.ts`), and tests with fakes. Its machine id is `application`, which its `#application.…` targets name; it runs as `HOST.application`. It's checked against the SDK's `HostShell` contract where it's defined (`satisfiesHostShell`, `machine.ts`), so a change to what frontend code may send or read fails the typecheck on one side or the other.

Modules, one concern each; a concern that owns a listener or subscription is a child actor:

- `surfaces.ts`: `withHostLast` (the host's surfaces, the Packs tab, after every pack's), `neighbourOf`, spawning a surface's actor with `id` and `systemId` its ref, moving between visible surfaces, and the back/forward history.
- `trail.ts`: `computeCrumbs` reads the breadcrumbs and context menu off the open surface's state `meta.breadcrumb` / `meta.contextMenu`; the `surfaceTrailer` child follows whichever surface is open.
- `layout.ts`: the panel sizes as pure changes. What the user resizes or toggles is saved through `storage`; the chat onboarding maximizes for the moment isn't.
- `input.ts`: the `hotkeyListener` (modifier tracking ported from VueUse `useMagicKeys`) and `mouseListener` (back/forward buttons) children, on `target`; with none, neither listens.
- `connection.ts`: the `connectionListener` child over `client.subscribe`: `onConnected` → `BUS_SUBSCRIBED`, `onDisconnected` → `BUS_CONNECTION_LOST`, `onFailed` → `BACKEND_ERROR`, and each message to `host/application` or to the surface it names.
- `pack-frontends.ts`: the `packFrontendLoader` child and `announcePackClientReady`.
- `machine.ts`: the machine, composing them.

Behaviour:

- **States:** `running.connecting` (tag `connecting`) goes to `error` after 30 s, showing the error page with `client.describeConnection()`; `running.connected` is re-entered on every `CLIENT_CONNECTED`; `onboarding.letter` (tag `welcome`) → `wizard` when `CLIENT_CONNECTED` has `hasOnboarded: false`, left on `ONBOARDING_COMPLETE`; `error` on `BACKEND_ERROR`.
- **Navigation:** `SELECT_SURFACE` sends `SURFACE_DEACTIVATED`/`SURFACE_ACTIVATED`, keeps the history, and (a main window's) sends the host's `application` system `SET_LAST_ACTIVE_SURFACE`; a main window opens on its first surface and switches to the recorded one on `CLIENT_CONNECTED`, or once its pack's frontend adds it (`pendingSurfaceId`). `SET_SURFACE_VISIBILITY` shows or hides a tab at once and sends the choice there too.
- **Opening a surface (`OPEN_SURFACE`, what `@apackdev/sdk/fe`'s `openSurface` sends):** a registered surface is selected and handed its events once the selection has settled. One that isn't registered waits in `awaitingSurface` while pack frontends may still add it (the loaded packs not read yet, or a load running or queued), opens when its pack's surfaces arrive, is refused through `notify` once loading settles, and is dropped when its pack unloads meanwhile. The latest navigation wins: a person's `SELECT_SURFACE`, or another `OPEN_SURFACE`, turns an open still waiting into a delivery of its events without selecting (`supersedeWaitingOpens`). The shell's own selections (the default surface, the restored last-active surface, an open whose surface is here) are `SELECT_SURFACE_BY_SHELL`, which supersedes nothing and cancels no entity open. A pack's system or action asks for the same with `broadcastToSurface('host/application', { type: 'OPEN_SURFACE', surface, events? })`; every window hears it, so the connection hands it to the machine as `OPEN_SURFACE_FROM_APP`, which only a main window (`ownsLastActiveSurface`) turns into `OPEN_SURFACE`: a popout keeps the surface it shows. A pack may build that payload at runtime, so one whose `surface` isn't a string or whose `events` aren't deliverable (objects with a `type`) is refused through `notify` rather than passed to a surface's actor.
- **Sending to a surface without opening it (`SEND_TO_SURFACE`, what the renderer's `sendToSurface` sends):** the same wait, in the same `awaitingSurface` queue — both requests ask it through `readyFor`, and an entry's `select` and the sender it carries are what differ — and the same refusal once loading settles, worded "Couldn't reach". One function writes every refusal (`refusal`, over the queued `SurfaceRequest`), so refusing at once and refusing after a wait say the same thing; they said different things until it existed, and only the immediate one named the sending pack. The entry carries the send's `from`/`via` for that reason: a refusal after the wait is the case where naming the sender helps most, since the surface's pack never loaded. What it doesn't do is select the surface: a cross-feature command is not a navigation. `@apackdev/sdk/fe`'s `_sendToLocalSurface` routes through here rather than reaching into `application.system.get(ref)`, so one owner answers "is that surface here yet" for both channels; it used to throw where the shell would have waited. How far each send reaches is pinned in `tests/features/application/fe/send-scope.spec.ts`: a backend `broadcastToSurface` reaches every window, this one only its own.
- **Hotkeys:** `PROCESS_GLOBAL_HOTKEY` maps the app's hotkeys to `TOGGLE_INSPECTION_PANEL` and `SWITCH_SURFACE_UP/DOWN`; others go to the open surface, and to other surfaces only their `global` ones. Skipped while `HOTKEYS_RECORDING_START` is in effect, and plain keys inside ProseMirror or Monaco.
- **Errors:** `SYSTEM_ERROR` is a toast, `severity: 'fatal'` the error page, and `diagnostic` nothing (it's in the Logs surface already). A backend failure (`ShellFailure`: a message, or `{ message, stack? }`) reaches `notify.errorPage` as the client reported it, so the page lays out an error's message over its stack.
- **Pack frontends:** `BUS_SUBSCRIBED` runs the loader in every state; requests during a run queue another read. Ordinary reads compare the accepted frontends' registration IDs; application state publication requests reconciliation when they differ. Disconnect stops the pending loader without removing accepted frontends. Reconnect refreshes their resources through the transactional loader; only a successful `client.loadedPacks()` read removes absent owners. `PACK_FRONTEND_LOADED` means acceptance: the shell replaces that owner's actors/definitions, preserving its tab position, visibility and selection when the selected feature remains. A refused first load reports its error; a refused replacement also unloads the frontend it would have replaced, which the next load brings back. Successful actors acknowledge their accepted registration ID after replacement. `SurfaceScope` remounts cached content when its actor instance changes; settings forms remount only for publication by their owner. Explicit `PACK_SURFACES_UNLOADED` still removes the owner and its actors.

- Welcome closing reads optional Threads designation from the shell's own window registry. Without a frontend destination it advances onboarding and keeps the current surface; it does not require default-setup or a process-global role binding.

## Settings (`features/settings/`)

The app's settings: `be/` holds persistence and the system, `fe/machine.ts` the surface's
machine, and `document.ts`/`validation.ts` hold pure contracts used by both halves, and the Vue is the renderer's (`packages/renderer/src/views/settings/`). The `./settings` export is what a
program composing the app needs: `createSettingsStore({ ears, catalog, onCatalogChanged })` and `createSettingsService(store)`.

The composition root supplies the store's owning engine and injects its settings service into app-data.
They do not borrow an ambient runtime's settings or engine. Test harnesses resolve their current engine
through the supplied provider because a test reset replaces it.

- **The row holds explicit choices.** Omitted keys follow current defaults. Targeted writes retain supplied
  values even when they equal today's defaults; whole-document replacement records every supplied value.
  Reset removes an override so future defaults apply again. An untouched app has no settings row.
- **App preferences belong to the host.** `app-definition.ts` declares defaults and JSON Schema for `app.hotkeys`,
  `app.personal` and ordered `app.projects`. The store always supplies them, without default-setup, and refuses a
  pack claiming `app`. Public types are generated with `npx tsx scripts/app-settings-types.ts`; the parity spec
  checks the recorded declaration. Pack groups are declared in `extensions.settings`, features in `features.<id>.settings`; both
  use JSON Schema and explicit defaults. The common installed catalog supplies definitions independently
  of runtime activation. Default-setup does not assemble application settings.
- **Window admission uses the same schemas.** Effective snapshots must carry all three owners and every declared
  settings value; they are validated directly, without filling absent values from defaults. Invalid broadcasts
  retain the accepted snapshot; invalid initial reads end disconnected. Declarations and values cannot change
  under unchanged revisions. Frontend exports reach pure validation, never the backend settings barrel.
  Pack-bound window reads share backend owner/dependency authorization; the host window port is administrative.
  Incompatible stored values remain refused under the current schema; there is no implicit grandfathering or
  conversion. A deliberate migration or explicit developer-data operation must repair such data.
- **One writer.** Every write, whoever makes it (the system, a feature through `services.settings`, an action, a
  applier, a migration), goes through `store.write()`, which checks the whole next document once
  (`document.ts`'s address checks and `validation.ts`'s catalog schemas for all three owners) and throws `SettingsRefusedError` otherwise, then tells its listeners.
  The system turns that into one `FEATURE_SETTINGS_UPDATED` per feature whose settings changed, and answers the
  sender `SETTINGS_SAVED` with the committed snapshot or `SETTINGS_REFUSED` with the store's reasons — **reply or broadcast, never both**
  (`be/answer.ts`), which takes the answer as an argument: `reply` where the write named a sender, and a
  broadcast to the `settings` surface where it named none — a write from an applier, a migration or a timer has
  nobody to answer. Broadcasting every answer
  instead leaves a sender that is not that surface learning nothing — a drive session's `/set-setting` then
  reports success for every refused write. A refusal is the sender's to fix, so only
  an unexpected error is reported as a system error.
- **`whileReplacingData`** brackets a wholesale replacement (reset or backup import): the writer tells listeners that one
  is running and, once it settles, that it ended, so those arrive in order with the writes they bracket and nothing
  is told a change in between. While one runs the system takes no pack change and refuses an app reset.
  The host-owned replacement callback retains settings write access for initialization and migrations;
  unrelated asynchronous pack writers are refused until replacement settles. That privilege expires with
  its callback, so detached initialization work cannot write during a later replacement.
- **The frontend reaches it through the SDK, never through the Settings view actor.** Each window establishes
  its validated `SettingsPort` before loading pack frontends. Host forms use that window resource; pack forms
  and consumers use generated owner-bound handles. A form emits an edit to its host-owned presenter,
  which submits it through the common writer and follows the correlated result. A save acknowledgement applies
  its authoritative snapshot before resolving, so a sequential write compares against committed data even
  before its broadcast arrives. Personal autosave awaits one save at a time and preserves typing beyond its
  acknowledged draft; a remote change/reset still cancels and replaces the draft.
- **One target is one place in the document.** A change names the app, a pack and its local group, or a
  qualified feature ref (`SettingsTarget`), and the whole of `path` is inside it. The Settings view's own General tab
  addresses `app.personal`, `app.projects` and `app.hotkeys`; its navigation labels do not add document levels.
  Reset can remove existing orphan fields without permitting new writes to undeclared owners.


## Secrets (`secrets/`)

- `secretsStore` (`secrets/index.ts`) is a lazy facade over `createSecretsStore` (`secrets/store.ts`). It uses the file vault in the `test` environment, and in `development` when `APACK_SECRETS_VAULT=file` is set. Otherwise it uses `osKeyVault(appName)`, backed by `@napi-rs/keyring` and loaded with `createRequire` on first use.
- `secrets.json` holds `{ format: 1, protection, keyId, secrets[] }`. Metadata is stored in plain text. Each value is AES-256-GCM encrypted with a 12-byte IV and a 16-byte tag, using the AAD `<id>:<provider>`. The 32-byte data key is stored in the vault under the account `secrets:<keyId>`, and an unprotected store keeps it in `secrets.key` beside the file. Both are facts about a store on disk rather than about either vault, so `dataKeyAccount` and `dataKeyFile` (`secrets/vault.ts`) are where they are written: a tool reading a store this process didn't create — `apack pack dev --with-secrets` — addresses it through them.
- `list`, `select`, `rename` and `delete` never load a data key. Selection and label rules come from `_secretRules` (`@apackdev/sdk/services`).
- `keyFor(provider)` decrypts the selected key on every call. An unreadable value throws an error that tells the user to enter it again in Settings, then Secrets.
- Every value the store encrypts or decrypts is passed to `registerSecretValue` (`secrets/redaction.ts`), so logs can mask it without keeping the plaintext. That module is the host's `SecretRedaction`, which `createHostRuntime` puts on the `HostRuntime` and `bindHost` installs as log redaction's matcher: the host owns the values and the SDK only reads the predicate, so no pack can install its own (`apack-sdk/tests/utils/secret-matcher-reach.spec.ts`).
- `status()` probes the OS vault once per process by reading the unused account `secrets:probe`. `KeyVaultUnavailableError` switches the status to `unavailable`, and a later successful vault call switches it back. Listeners from `onChange` hear these status changes as well as data changes.
- `allowUnprotected()` re-encrypts the readable values under a new key in the file vault, sets `protection: 'unprotected'` and deletes the old OS vault entries.
- `clearAll()` empties the key list but keeps `keyId`. If the file can't be read or emptied, it deletes the file.
- A data key created for a write that then fails is removed from the vault again (`pendingKeys`).
- `writePrivateFile` (`./private-file`) writes a unique temp file with mode `0600`, fsyncs it, renames it into place and fsyncs the directory. On Windows it retries renames that fail with `EPERM`, `EBUSY` or `EACCES`, and skips the directory sync.
- `secretsSnapshot()` is the `SecretsSnapshot` (`list()` and `status()`) the API's procedures return. `forwardSecretsChanges(registry)`, which the API's boot calls once, sends `SECRETS_CHANGED` (no values) on the bound `rootEvents` to every system that declares it takes it, on every store change.
- Only the API's `transport/secrets.ts` tRPC procedures (`add`, `replaceValue`, `allowUnprotected`, ...) and `services/inference.ts` (`keyFor`) touch values. `services/secrets.ts` exposes only `status`, `list`, `select`, `rename` and `delete` to packs.

## Services (`services/`)

- `createHostRuntime({ database, runHistory, engine, transport, appVersion, packs })` (`index.ts`) is the only place the app's `HostRuntime` (`@apackdev/sdk/runtime`) is assembled: the given bus and version, the engine (typed `Ears`, which `bindHost` binds), the app's registry as `packs` (the SDK's lookups read it) and the host-implemented services (`appData`, `onboarding`, `runHistory`, `inference`, `secrets`, `filesystem`, `settings`) over the app's database (`EarsDatabase`, opened through `@apackdev/ears/lmdb`), the engine's admin face, and the run history's database and engine. The API binds it in `packages/api/src/runtime/index.ts`, once it has opened both.
- `inference.ts`: `createModelResolver()` parses the `provider:model` id and checks the requested kind against `providerCapabilities`. It lazily imports the `@ai-sdk/<provider>` factory and passes an explicit `apiKey` (from `secretsStore.keyFor`) and an explicit `baseURL` (from `PROVIDER_BASE_URLS`). As a result, environment variables such as `ANTHROPIC_BASE_URL` can't redirect calls. The `baseUrls` option exists only for tests.
- `app-data.ts` (`createAppData({ database, engine, history, registry, settings, onReplaced })`) handles whole-app reset and backup export/import, of the app's database and the run history's alike; an import marks what the restored history left `active` as `stopped`. Its settings service and engine belong to the same runtime; replacement never borrows the ambient settings binding. Reset runs shutdown hooks, empties both databases (elmdb's `reset`, which keeps each schema; the app's through `engine.admin.clear()`, so its watches hear of it) and the keys, then starts packs as boot does. Import validates the current-format candidate before replacement, replaces each database's contents with the backup's (`replaceWith`, the database open throughout; the app's through `engine.admin.replaceWith`) and runs declared migrations. Failed replacement puts the previous data back the same way. `onReplaced` runs after the settings replacement boundary settles so consumers see the new revision. `onboarding.ts` supplies `isComplete()` and `complete()` using `createAppState` on the owning engine; preferences reset does not change that lifecycle state.
- `run-history.ts` (`createRunHistory(runs)`) is the SDK's run history over the run history's engine (`openRunHistory`, `database/open.ts`: `RunNode` entities in a database of their own), and, as it opens, stops what the last session left active and removes, whole, every session that ended more than `RUN_HISTORY_RETENTION_MS` (30 days) ago.

## Process liveness (`./process-liveness`)

A pid on disk can't say whether the process that wrote it is still there — pids are recycled, so a record a crash left behind names whatever took its number. Bounding the pid by when the record was written clears that and buys the opposite error. Which error to prefer isn't a property of the pid; it's a property of the question, and two questions are asked here, so there is a predicate per question:

- `lockIsHeld(pid)` — may I take this mutual-exclusion lock? The pid alone (anything but `ESRCH`, so a process another user owns counts), so it errs toward held: a dead holder whose pid this boot reassigned keeps the caller out, and no live holder is ever missed. The database write lock and the app's instance lock, which both guard against two writers — missing a live one is silent data loss, inventing a dead one is an error naming the file to delete.
- `recordIsStale(file, pid)` — is this recorded handle still worth using? The pid, bounded by the file's mtime against this boot (`lstat`, so a symlink answers for itself rather than for its target; a missing file is stale). It errs toward stale, since the caller falls back, re-derives or cleans up. Staging recovery, `readApiEndpoint` and the dev server marker.

`true` is the cautious answer in both, and the shapes differ enough that neither compiles where the other was meant. Each owns its reasoning: a call site picks the predicate that names what it is doing — local knowledge — rather than restating how bad corruption would be here.

`readApiEndpoint(apiPortFile)` is here too — the `{ port, pid }` a running API published, or `null` for a file a crashed run left behind — because it is the one reader that needs the bound. Its one reader is the CLI (`apack-cli/src/build/dev-reload.ts`, which `apack pack dev` and `apack pack build --watch` ask for a reload through). A pack reaches a running API through the app, never by reading its port file, so the export is listed unbridged by design in `tests/packs/runtime/sdk-bridge-drift.spec.ts`.

Only for a record this machine wrote: `os.uptime()` is this machine's boot and a foreign mtime is on another clock, so callers that can tell whose record it is (the write lock's `machine`, the instance lock's hostname) check that first.

Neither predicate is exact, and the module's header says what exact would take: the holder's start time read per platform, or an OS advisory lock the kernel releases on process death. For records this app writes itself there is a cheaper half-step — record the writer's `startedAt` and bound by that rather than an mtime, which is whatever last touched the file. It doesn't reach every caller, so it would shrink the problem rather than end it.

`build/packages-built.ts` keeps its own copy of the rule on purpose: it is the freshness check the package builds run through, so it resolves the packages' published `dist` — the stale copy, while they are being built. It bounds by the lock's own `startedAt` instead of a file's mtime.

## Persistence and backup

- EARS persistence isn't host code. Both databases are elmdb's, opened through `@apackdev/ears/lmdb`'s `openDatabase`: the app's (`openDatabaseStore` in `database/open.ts`) and the run history's (`openRunHistory` there, held to the SDK's `_RUN_HISTORY_SCHEMA`); host takes each database as an argument and never imports `elmdb` or `lmdb` (`check:specifiers`, `findLmdbImports`).
- `backup/index.ts`: progress lines go through a `log` sink (`BackupLog`), the app's logger by default and the command's stderr for `apack db import`, so they never land in output something else reads. A backup holds a folder per database (`BackupStores`): `lmdb`, the app's, and `runHistory`, the run history's, which the app's import and reset cover with the app's. `exportDatabase` copies the requested ones (`['lmdb']` by default) through each store's `copyTo`, elmdb's compacted copy (`databaseBackupStore`), so a backup taken from the running app holds one moment of each store instead of files read while a commit was landing; it then writes `metadata.json`: `timestamp`, `databases`, `includesMedia`, and what wrote it — the `appVersion` it is given (the app passes `getAppVersion()`) and each database's format (`storageFormats`). Those two are provenance only: whether a backup restores is settled by opening its databases, so one whose metadata claims a format its files aren't in still restores, and the refusal a genuinely unreadable database raises names the apack that made it. `readBackupSummary` returns `appVersion` too, so a backup folder says where it came from. It also copies the media folder it's given when `lmdb` is included and the folder exists. On import (`importDatabase(stores, path, mediaPath)`) it captures a private candidate and retains rollback files in `.apack-import-*` beside the database. The rollback copy survives until the replacement and the caller's acceptance succeed. Failure puts the incumbent back (`replaceWith`); failed recovery retains the durable copy and reports both failures with its path. App-data reset/import refuse overlapping replacement requests, and hold every pack's operation claim while they run, so no install, update or removal overlaps them. It validates the backup first (`readBackup`), so one this app can't restore — data in another storage format, or a missing main database — is refused before the user's files are touched. A store the backup lists but holds nothing for comes back as `missingDatabases`, which the app's import reports to the user and the CLI prints, rather than dropping it in silence. A backup holding stores this app doesn't have (a newer version's) throws `UnknownBackupDatabasesError` (`@apackdev/sdk/services`, so pack code can recognise it) unless `skipUnknownDatabases` says the user chose to import it without them: the Database settings ask, and `apack db import` takes `--skip-unknown`. `readBackup(dir, entityTypes)` checks a backup restores into this app (known databases, the primary one included, each present, and each opening in a storage format this version reads — every database the import would put in place, not only the primary one) and counts, without changing it, its entities per type. Types it holds that none of `entityTypes` names come back as `unknownEntityTypes` (a pack that was installed when the backup was made and isn't now): the rows are restored, not dropped, and the import says so — `services.appData.importBackup` returns them (the Database settings put it in the success message, so the user knows why nothing shows them), and `apack db import` prints a line. `services.appData` passes the app's media folder (`_getMediaPath()`); `apack db import` the target data dir's.

## Database (`database/`)

What opening an app's database needs, shared by the API's boot and `apack db`, so both read a data dir the same way (`packages/api/tests/runtime/app-database-parity.spec.ts`):

- `openDatabaseStore({ path, schema, readOnly?, warn? })` (`open.ts`): the elmdb database at `path` and a new engine on it. Opened to write, the database is held to what `schema` declares (`DatabaseSchema`: the registered entity types, relation kinds with their rules and roles, and each type's row rules, which the app's registry implements) through `admin.declare`, again on each `onRegistrationsChanged`, so a pack registering changes nothing another declared. The API's composition calls it with its registry. `openRunHistory(dir, { readOnly? })` opens the run history's database the same way, held to `_RUN_HISTORY_SCHEMA`, and moves files it can't read aside to `<dir>.unreadable-<time>` rather than keep the app from starting.
- `openAppDatabase({ env, userDataDir, readOnly? })`: for a data dir outside the app. It reads the installed packs' schema (`readInstalledSchema`, `schema.ts`: every enabled pack's own `apack.json` under `packsDir`, minus those `installed-packs.json` disables; entity types and relation kinds from all, and each pack's short code prefixes (each entity entry's `shortCode`), so a row created offline is numbered as the app numbers it — a pack's required fields stay unknown, its shapes being types no manifest carries; no pack code runs — **one account of the data dir, which is the packs directory**, because every pack is installed there, so a dir with no packs knows only the names the app itself declares, which is the truth about it rather than a degraded reading of it; `--schema-from` names packs to read as well, for a dir whose rows outlived the packs that declared their types — a snapshot file, a pack directory, or a directory of pack directories, which is what lets one flag cover an app, a checkout or a published `host-packs`; a directory is read as one pack before its children are, since a pack directory never holds packs, and it is resolved whether or not it adds anything, so a path naming nothing is an error rather than a flag that quietly did nothing), resolves the stores (`findAppDataPaths`, `layout.ts`: `_appDataPaths` in `@apackdev/sdk/utils`, which puts them under `appDir` — the one directory the app owns inside Electron's `userData`; a dir holding neither partition, or only one, throws), opens the database held to the schema the app last declared (which carries the packs' required fields no manifest does; a writable open of a database that holds none is refused, naming the fix: start apack on it once), and binds the engine (`db.ears`, beside `db.admin`). `schema` keeps meaning *declared by an installed pack*, since a backup's "no installed pack declares this" is read from it. `close()` puts back the engine that was bound before this one (none, in a tool) and closes the database, syncing what was committed. `readOnly` opens the files read-only, while the app holds the database open too: a write throws. Files elmdb can't read are refused by elmdb itself, so the app, `apack db` and a backup read all refuse them alike.
- `findRunningApp({ userDataDir, apiPortFile })` (`running.ts`): why an app runs on the data dir, or `null`. Two answers: `app.lock`, which the Electron main process writes through `publishRunningApp` as soon as it holds the single-instance lock and removes on `will-quit`; and the API's port file, whose process is running (`readApiEndpoint`, `./process-liveness`). The port file is the direct signal — the API process is the one that opens the database (`openAppStore`) — and `app.lock` covers the two windows it can't: before the API has published a port, and while a crashed one is being restarted. Without that, a tool would take the write lock in those windows and the API would then refuse to come back. Both count only while the process they name is running; one naming another machine, or one that can't be read, counts as an app, because what this guards is a database. Chromium's `SingletonLock` is not one of them, and is the wrong instrument for this: a symlink it writes on POSIX only, parsed from another product's private format, and failing *open* — unreadable, or Windows, and the answer is silently "no app".
- `holdDatabaseWriteLock(userDataDir, what)` / `findDatabaseWriter` / `assertNoDatabaseWriter` (`write-lock.ts`): `db-write.lock` in the data dir, holding the tool's pid, machine and what it's doing. A tool takes it while it changes the database and releases it however it ends (`process.on('exit')` too, dropped again on an explicit release so a process taking many locks doesn't pile up listeners). The lock is created with `wx` (`O_EXCL`), so the create is the acquisition and two tools arriving together cannot both have it — it checked and then wrote before, and every racer read "nothing holds it". The handlers are registered before the file is written, so there is no moment when the lock is on disk and an interrupt would take the default disposition and leave it behind; a lock whose pid has exited (`lockIsHeld`) is taken over, one naming another machine counts as held, and one missing either field can't be resolved and counts as held too; a release only removes this process's own. The lock is also released on `SIGINT`, `SIGTERM` and `SIGHUP`, which run no `exit` handler: without that, Ctrl-C on any `apack db` command left a lock behind. Only `SIGKILL` and power loss still can, and nothing can catch those. The API's boot calls `assertNoDatabaseWriter` before it opens the store, so a check-then-act race can't end with the app overwriting a change: the app refuses to start instead. Specs: `tests/database/write-lock.spec.ts`, `packages/api/tests/runtime/db-write-lock.spec.ts`.
- Specs: `tests/database/` (`open-app-database`, `installed-schema`, `running-app`).

## Build helpers and source resolution

- `build/pack-inputs` owns authored input traversal, content hashes and linked-source watch targets for the CLI and source-build readers. Generated output and dependencies have separate scopes; timestamps do not enter authored identity.
- Timestamps do not enter a compiler's recorded inputs either: where a compiler reads a regular file's time field (Tailwind and Vite stat what they scan), the fact records that file's content hash (`compiler-inputs/compiler-metadata.ts`). The compiler still sees the real time; a touched, unchanged file leaves a build current, and a record replays on a checkout whose times differ.
- `build/package-inputs` reads npm ownership, raw metadata, dependency lookup edges, files, links and executable permissions without module activation. Its normalized graph supplies content identity, subscriptions and compiler copying; the copy callback receives the bytes that were hashed. Root authored scopes are excluded unless an owner requests its contents.

- `SHARED_INSTANCE_PACKAGES` (`@apackdev/sdk`, `@apackdev/ears`) lists the packages a process loads once. The CLI's bundler externals and FE resolution, the pack loader's bridge (`packs/runtime/sdk-modules.ts`, generated by `build/render-sdk-modules.ts` with `npm run sdk-modules:update`), `@apackdev/testing`'s dependency-runtime bridge and `scripts/bundle-package.ts` derive from it; `check:specifiers` (`findSharedPackageLists`) fails when one of them names the packages itself. `APP_ONLY_EXPORTS` (`@apackdev/ears/lmdb`) are left out of `sharedInstanceSpecifiers`, so neither bridge provides them: pack code never loads the LMDB store, and pack tests never load `lmdb`. Pack frontends don't share `@apackdev/ears`: the renderer keeps no EARS data, so a pack FE inlines the constants and helpers it imports.
- `SHARED_DEPS` lists the packages the host provides to packs. FE entries reach a pack by resolution — `sharedFeModules()` folds them in with the SDK's frontend modules and `@apackdev/ui`'s exports, the renderer serves each and names it in the document's import map, and a pack's bundle leaves the specifier external. BE entries (`xstate`, `zod`) are bridged.
  - `getSharedFeDeps()` also shares every exported subpath of `@tiptap/pm` and `@tiptap/vue-3`. `@tiptap/pm/<name>` is `export * from 'prosemirror-<name>'`, so the two spellings name one module and `SharedDep.canonical` makes the prosemirror package the one both resolve to — loaded separately they are two copies of ProseMirror.
  - To give pack FE code a new SDK module, add it to `SDK_FE_MODULES`. The FE bundler's error message says to do this.
- `assertSourceResolution(resolve, processName)` throws when a checkout's `@apackdev/ears`, `@apackdev/sdk` or `@apackdev/ui` (a package with `src/`) resolves outside `src/`. It is called by the API boot (except under Electron) and the CLI bin (`apack-cli/bin/apack.mjs`) — host processes, which load workspace source. `@apackdev/testing` doesn't call it: a pack's test run resolves the packages' `dist` like the pack itself, and checks instead that the checkout built that `dist` from its current sources (`src/checkout-freshness.ts`).
- `withoutSourceCondition` strips the source condition from `NODE_OPTIONS`, for the processes the CLI starts to run pack code: `apack pack test`'s Playwright runner, `checkContentRuntimeLoads` and the fixture's launch env. Nothing here adds the condition; a host process that needs it is started through `scripts/with-source.mjs`, which runs before any TypeScript loader and keeps its own copy.

## Gotchas

- `writeInstalledPacks` reports a failed write rather than throwing; the enable/disable path turns that into an error the user sees. A background write (a content item outcome, an update check) still only logs.
- External pack FE code can't reach the renderer's `createFePackRegistry()` instance: the renderer calls `registerPackFE` on its behalf (see the pack runtime doc's FE entry section), and pack frontends read it through the SDK's lookups.
- Adding a host service means updating `HostServices` and `HostRuntimeServices` in the SDK, `_HOST_SERVICE_NAMES` (SDK `framework/service-consumption.ts`), `createHostRuntime`'s `services` (`services/index.ts`, with the implementation in `services/<kebab-case key>.ts`) and `HOST_SERVICE_KEYS` in `tests/boundaries.spec.ts`. All are type-checked against the SDK types. Helpers that aren't a service don't go in `services/`.
