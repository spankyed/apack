# apack-terminal: marks, recording and path links on remote targets (deferred)

Status: deferred by decision, 2026-11-12. Nothing here is started or scheduled. Not in v1
(`docs/plans/apack-terminal-v1.md`).

Why deferred: the owner does not need it for v1. Whether anyone uses remote targets in practice is not yet known
(see "When to revisit").

## What a target is

A terminal whose shell runs on another machine. The app starts it with a command (for example `ssh host`, or
`docker exec -i <container>`). The command runs a copy of the broker on the far side in proxy mode
(`apack-terminal proxy`), which carries the protocol back over the command's input and output. The app's
terminal service has one entry point for targets (`services.terminal.at({ command })`).

## What is missing on a target, measured in the code

Checked 2026-11-12 in `packages/default-setup/src/features/code/be/services/terminal.ts`:

| Feature | Local terminal | Target |
|---|---|---|
| Startup hook: command marks, directory reporting, prompt boundaries | yes | no. A target is opened with no integration (`if (target) { … open({ cols, rows, colors, images }) }`) |
| Vouching key for marks | yes | no, because there is no hook |
| Recording and playback (rewind) | yes | no. Recording is written on the machine that runs the shell, and the app never passes it a path on a target |
| Clickable file paths | yes | no. A printed path is resolved against the terminal's directory and opened in the code surface's explorer, which reads this machine's files; on a target the path names a file the explorer cannot see |

Shell marks are the one the user would notice first: on a target, a command's status cannot be read by a flow or
an agent.

## Why it is more than a feature

The work spans two repositories and one protocol.

- **The far side (broker, `spankyed/apack-terminal`).** The hook must be written to the remote machine, and the
  remote broker must keep the recording and serve it back. Today the broker starts whatever shell it is given with
  whatever environment and arguments it is given. The hook text is generated by the app, in TypeScript
  (`packages/default-setup/src/features/code/be/services/shell-integration.ts`), so the remote side needs the hook
  delivered to it: either the app sends the hook files over the protocol with the spawn request, or the broker
  takes over generating them. The second is a large move of code between repositories.
- **The near side (app, `spankyed/apack`).** Drop the target exclusion, carry the marks key to the far side (the
  spawn request already has a `marks_key` field, which the proxy passes through), read recordings and rewind them
  across the wire, and resolve paths against the target instead of this machine.
- **The protocol.** Rewind needs requests that read a recording on the far side (today `rewind` opens a path on
  the machine the broker runs on). Path resolution may need the far side to report its working directory in a form
  the app can interpret; the broker already reports it, but the app treats it as local.

Each step is a protocol change that both repositories must agree on. The v1 rule is that the protocol may change
in the same commit as the app; a target feature is larger than that, because the far side is a different
installation that may run an older broker.

## Open questions to answer before starting

1. **Versions on the far side.** If the far broker is older than the near app, a missing request must be handled
   without crashing. The protocol's `hello` exchange already refuses a different version; decide whether this
   feature needs a capability check instead.
2. **Where recordings live on a target.** The far side's disk, and what happens when the target goes away. Options:
   keep them on the far side and fetch on demand; or stream them to the near side as they are written.
3. **Hook delivery.** Send the hook files with each spawn, or install them once on the far side. Install-once is
   less traffic and more state to manage.
4. **Path links.** Whether to resolve only paths the far shell reported as its directory, or any path.

## When to revisit

- A flow, an agent or a person needs a command's status from a remote terminal.
- A person needs to look back through a remote session.

Until one of those, do not start.

## Relation to v1

v1 leaves targets as they are: a target terminal runs and draws, and has no marks, recording or path links. The v1
plan does not depend on this document.
