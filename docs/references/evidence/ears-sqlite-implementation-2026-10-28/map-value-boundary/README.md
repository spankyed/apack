# Map identity and ordinary relation-info validation

Source review after the f496 relation-key integration found two value-boundary defects. SqliteDatabase.canonical left JavaScript Maps untouched, while relation-key comparison reads own object fields. Distinct string-keyed Map infos could therefore both appear to have a missing/null key and merge into one edge. Ordinary link/updateRelation also serialized info without the finite/nested-value validation applied to attributes; invalid Map contents bypassed Object.values(Map), which is empty.

The correction canonicalizes string-keyed Maps recursively to own-field objects (__proto__ included), refuses non-string keys, validates nested Map values even inside other objects, and validates ordinary relation info before identity lookup/update. Unchecked relation loads remain deliberately unchecked, matching native maintenance restore; this is not a new schema restriction on raw repair/import. Native f496 ordinary relations call values::check_spec before check_info; its wire maps require string keys.

Pure controls executed the actual old/current canonical and validate methods. They reproduce the old relation-key collision and validation bypass; current methods keep distinct Map keys separate and refuse non-string keys and nested NaN. These are source-method negative controls, not native-driver parity. Shared regressions cover native/SQLite string and nested Map infos, relink identity, own __proto__ attribute fields, invalid info and unchanged commit/data on refusal. Matching focused CI is still required before claiming those cases pass on both backends.
