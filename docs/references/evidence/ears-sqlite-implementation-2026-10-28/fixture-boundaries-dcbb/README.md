# Scope application boot selection to isolated app launches

Strict `92ae` qualification failed 25 unit cases plus the CLI query integration because global APACK_STORAGE_FORMAT=sqlite/1 reached fixtures deliberately constructing elmdb stores or exercising default-profile refusals. These are fixture-selection failures; the production isolation guard is retained. Checkpoint `dcbb289e56` keeps EARS_EVALUATION_BACKEND=sqlite for shared SDK/engine contracts and scopes APACK_STORAGE_FORMAT to an additional isolated real-app step. That step requires six actual passes, no retries/skips/flakes, and the source-app witness that both managed stores contain the SQLite format/identity headers. Explicit both-backend host contracts remain in the chain.

The focused persistent-storage rerun uses the corrected boundaries over current package sources/frozen dependencies in a two-CPU/6-GiB disposable Linux arm64 container. It ends with 70 passes, 20 failures and a Vitest RPC timeout; 30-second test deadlines and shutdown failures after timed-out work are retained. The CLI integration did not run because the unit command failed. This is not a passing validation gate.

A second independent logic run changes only private temporary data to a 768-MiB tmpfs, keeping configured sync flags, test deadlines and backend selection unchanged. All 90 selected unit cases in seven files pass, including backup/import/restore/refusal, run history, native profile controls and API metadata. All 77 CLI integration cases then pass, without deselections. This supports the boundary correction and a storage-latency explanation for the earlier failures; it does not qualify persistent durability, recovery after power loss, application performance or arbitrary filesystems. No deadline was raised and neither failure was discarded.
