# Checkpoint-policy diagnostic protocol

The current ordinary FULL value-admission cohort at source `80c289ca62`, run [41312905554](https://github.com/spankyed/apack/actions/runs/41312905554), completes six trials on AMD EPYC 9V45. Five pass all budgets; 100k trial 2 fails heartbeat p99 at 16.3925ms against 16ms. The three 100k heartbeat p99 values are 14.8000/16.3925/15.4725ms. All six pass foreground operation, lookup, admission, turn-wait, WAL and observed disk budgets. This is an unresolved failure, not an improvement claim over the old 4ded cohort with unknown CPU identity. Other ordinary cohorts are still running at preparation time.

The 100k FULL reports show retirement/background batches above 8ms periodically, commonly about fourteen batches apart; 157 of 3127 GC batches exceed 8ms in trial 2. Build p99 is 2.97ms versus GC p99 12.95ms. The existing connection leaves wal_autocheckpoint at SQLite's default. [SQLite describes automatic checkpoints](https://sqlite.org/wal.html#performance_considerations) as running on the committing thread and explains the frequency/size tradeoff; [the pragma](https://sqlite.org/pragma.html#pragma_wal_autocheckpoint) controls its page threshold. This motivates a controlled policy comparison, not a proven causal attribution or production change.

`packages/apack-ears/bench/sqlite/checkpoint-admission.py` runs three fresh processes each at explicit 1000 and 128-page thresholds, alternating policy order. It keeps the original 100k FULL value/53-watch workload and all budgets, without profiler or per-commit spans. Actual pragma readback, CPU identity, source/native hashes, limits, raw outcomes, timings and budget failures are retained. Valid budget failures do not truncate later trials or become a diagnostic workflow failure; the receipt is always qualification:false. Invalid protocol/process outcomes stop with partial evidence, with no retry. The ordinary runner rejects checkpoint-control receipts.

The CI-only `sqlite_admission_checkpoint_probe` input selects this comparison under 2 CPU/6GiB/no swap, refuses simultaneous tracing, and uses matching source/package types. No production connection policy or durability setting changes. Scope excludes 10k/search/other platforms/actual app; all must qualify a promoted policy independently.

`python3 docs/references/evidence/ears-sqlite-implementation-2026-10-28/checkpoint-protocol/controls.py` passes nine pure actual-runner controls: ordered successful children, retention of budget failures, and refusal of wrong CPU, nonfinite measurements, wrong policy, invalid process outcome, instrumentation, relaxed heartbeat limit and wrong native binding. Fake children are protocol evidence only. Existing benchmark/admission metadata controls also pass; no native workload is run on the host. Actual diagnostic has not yet been dispatched because numeric qualification is already pending behind ordinary admission.
