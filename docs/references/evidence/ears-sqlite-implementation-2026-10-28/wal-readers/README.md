# Retained SQLite reader and checkpoint

Exact committed source 8c04a6bca0, capped disposable Linux ARM64 (two CPUs/6 GiB/no swap, capabilities dropped, real mode-denial preflight). Runner reconciles dependencies with scripts disabled and asserts unchanged lockfile. EARS build/types, the retained-reader case and root lint pass. The earlier typecheck failure from using an undeclared driver pragma helper is retained; corrected test uses the owned SQL accessors.

The real test pins a second read-only connection's SQLite snapshot, commits 16 new owners with 32 KiB fields, checks that the writer sees 17 while the reader still sees one, and observes WAL growth beyond the inserted payload size. Automatic checkpointing is disabled for this bounded fixture. TRUNCATE reports busy with incomplete checkpoint progress and cannot reduce the WAL while the snapshot is held. After rollback releases the reader, it sees all 17, truncation succeeds, and WAL size reaches zero without losing rows.

This proves a bounded mechanism, not a WAL growth ceiling, durable throughput, timeout budget, power-loss behavior or filesystem certification. Normal EARS reads release their snapshots before returning; the raw SQLite transaction deliberately models an external retained reader. Do not introduce a background reader without bounded lifetime/cancellation and measured growth under sustained writes. Existing busy_timeout=0 avoids configuring a foreground busy wait; this fixture does not measure elapsed stall latency. FULL/checkpoint I/O, automatic checkpoint scheduling, cross-process readers and application resource budgets remain required.
