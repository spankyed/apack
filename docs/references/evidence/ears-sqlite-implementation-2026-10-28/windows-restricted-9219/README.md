# Windows directory barriers under a restricted identity

Run41189779880 succeeds at exact source9219deb4dc86960283567db8b31d049082908a72. Actual restricted.json verifies same-user thread impersonation with administrator membership disabled and only SeChangeNotifyPrivilege enabled. A protected owner-only ACL permits a writable directory handle and successful FlushFileBuffers before and after deleting a flushed file. A second directory granting only read/execute refuses the writable handle with kernel error5. No account, existing profile ACL or machine setting changes.

This confirms the raw Win32 directory-flush mechanism can work without administrator access on the owned NTFS tree, Windows10.0.26100. The same run repeats ordinary Node23/libuv1.50 r+ directory success and r refusal under the hosted process's normal identity. Node itself was not executed under the restricted token: the combination is mechanism evidence, not installed-runtime qualification or an all-ACLs guarantee. Arbitrary filesystems, installed Electron architectures and physical power loss remain outside these observations. qualification stays false. Compressed original reports and original-byte receipts are retained.

The probe follows Microsoft's documented[CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken) and[RunImpersonated](https://learn.microsoft.com/en-us/dotnet/api/system.security.principal.windowsidentity.runimpersonated) APIs; the denial/identity/privilege controls are mandatory, not inferred from successful flush alone.
