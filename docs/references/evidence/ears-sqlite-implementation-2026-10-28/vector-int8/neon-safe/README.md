# Bounded-domain NEON counterfactual

Exact benchmark source: 53e625f2efa4ace05587cb5515cb14c2f7970b01. Disposable Linux ARM64, two CPUs, 6 GiB, no swap; no daily-Mac compiler ran. Official sqlite-vec source and identical compiler flags are recorded by the retained runner and native receipt. Only the NEON build defines SQLITE_VEC_ENABLE_NEON.

The l2-safe encoding restricts every coordinate to [-90,90], including equal-norm padding, avoiding the demonstrated signed-16 square overflow in this upstream NEON kernel. Authoritative inputs and reranking remain Float32. This does not make unrestricted int8 NEON safe.

This is a primitive experiment, not EARS integration or an adoption result. It demonstrates a faster sampled candidate kernel, but still fails synchronous responsiveness at 100k. Stable derived identity, multi-chunk aggregation, large k, real embeddings, background ownership and platform qualification remain open. Moving work off the app thread requires an explicit snapshot/transaction design; it is not established by these measurements.

## Execution ownership review

The current structured port (`packages/apack-ears/src/database.ts`) exposes synchronous readSync, EarsUnit.read and begin/savepoint/rollback. `src/query.ts` terminals use that connection; function predicates execute JavaScript and cannot simply become worker messages. `src/sqlite/database.ts:readSync` opens one BEGIN/COMMIT snapshot outside a unit and uses the existing connection inside a unit. It also records watch dependencies on that owner. `src/sqlite/search.ts:vector` ranks chunks and aggregates by owner in the same SQL request.

Consequently a worker's independent connection cannot replace an in-unit read: it cannot see the owner's uncommitted writes or savepoints. Blocking synchronous RPC to a worker does not meet an event-loop responsiveness gate. Offloading only candidate generation also risks combining old candidates with current authoritative rows, generations or trash state. An asynchronous result needs an explicit revision/snapshot contract and handling for close, cancellation, replacement and schema changes; copying embeddings on every request would need its own resource measurement.

Preserve the synchronous facade and unit behavior. A background read facility, if introduced, must be an explicit app-owned asynchronous operation, run the complete structured plan in one worker-owned read snapshot, and return its revision and generation identity. It cannot silently substitute for synchronous watch evaluation or arbitrary callback predicates. This is a design constraint, not an implemented facility or approval to change pack contracts. A separate reader needs bounded WAL lifetime and tests for concurrent update/delete/trash, generation replacement, close and stale-result publication. Uncommitted unit reads remain on their transaction owner. The candidate still owes synchronous vector acceptance or an explicitly approved product disposition; background execution alone does not satisfy it.

## Native selection complexity

Inspection of the exact archived sqlite-vec.c shows `min_idx` at line 5957 loops over requested k and scans n positions on every iteration, with a taken bitmap. Its local selection is O(n*k), plus bitmap work; the vec0 chunk path calls it at line 6981. This is not a claim that the whole query has only that cost or that selection dominates the measured runtime. The retained experiment times candidate SQL as a whole, not kernel subcomponents. In particular, measuring distance alone cannot establish end-to-end improvement. Before considering an extension patch, isolate selection versus distance on the same corpus/build and retain chunk/filter/large-k correctness; avoid adding a maintained fork solely from this asymptotic observation.

Next implementation checkpoint: establish the actual app-level vector latency and responsiveness requirements and trace a representative asynchronous host search flow, while keeping unit/watch semantics intact. Compare a fully integrated execution strategy against those recorded budgets, with multi-chunk owners, large k, hybrid and representative real embeddings. The existing 16 ms primitive heartbeat target remains a failed engineering gate, not a retroactively relaxed app requirement.
